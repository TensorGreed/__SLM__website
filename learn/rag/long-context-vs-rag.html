    Long context vs RAG: when to just paste the document

    If the documents fit in the model's context window, you can skip retrieval and paste them all into the prompt; RAG is for when they don't fit, or when sending everything costs too much time or money per question. Long context also isn't free in quality: small models read a long prompt less reliably than a short one with the right passages. IRS Publication 17 is about 286,000 tokens, 8.7 times a 32,768-token window, and its first chapter alone made a 1.5B model on CPU read about 26,300 tokens per question against about 600 for five retrieved chunks; the first such question took over 20 minutes, and on 11 keyed questions the two arms scored 7 and 6, too close to call.

    Runs on: CPU, about half an hour for every block on the page once the models are downloaded, most of it the first long-context question Updated: 26 Nov 2026

    Tested on 26 Nov 2026 · Python 3.12.3 · sentence-transformers 3.3.1 · transformers 4.46.3 · torch 2.5.1 · pypdf 5.1.0 · numpy 2.1.3 · Ollama 0.32.9 · qwen2.5:1.5b-instruct (Q4_K_M) · CPU (20-core Arm, no GPU)

    The trade

    A context window is the number of tokens a model can read at once: 32,768 for Qwen2.5-1.5B-Instruct, the model on this page. If your documents fit, the simplest system is no system: put them in the prompt and ask. Retrieval earns its complexity in three situations:

    • The documents don't fit. One long PDF can exceed the window; a folder of them always will.
    • Cost per question. Every token in the prompt is processed on every question. On a CPU that is seconds or minutes; on a paid API it is money.
    • Reading quality. Models use information in a long prompt unevenly, worse in the middle than at the ends, as Liu et al. (2023) showed. Five relevant passages are easier to read than fifty pages.

    Prompt caching changes the cost side when many questions share the same long prefix: the server keeps the processed prefix and only reads the new question. That helps a fixed document a lot, and helps nothing when each question needs different documents.

    import hashlib, json, os, re, urllib.request
from pypdf import PdfReader

if not os.path.exists("p17.pdf"):
    urllib.request.urlretrieve("https://www.irs.gov/pub/irs-prior/p17--2025.pdf", "p17.pdf")
FURNITURE = re.compile(r"^(Userid:|AH XSL/XML Fileid|Page \d+ of \d+|The type and rule above).*$", re.M)

def clean(page):
    page = FURNITURE.sub("", page)                  # proof-sheet lines on every page
    page = re.sub(r"-[ \t]*\n(?=[a-z])", "", page)  # re-join words hyphenated at line ends
    page = re.sub(r"\s*\n\s*", " ", page)
    return re.sub(r" {2,}", " ", page).strip()

def split_keep(text, sep):
    if sep == "":
        return list(text)
    parts = text.split(sep)
    return [p + sep for p in parts[:-1]] + ([parts[-1]] if parts[-1] else [])

def recursive_split(text, size, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size:
        return [text]
    pieces = []
    for piece in split_keep(text, seps[0]):
        pieces += [piece] if len(piece) <= size else recursive_split(piece, size, seps[1:])
    chunks, buf = [], ""
    for p in pieces:                                # greedy packing, never over size
        if buf and len(buf) + len(p) > size:
            chunks.append(buf)
            buf = ""
        buf += p
    return chunks + [buf] if buf else chunks

text = "\n\n".join(clean(p.extract_text()) for p in PdfReader("p17.pdf").pages)
chunks = recursive_split(text, 512)
starts = [0]
for c in chunks[:-1]:
    starts.append(starts[-1] + len(c))

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json")
      for q in json.load(open(f))["questions"]]
gold = []                                           # chunks holding a whole evidence span
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    gold.append({j for j, s in enumerate(starts) if any(s <= a and b <= s + len(chunks[j]) for a, b in occ)})
print("sha256:", hashlib.sha256(open("p17.pdf", "rb").read()).hexdigest()[:16], "| chunks:", len(chunks),
      "| questions:", len(qs), "| with a relevant chunk:", sum(map(bool, gold)))

    Questions. The 14 of the 80 frozen questions whose evidence is on pages 8 to 22. Eleven have a short answer key (pub17-answer-keys.json), and only those are scored, with the same crude key-string check as the what is RAG page. Fourteen questions can show a cost difference clearly; for answer quality they are a demonstration, not a measurement.

    Arms. RAG: all-MiniLM-L6-v2 retrieves five chunks from the whole publication. Long context: the chapter goes first in the prompt and the question last, so the server can reuse the processed chapter between questions. The first long-context call pays for the whole chapter; the rest pay only for the question.

    import json, os, urllib.request

host = os.environ.get("OLLAMA_HOST", "127.0.0.1:11434")      # where `ollama serve` listens
OLLAMA = host if host.startswith("http") else "http://" + host
MODEL = "qwen2.5:1.5b-instruct"                              # `ollama pull qwen2.5:1.5b-instruct`

def chat(prompt, num_predict=120, num_ctx=4096):
    body = {"model": MODEL, "messages": [{"role": "user", "content": prompt}], "stream": False,
            "keep_alive": 0,                                 # unload after each call, so no cached prompt carries over
            "options": {"temperature": 0, "seed": 0, "num_ctx": num_ctx, "num_predict": num_predict,
                        "num_thread": 10}}                   # fastest on this machine; adjust for yours
    req = urllib.request.Request(OLLAMA + "/api/chat", json.dumps(body).encode(), {"Content-Type": "application/json"})
    return json.load(urllib.request.urlopen(req, timeout=900))["message"]["content"].strip()

tags = json.load(urllib.request.urlopen(OLLAMA + "/api/tags"))
print(MODEL, "digest", next(m["digest"][:12] for m in tags["models"] if m["name"] == MODEL))

    import time
import numpy as np
from sentence_transformers import SentenceTransformer

def chat_timed(prompt, num_ctx, keep_alive):
    body = {"model": MODEL, "messages": [{"role": "user", "content": prompt}], "stream": False, "keep_alive": keep_alive,
            "options": {"temperature": 0, "seed": 0, "num_ctx": num_ctx, "num_predict": 120, "num_thread": 10}}
    req = urllib.request.Request(OLLAMA + "/api/chat", json.dumps(body).encode(), {"Content-Type": "application/json"})
    t0 = time.time()
    r = json.load(urllib.request.urlopen(req, timeout=3600))
    return r["message"]["content"].strip(), r["prompt_eval_count"], time.time() - t0

keys = json.load(open("pub17-answer-keys.json"))["keys"]
norm = lambda s: re.sub(r"[^a-z0-9]", "", s.lower())
in_ch1 = [i for i, q in enumerate(qs) if 8 <= q["page"] <= 22]
scored = [i for i in in_ch1 if qs[i]["id"] in keys]
print(len(in_ch1), "questions on pages 8-22,", len(scored), "with an answer key")

embedder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device="cpu",
                               revision="1110a243fdf4706b3f48f1d95db1a4f5529b4d41")
index = embedder.encode([c.strip() for c in chunks], normalize_embeddings=True, batch_size=64)
ask = "Answer the question using only the {what} above, in one or two sentences. If it doesn't contain the answer, say so."
results = {}
for arm in ("rag", "long context"):
    right, toks, secs = [], [], []
    for n, i in enumerate(scored):
        q = qs[i]["question"]
        if arm == "rag":
            ids = np.argsort(-(index @ embedder.encode(q, normalize_embeddings=True)))[:5]
            ctx = "\n\n".join(f"[{k}] " + " ".join(chunks[j].split()) for k, j in enumerate(ids, 1))
            answer, t, s = chat_timed(f"{ctx}\n\n{ask.format(what='passages')}\n\nQuestion: {q}", 4096, 0)
        else:
            answer, t, s = chat_timed(f"{chapter1}\n\n{ask.format(what='document')}\n\nQuestion: {q}", 32768,
                                      0 if n == len(scored) - 1 else "5m")
        right.append(any(norm(k) in norm(answer) for k in keys[qs[i]["id"]]))
        toks.append(t)
        secs.append(s)
    results[arm] = right
    print(f"\n{arm}: {sum(right)} of {len(scored)} match the key")
    print(f"  prompt tokens read: first question {toks[0]:,}, then median {int(np.median(toks[1:])):,}")
    print(f"  seconds: first question {secs[0]:.0f} s, later questions median {np.median(secs[1:]):.1f} s")
both = sum(a and b for a, b in zip(results["rag"], results["long context"]))
print(f"\nright in both arms: {both} | only rag: {sum(a and not b for a, b in zip(results['rag'], results['long context']))}"
      f" | only long context: {sum(b and not a for a, b in zip(results['rag'], results['long context']))}")

    • The cost gap is large. Every long-context prompt held the whole chapter, about 26,300 tokens, against about 600 for RAG. The first one took over 20 minutes on this loaded CPU; the first RAG question took seconds.
    • Caching closes the time gap after the first question, because every question shares the same chapter prefix: later long-context questions took a few seconds, like RAG's. Ollama still reports the full prompt length, since the cached tokens count as read. That only works when the long context is the same for every question; a different document per question pays the full cost every time.
    • Answer quality was too close to call. Long context matched 7 of 11 keys and RAG 6; 4 were right in both, 3 only with long context and 2 only with RAG (3 vs 2, p = 1.0). And the long-context arm only worked because the evidence was known to be in chapter 1; RAG searched the whole publication.

    Limits: 11 scored questions, one 1.5B model with a Q4 quantization, one chapter, CPU only. Prompt-processing speed on a GPU is far higher, so the time ratio here overstates it for GPU serving, while the token ratio holds anywhere.

    Variations and parameters

    ChoiceWhat it changesDefault here
    num_ctxOllama's context length. Too small and the prompt is cut silently from the front; larger costs memory for the KV cache.32,768 (long), 4,096 (RAG)
    Prompt orderDocument first, question last lets the server reuse the document between questions.Document first
    HybridRetrieve generously (20 to 50 chunks) into a long context: fewer misses than top 5, cheaper than everything.Not measured
    QuantizationQ4 weights and a quantized KV cache save memory and can cost long-context accuracy.Q4_K_M weights, f16 cache

    Pitfalls

    • Ollama's default context is small. Unless num_ctx is set, Ollama uses a default of 4,096 tokens, far below the model's 32,768, and drops the overflow without an error. Set it per request, as the code does (Ollama FAQ). BrewSLM sizes it per request from the prompt length for the same reason (synth_backends/ollama.py).
    • Lost in the middle. Facts in the middle of a long prompt are used less reliably than those at the start or end (Liu et al., 2023). Long context removes retrieval misses and adds reading misses.
    • Caching that breaks reproducibility. The reused prefix makes later answers depend on earlier calls; the what is RAG page shows a temperature-0 answer changing because of it. This page unloads the model before the first long-context call so every run starts the same way.
    • Assuming it fits. Pub 17 alone is 8.7 windows long. Count tokens with the model's tokenizer, as the token count above does, before designing around long context.

    In BrewSLM: answers come from retrieved passages, never the whole corpus, and the documents → Q&A check measures whether those passages are enough before any training.

    Practice

    1. Your documents total 20,000 tokens and the model's window is 128,000. Do you need RAG?

    Not to fit them. You might still want it for cost per question (20,000 tokens read every time unless cached), for reading quality with a small model, or because the collection will grow. Measure both on labelled questions.

    2. Why did the second long-context question cost so much less than the first?

    The prompt starts with the same chapter, so the server reused its processed state (the KV cache) and only read the new question. A different document per question would pay the full cost every time.

    3. What does Ollama do if your prompt is longer than num_ctx?

    It truncates the prompt to fit, keeping the most recent tokens, so with the document first and the question last the start of the document is what gets lost, without an error. Count tokens and set num_ctx above the total.
