    HyDE: retrieve with a hypothetical answer

    HyDE (hypothetical document embeddings) asks a language model to write a passage that would answer the question, embeds that passage instead of the question, and retrieves the real passages closest to it. The idea is that a fake answer looks more like a real answer than a question does, even when its facts are wrong. On 80 questions about IRS Publication 17 with a 1.5B model writing the passages, HyDE alone found the answer chunk in the top 5 for 53 against 57 for the plain question, and averaging the two vectors gave 62: neither change is significant, and at this model size HyDE did not clearly pay for its extra generation.

    Runs on: CPU, about four minutes for every block on the page once the models are downloaded Updated: 26 Nov 2026

    Tested on 26 Nov 2026 · Python 3.12.3 · sentence-transformers 3.3.1 · transformers 4.46.3 · torch 2.5.1 · rank-bm25 0.2.2 · pypdf 5.1.0 · numpy 2.1.3 · Ollama 0.32.9 · qwen2.5:1.5b-instruct (Q4_K_M) · CPU (20-core Arm, no GPU)

    Why embed a made-up answer

    A dense retriever compares a question vector with passage vectors. Questions and passages are different kinds of text: "Can I deduct my travel to a shareholders' meeting?" against "You can't deduct transportation and other expenses you pay to attend stockholders' meetings…". HyDE, from Gao et al. (2022), closes the gap from the question side:

    1. Prompt a language model: "write a passage that answers this question".
    2. Embed the generated passage (in the paper, several of them, averaged with the question).
    3. Retrieve real passages near that vector. The generated text is thrown away; only real passages reach the answer step.

    The fake passage can be factually wrong and still help, as long as it uses the vocabulary and shape of a real answer. It can also mislead: if the model guesses a different topic, the vector points there.

    Measured: HyDE against the plain question on IRS Publication 17

    Same corpus, 512-character chunks and 80 frozen questions as the other RAG pages (30 + 50); a chunk is relevant when it holds the whole evidence span, and 79 is the ceiling.

    import hashlib, json, os, re, urllib.request
from pypdf import PdfReader

if not os.path.exists("p17.pdf"):
    urllib.request.urlretrieve("https://www.irs.gov/pub/irs-prior/p17--2025.pdf", "p17.pdf")
FURNITURE = re.compile(r"^(Userid:|AH XSL/XML Fileid|Page \d+ of \d+|The type and rule above).*$", re.M)

def clean(page):
    page = FURNITURE.sub("", page)                  # proof-sheet lines on every page
    page = re.sub(r"-[ \t]*\n(?=[a-z])", "", page)  # re-join words hyphenated at line ends
    page = re.sub(r"\s*\n\s*", " ", page)
    return re.sub(r" {2,}", " ", page).strip()

def split_keep(text, sep):
    if sep == "":
        return list(text)
    parts = text.split(sep)
    return [p + sep for p in parts[:-1]] + ([parts[-1]] if parts[-1] else [])

def recursive_split(text, size, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size:
        return [text]
    pieces = []
    for piece in split_keep(text, seps[0]):
        pieces += [piece] if len(piece) <= size else recursive_split(piece, size, seps[1:])
    chunks, buf = [], ""
    for p in pieces:                                # greedy packing, never over size
        if buf and len(buf) + len(p) > size:
            chunks.append(buf)
            buf = ""
        buf += p
    return chunks + [buf] if buf else chunks

text = "\n\n".join(clean(p.extract_text()) for p in PdfReader("p17.pdf").pages)
chunks = recursive_split(text, 512)
starts = [0]
for c in chunks[:-1]:
    starts.append(starts[-1] + len(c))

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json")
      for q in json.load(open(f))["questions"]]
gold = []                                           # chunks holding a whole evidence span
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    gold.append({j for j, s in enumerate(starts) if any(s <= a and b <= s + len(chunks[j]) for a, b in occ)})
print("sha256:", hashlib.sha256(open("p17.pdf", "rb").read()).hexdigest()[:16], "| chunks:", len(chunks),
      "| questions:", len(qs), "| with a relevant chunk:", sum(map(bool, gold)))

    Output

    sha256: 2d2381d62c7c77ed | chunks: 2170 | questions: 80 | with a relevant chunk: 79

    Arms. Dense retrieval with all-MiniLM-L6-v2 on the question; on the hypothetical passage alone; on the normalised average of the two vectors. Then BM25 on the question, and on the question with the passage appended (HyDE was designed for dense retrieval; this checks the keyword side).

    import math, time
import numpy as np
from sentence_transformers import SentenceTransformer
from rank_bm25 import BM25Okapi

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device="cpu",
                            revision="1110a243fdf4706b3f48f1d95db1a4f5529b4d41")
vecs = model.encode([c.strip() for c in chunks], normalize_embeddings=True, batch_size=64)
questions = [q["question"] for q in qs]
t0 = time.time()
fake = [hypothetical(q) for q in questions]
print(f"hypothetical passages: {(time.time() - t0) / len(qs):.1f} s a question")

qv = model.encode(questions, normalize_embeddings=True)
hv = model.encode(fake, normalize_embeddings=True)
mix = qv + hv
mix /= np.linalg.norm(mix, axis=1, keepdims=True)
words = lambda s: re.findall(r"[a-z0-9]+", s.lower())
bm25 = BM25Okapi([words(c) for c in chunks])

def found(ranked, k=5):
    return [bool(set(list(ranked[i])[:k]) & gold[i]) for i in range(len(qs))]

def mcnemar(x, y):
    b = sum(p and not q for p, q in zip(x, y))
    c = sum(q and not p for p, q in zip(x, y))
    p = min(1.0, 2 * sum(math.comb(b + c, i) for i in range(min(b, c) + 1)) / 2 ** (b + c))
    return f"{b} vs {c}, p = {p:.3f}"

runs = {"dense, question": np.argsort(-(qv @ vecs.T), axis=1),
        "dense, HyDE passage": np.argsort(-(hv @ vecs.T), axis=1),
        "dense, average of both": np.argsort(-(mix @ vecs.T), axis=1),
        "bm25, question": [np.argsort(-bm25.get_scores(words(q))) for q in questions],
        "bm25, question + passage": [np.argsort(-bm25.get_scores(words(q + " " + f))) for q, f in zip(questions, fake)]}
print("\nquery                      top 1  top 5  top 10  (of 80)")
for name, r in runs.items():
    print(f"{name:<26}" + "".join(f"{sum(found(r, k)):>7}" for k in (1, 5, 10)))
for a, b in (("dense, HyDE passage", "dense, question"), ("dense, average of both", "dense, question"),
             ("bm25, question + passage", "bm25, question")):
    print(f"{a} vs {b}: {mcnemar(found(runs[a]), found(runs[b]))}")

    hypothetical passages: 4.6 s a question

dense, question                36     57     70
dense, HyDE passage            19     53     63
dense, average of both         31     62     70
bm25, question                 39     56     64
bm25, question + passage       32     57     62
dense, HyDE passage vs dense, question: 10 vs 14, p = 0.541
dense, average of both vs dense, question: 10 vs 5, p = 0.302
bm25, question + passage vs bm25, question: 8 vs 7, p = 1.000
    • The passage alone was worse than the question, most clearly at the top: 19 questions had the answer chunk first, against 36 for the question itself. At top 5 the gap narrowed to 53 against 57 (10 gained, 14 lost, p = 0.54). When a 1.5B model guesses the wrong rule or topic, the vector follows the guess.
    • Averaging with the question helped a little at top 5: 62 against 57 (10 gained, 5 lost, p = 0.30), while losing at top 1 (31 against 36) and tying at top 10. Suggestive at best, for the cost of one generation per question, about 4.6 seconds on this CPU.
    • For BM25 the extra words changed almost nothing (57 against 56 at top 5). The generated passage brings in plausible tax vocabulary, and plenty of it is the wrong vocabulary.

    Limits: one 1.5B writer, one prompt, one passage per question (the paper averages several), one small embedding model, 80 single-fact questions drafted with an AI assistant. HyDE was proposed for retrieval without labelled training data, with a much larger writer than this. Treat this as "not worth it at 1.5B on this corpus", not as a verdict on the method.

    Pitfalls

    • Hallucinated facts steer retrieval. A wrong guess about the rule points the vector at the wrong section. The HyDE paper relies on the encoder to filter out such detail; with a small writer, the guess dominates (table above).
    • Showing the fake passage to users. The hypothetical text must never reach the answer step or the screen. It exists only to make a vector; in the code above it is embedded and then dropped.
    • Latency. A generation per question before retrieval even starts: here several seconds on CPU, more than the retrieval and reranking combined (reranking page).
    • Comparing against a weak baseline. HyDE is often compared with dense retrieval alone. Compare it with what you would otherwise ship, such as hybrid search plus a reranker, which reached 72 of 80 at top 5 on these questions (reranking).

    In BrewSLM: there is no HyDE step; retrieval is BM25 with an optional cross-encoder reranker, tuned per project by the documents → Q&A sweep.

    Practice

    1. Why can a hypothetical passage with the wrong number still retrieve the right chunk?

    The embedding captures topic and phrasing far more than the exact figure. A passage saying "you can exclude up to $500 a day of long-term care benefits" sits close to the real one saying $420, because nearly every other word matches.

    2. You see HyDE help on one corpus and hurt on another with the same model. What would you look at?

    How often the generated passages are on the right topic for each corpus. A model that knows the domain writes useful fakes; on a niche corpus it guesses, and the guesses point elsewhere. Averaging with the question vector limits the damage.

    3. What does averaging the question and passage vectors protect against?

    A fake passage that drifts off topic. The question vector keeps part of the query anchored to what was actually asked, so a bad generation moves the vector less.
