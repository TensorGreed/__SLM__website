    Parent-document retrieval: search small, return big

    Parent-document retrieval indexes small chunks for precise matching but returns the larger section each one came from, so the model gets the surrounding context the small chunk lacks. A close cousin, the sentence window, returns the matched chunk plus its neighbours. On 80 questions about IRS Publication 17 with at most 2,048 characters returned, finding 1,024-character parents through their 256-character children held the answer for 62 questions against 52 for searching the parents directly (p = 0.052, suggestive), but eight plain 256-character chunks held it for 69: for single-fact questions, small chunks alone did best.

    Runs on: CPU, about two minutes for every block on the page once the model is downloaded Updated: 26 Nov 2026

    Tested on 26 Nov 2026 · Python 3.12.3 · sentence-transformers 3.3.1 · transformers 4.46.3 · torch 2.5.1 · pypdf 5.1.0 · numpy 2.1.3 · CPU (20-core Arm, no GPU)

    Two sizes for two jobs

    Chunk size is a compromise between two jobs. Matching wants small chunks: one topic per vector, short enough for the embedding model to read in full. Answering wants large ones: the sentence before the rule, the exception after it, the table header. Parent-document retrieval stops compromising:

    1. Cut the document into parents (sections, pages, or large chunks).
    2. Cut each parent into children and remember which parent each child belongs to.
    3. Embed and search only the children.
    4. Map the top children to their parents, drop duplicates, and send the parents.

    The sentence-window variant skips the parent level and returns each matched child with its neighbours on both sides. Both need nothing more than an id map; no library is required.

    Children inside parents

    Children are made by splitting each parent, never the whole text, so a child can't straddle two parents. Install:

    huggingface_hub==0.36.2 pypdf==5.1.0 numpy==2.1.3

    The corpus and the 80 frozen questions shared by every RAG page here (30 + 50); the load block's 512-character chunks are not used below.

    import hashlib, json, os, re, urllib.request
from pypdf import PdfReader

if not os.path.exists("p17.pdf"):
    urllib.request.urlretrieve("https://www.irs.gov/pub/irs-prior/p17--2025.pdf", "p17.pdf")
FURNITURE = re.compile(r"^(Userid:|AH XSL/XML Fileid|Page \d+ of \d+|The type and rule above).*$", re.M)

def clean(page):
    page = FURNITURE.sub("", page)                  # proof-sheet lines on every page
    page = re.sub(r"-[ \t]*\n(?=[a-z])", "", page)  # re-join words hyphenated at line ends
    page = re.sub(r"\s*\n\s*", " ", page)
    return re.sub(r" {2,}", " ", page).strip()

def split_keep(text, sep):
    if sep == "":
        return list(text)
    parts = text.split(sep)
    return [p + sep for p in parts[:-1]] + ([parts[-1]] if parts[-1] else [])

def recursive_split(text, size, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size:
        return [text]
    pieces = []
    for piece in split_keep(text, seps[0]):
        pieces += [piece] if len(piece) <= size else recursive_split(piece, size, seps[1:])
    chunks, buf = [], ""
    for p in pieces:                                # greedy packing, never over size
        if buf and len(buf) + len(p) > size:
            chunks.append(buf)
            buf = ""
        buf += p
    return chunks + [buf] if buf else chunks

text = "\n\n".join(clean(p.extract_text()) for p in PdfReader("p17.pdf").pages)
chunks = recursive_split(text, 512)
starts = [0]
for c in chunks[:-1]:
    starts.append(starts[-1] + len(c))

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json")
      for q in json.load(open(f))["questions"]]
gold = []                                           # chunks holding a whole evidence span
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    gold.append({j for j, s in enumerate(starts) if any(s <= a and b <= s + len(chunks[j]) for a, b in occ)})
print("sha256:", hashlib.sha256(open("p17.pdf", "rb").read()).hexdigest()[:16], "| chunks:", len(chunks),
      "| questions:", len(qs), "| with a relevant chunk:", sum(map(bool, gold)))

children, parent_of, child_starts, pos = [], [], [], 0
for p_id, p in enumerate(parents):

for p in parents[:-1]:

    Measured: what to return after searching small chunks

    Setup. all-MiniLM-L6-v2 at a pinned revision. Every arm returns at most 2,048 characters: plain 1,024-character chunks (top 2); plain 256-character chunks (top 8); 256-character children mapped to their parents (top 2 distinct parents); and a sentence window: each top child with one neighbour on each side (about 768 characters), overlapping windows merged, added in rank order until the next would pass the budget. A question counts as found when the returned text holds a whole occurrence of its evidence span.

    import math, time
import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device="cpu",
                            revision="1110a243fdf4706b3f48f1d95db1a4f5529b4d41")
q_vecs = model.encode([q["question"] for q in qs], normalize_embeddings=True)
occ = [[m.span() for m in re.finditer(re.escape(q["evidence"]), text)] for q in qs]
t0 = time.time()
child_rank = np.argsort(-(q_vecs @ model.encode([c.strip() for c in children], normalize_embeddings=True,
                                                 batch_size=64).T), axis=1)
parent_rank = np.argsort(-(q_vecs @ model.encode([p.strip() for p in parents], normalize_embeddings=True,
                                                  batch_size=64).T), axis=1)
print(f"embedded {len(children)} children and {len(parents)} parents in {time.time() - t0:.0f} s")

def covered(i, ranges):
    """Does the union of returned (start, end) ranges hold a whole evidence span?"""
    return any(any(a <= s and e <= b for a, b in merge(ranges)) for s, e in occ[i])

def merge(ranges):
    out = []
    for a, b in sorted(ranges):
        if out and a <= out[-1][1]:
            out[-1] = (out[-1][0], max(out[-1][1], b))
        else:
            out.append((a, b))
    return out

def plain(i, k):
    return [(child_starts[j], child_starts[j] + len(children[j])) for j in child_rank[i][:k]]

def big_chunks(i, k=2):
    return [(parent_starts[j], parent_starts[j] + len(parents[j])) for j in parent_rank[i][:k]]

def to_parents(i, k=2):
    picked = list(dict.fromkeys(parent_of[j] for j in child_rank[i]))[:k]
    return [(parent_starts[p], parent_starts[p] + len(parents[p])) for p in picked]

def windows(i, w=1, budget=2048):
    """each top child with w neighbours a side, added until the next window would pass the budget"""
    out = []
    for j in child_rank[i]:
        lo, hi = max(j - w, 0), min(j + w, len(children) - 1)
        win = (child_starts[lo], child_starts[hi] + len(children[hi]))
        if sum(b - a for a, b in merge(out + [win])) > budget:
            break
        out.append(win)
    return out

arms = {"1,024-char chunks, top 2": big_chunks, "256-char chunks, top 8": lambda i: plain(i, 8),
        "256 children -> 2 parents": to_parents, "256 children -> windows": windows}
res = {}
print("\narm                          found  distinct chars sent")
for name, f in arms.items():
    res[name] = [covered(i, f(i)) for i in range(len(qs))]
    sent = np.mean([sum(b - a for a, b in merge(f(i))) for i in range(len(qs))])
    print(f"{name:<28} {sum(res[name]):>3}/80   {sent:>8,.0f}")

def mcnemar(x, y):
    b = sum(p and not q for p, q in zip(x, y))
    c = sum(q and not p for p, q in zip(x, y))
    p = min(1.0, 2 * sum(math.comb(b + c, i) for i in range(min(b, c) + 1)) / 2 ** (b + c))
    return f"{b} vs {c}, p = {p:.3f}"

print("\nparents vs 1,024-char chunks:", mcnemar(res["256 children -> 2 parents"], res["1,024-char chunks, top 2"]))
print("parents vs 256-char chunks:  ", mcnemar(res["256 children -> 2 parents"], res["256-char chunks, top 8"]))
print("windows vs 256-char chunks:  ", mcnemar(res["256 children -> windows"], res["256-char chunks, top 8"]))

    • Searching small beat searching big. The same 1,024-character parents, picked through their best-matching child instead of through their own vector, held the answer for 62 questions instead of 52 (16 gained, 6 lost, p = 0.052). A parent's vector averages several topics, and the embedding model reads only its first 256 word pieces; a 256-character child is read in full.
    • Plain small chunks did better still: 69 of 80, while sending fewer characters (about 1,540 on average, since recursive chunks run short of 256). Eight separate chunks cover eight places in the document; two parents cover two. For single-fact questions, breadth beat context (10 against 3 questions, p = 0.092, suggestive).
    • Windows landed in between (64), with context around each hit and more places covered than two parents.

    Limits: retrieval only. The point of returning parents is that answers improve with context, and that is not scored here; single-fact questions whose evidence fits in 256 characters favour plain small chunks. One document, one small model, 80 questions drafted with an AI assistant.

    Variations and parameters

    ChoiceWhat it changesDefault here
    Parent unitFixed-size chunk, page, or a real section from the document's headings (best when headings survive extraction).1,024-character chunk
    Child sizeSmall enough for one topic and the model's input limit.256 characters
    Parents returnedFewer parents, more context per hit; more parents, more places covered.2
    Window widthNeighbours on each side of a matched child.1
    Scoring a parentIts best child's score (here), the sum of its children's scores, or how many of its children are in the top k.Best child

    Pitfalls

    • Children that straddle parents. Splitting the whole text twice, once at each size, produces children that cross parent boundaries and map to the wrong parent. Split each parent, as the code above does, and assert that both levels rebuild the text.
    • Duplicate parents. Several top children often share a parent. Deduplicate before counting k, or two of your "top 2" are the same text; the measurement keeps each parent once, in the order of its best-ranked child.
    • Parents longer than the generator should read. Whole chapters as parents blow the prompt budget; the long context page measures what that costs on CPU.
    • Embedding big chunks and expecting the model to read them. all-MiniLM-L6-v2 truncates input over 256 word pieces (model card), so a 1,024-character chunk's vector often ignores its second half. That alone explains part of the gap above.

    In BrewSLM: passages are a single size per retrieval setting, with no parent map; the documents → Q&A sweep re-cuts the corpus at other passage sizes instead.

    Practice

    1. Why does finding a parent through its child beat finding it through its own embedding?

    The child's vector is about one thing and the model reads all of it. The parent's vector mixes several topics and, with a 256-word-piece limit, may ignore its second half, so a question about that part matches it weakly.

    2. Three of your top five children belong to the same parent. What does that suggest, and what do you send?

    That the parent is very likely the right section. Send it once, then fill the rest of the budget with the next distinct parents. Counting how many top children a parent has is itself a good parent score.

    3. When would you prefer plain small chunks over parents?

    When answers are short, self-contained facts and the budget is tight, as on this page: eight separate chunks cover more ground than two parents. Parents pay off when answers need the surrounding text: conditions, exceptions, table headers.
