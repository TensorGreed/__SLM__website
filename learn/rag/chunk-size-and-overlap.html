    How to choose chunk size and overlap for RAG

    Pick the smallest chunk size that still holds a whole answer, check it against your embedding model's input limit, and compare sizes at the same number of characters retrieved rather than the same number of chunks; add overlap only if answers are being cut at chunk boundaries. Overlap is not free: it repeats text, so a fixed budget holds less new material. On 80 questions about IRS Publication 17 at a 2,048-character budget, 256-character chunks gave dense retrieval the best recall (68 of 80), 128-character chunks could hold the whole answer for only 57 questions, and 25% overlap did not beat no overlap at any size.

    What size and overlap trade

    The chunking strategies page compared ways of cutting text. This page holds the method fixed (recursive splitting) and turns the two dials that remain.

    • Size. A chunk has to be big enough to hold the fact whole, and small enough that its one vector is about one thing and fits the embedding model's input. Bigger chunks also mean fewer of them fit in the prompt.
    • Overlap. Repeating the end of each chunk at the start of the next keeps a fact near a cut whole in at least one of them. The cost is more chunks to embed and store, and duplicate text in what you retrieve.

    The fair comparison holds the retrieved characters constant, not k. Five chunks of 1,024 characters is four times the prompt of five chunks of 256, and of course it holds the answer more often.

    Overlap on top of a recursive splitter

    Recursive splitting has no natural overlap, so this adds it afterwards: each chunk is prefixed with the last characters of the one before, starting at a word boundary. The base chunks stay exactly what the splitter produced, which keeps the comparison clean. Install:

    The corpus and questions are shared with every RAG page here: IRS Publication 17 (2025), 80 frozen questions (30 + 50), and a chunk counts as relevant when it holds the question's whole evidence span. The load block also cuts 512-character chunks, which the measurement replaces.

    import hashlib, json, os, re, urllib.request
from pypdf import PdfReader

if not os.path.exists("p17.pdf"):
    urllib.request.urlretrieve("https://www.irs.gov/pub/irs-prior/p17--2025.pdf", "p17.pdf")
FURNITURE = re.compile(r"^(Userid:|AH XSL/XML Fileid|Page \d+ of \d+|The type and rule above).*$", re.M)

def clean(page):
    page = FURNITURE.sub("", page)                  # proof-sheet lines on every page
    page = re.sub(r"-[ \t]*\n(?=[a-z])", "", page)  # re-join words hyphenated at line ends
    page = re.sub(r"\s*\n\s*", " ", page)
    return re.sub(r" {2,}", " ", page).strip()

def split_keep(text, sep):
    if sep == "":
        return list(text)
    parts = text.split(sep)
    return [p + sep for p in parts[:-1]] + ([parts[-1]] if parts[-1] else [])

def recursive_split(text, size, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size:
        return [text]
    pieces = []
    for piece in split_keep(text, seps[0]):
        pieces += [piece] if len(piece) <= size else recursive_split(piece, size, seps[1:])
    chunks, buf = [], ""
    for p in pieces:                                # greedy packing, never over size
        if buf and len(buf) + len(p) > size:
            chunks.append(buf)
            buf = ""
        buf += p
    return chunks + [buf] if buf else chunks

text = "\n\n".join(clean(p.extract_text()) for p in PdfReader("p17.pdf").pages)
chunks = recursive_split(text, 512)
starts = [0]
for c in chunks[:-1]:
    starts.append(starts[-1] + len(c))

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json")
      for q in json.load(open(f))["questions"]]
gold = []                                           # chunks holding a whole evidence span
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    gold.append({j for j, s in enumerate(starts) if any(s <= a and b <= s + len(chunks[j]) for a, b in occ)})
print("sha256:", hashlib.sha256(open("p17.pdf", "rb").read()).hexdigest()[:16], "| chunks:", len(chunks),
      "| questions:", len(qs), "| with a relevant chunk:", sum(map(bool, gold)))

    def with_overlap(chunks, overlap):
    """Prefix every chunk after the first with up to `overlap` characters of the one before."""
    out, starts, pos = [], [], 0
    for i, c in enumerate(chunks):
        prefix = ""
        if i and overlap:
            tail = chunks[i - 1][-overlap:]
            cut = tail.find(" ")
            prefix = tail[cut + 1:] if cut != -1 else tail      # start at a word boundary
        out.append(prefix + c)
        starts.append(pos - len(prefix))
        pos += len(c)
    return out, starts

base = recursive_split(text, 256)
over, over_starts = with_overlap(base, 64)
print(len(base), "chunks; with 64 characters of overlap the average chunk grows from",
      round(sum(map(len, base)) / len(base)), "to", round(sum(map(len, over)) / len(over)), "characters")
print("chunk 1 starts:", repr(over[1][:60]))
print("chunk 0 ends:  ", repr(base[0][-60:]))
lengths = sorted(len(q["evidence"]) for q in qs)
print("evidence spans: shortest", lengths[0], "| median", lengths[len(lengths) // 2], "| longest", lengths[-1], "characters")

    Measured: four sizes, with and without overlap

    Setup. Recursive chunks of 128, 256, 512 and 1,024 characters, each with no overlap and with 25% overlap (32, 64, 128 and 256 characters). all-MiniLM-L6-v2 at a pinned revision and BM25 (rank-bm25 defaults). "Answerable" counts questions with at least one chunk holding the whole span, the ceiling for that setup. The budget column retrieves 2,048 ÷ size chunks (16, 8, 4 or 2) and reports the distinct characters they cover, since overlap repeats some.

    import math, time
import numpy as np
from sentence_transformers import SentenceTransformer
from rank_bm25 import BM25Okapi

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device="cpu",
                            revision="1110a243fdf4706b3f48f1d95db1a4f5529b4d41")
q_vecs = model.encode([q["question"] for q in qs], normalize_embeddings=True)
words = lambda s: re.findall(r"[a-z0-9]+", s.lower())
occ = [[m.span() for m in re.finditer(re.escape(q["evidence"]), text)] for q in qs]

def mcnemar(x, y):
    b = sum(p and not q for p, q in zip(x, y))
    c = sum(q and not p for p, q in zip(x, y))
    p = min(1.0, 2 * sum(math.comb(b + c, i) for i in range(min(b, c) + 1)) / 2 ** (b + c))
    return f"{b} vs {c}, p = {p:.3f}"

hits = {}
print("size  overlap  chunks  >256tok  answerable  dense@5  dense@budget (k, distinct chars)  bm25@budget")
for size in (128, 256, 512, 1024):
    base = recursive_split(text, size)
    for ov in (0, size // 4):
        t0 = time.time()
        ch, st = with_overlap(base, ov)
        rel = [{j for j, s in enumerate(st) if any(s <= a and b <= s + len(ch[j]) for a, b in o)} for o in occ]
        vecs = model.encode([c.strip() for c in ch], normalize_embeddings=True, batch_size=64)
        dense = np.argsort(-(q_vecs @ vecs.T), axis=1)
        bm25 = BM25Okapi([words(c) for c in ch])
        lex = [np.argsort(-bm25.get_scores(words(q["question"]))) for q in qs]
        k = 2048 // size
        found = lambda r, k: [bool(set(r[i][:k]) & rel[i]) for i in range(len(qs))]
        distinct = np.mean([len(set().union(*(range(st[j], st[j] + len(ch[j])) for j in dense[i][:k])))
                            for i in range(len(qs))])
        too_long = sum(len(model.tokenizer(c.strip())["input_ids"]) > model.max_seq_length for c in ch)
        hits[size, ov] = found(dense, k)
        print(f"{size:>4}  {ov:>7}  {len(ch):>6}  {too_long:>7}  {sum(map(bool, rel)):>10}  {sum(found(dense, 5)):>7}  "
              f"{sum(hits[size, ov]):>12} ({k:>2}, {distinct:,.0f})  {sum(found(lex, k)):>19}   {time.time() - t0:.0f} s")
print("\ndense@budget, 256 vs 1024:", mcnemar(hits[256, 0], hits[1024, 0]))
print("dense@budget, 256 vs 128:", mcnemar(hits[256, 0], hits[128, 0]))
for size in (128, 256, 512, 1024):
    print(f"dense@budget, {size} with vs without overlap:", mcnemar(hits[size, size // 4], hits[size, 0]))

    • Too small fails first. At 128 characters, only 57 of 80 questions have any chunk that holds the whole evidence span: the spans are longer than the chunks, or cut by a boundary. No retriever can recover that.
    • 256 was the best size for dense retrieval at this budget: 68 of 80 with eight chunks, against 52 for two 1,024-character chunks (20 questions gained, 4 lost, p = 0.002) and 44 for sixteen 128-character ones (28 vs 4, p < 0.001).
    • Overlap raised the ceiling but not recall. At 128 characters it made nine more questions answerable (57 to 66), because spans cut by a boundary became whole in the next chunk, yet recall moved by one (44 to 45, 8 vs 7). At every size the paired difference was within noise (p from 0.58 to 1.0), and at 256 the overlapped version was three lower.
    • BM25 was flatter: 54 to 60 for sizes from 256 to 1,024, and well behind dense retrieval at 256. Overlap gave it a few questions at 128 and 256 (39 to 44, 56 to 60), which this page did not test for significance.

    Limits: one document, one small embedding model (input limit 256 word pieces), 80 single-fact questions with evidence spans of at most about 130 characters. Questions that need several sentences, or a table, would push the best size up. The "whole span" rule favours small chunks less than a "half span" rule would; the chunking page explains why it was chosen.

    How to pick, in order

    StepWhat to checkHere
    1. Answer lengthThe span that must stay whole: a sentence, a paragraph, a table row. The chunk must be comfortably longer.Spans up to about 130 characters
    2. Model limitCount tokens with the embedding model's tokenizer; chunks over the limit are truncated.256 word pieces
    3. BudgetHow much text the generator should read; then k = budget ÷ size.2,048 characters
    4. Measure sizesTwo or three sizes on labelled questions, at that budget, with a paired test.128 to 1,024
    5. Overlap lastAdd 10 to 25% only if answers are being cut at boundaries (compare "answerable" with and without).0 or 25%

    Pitfalls

    • Comparing at equal k. At top 5, 1,024-character chunks look as good as small ones while sending four times the text. Compare at an equal budget (chunking page, and the dense@5 column above).
    • Counting overlap as free context. With 25% overlap, a budget of eight chunks covers fewer distinct characters; the distinct-characters column (above) shows how many. Deduplicate overlapping hits before building the prompt.
    • Chunks larger than the model reads. all-MiniLM-L6-v2 truncates past 256 word pieces (model card); the >256tok column counts the chunks that lose their ends.
    • Tuning size on the questions you report. Eight setups scored on the same 80 questions: the best one flatters itself. BrewSLM's Pub 17 sweep re-cut passages at 600 and 1,200 characters and saw 0.73 against 0.57 in answer quality, on the same questions it reported (IRS Pub 17 post).

    In BrewSLM: Data → Prepare cuts passages at sentence boundaries, at most 1,000 characters with up to 100 characters of overlap by default, and the documents → Q&A sweep re-cuts them at other sizes for retrieval.

    Practice

    1. Your answers are usually two sentences, about 300 characters. Is 256 a sensible chunk size?

    No. A 256-character chunk can't hold a 300-character answer whole, so the "answerable" ceiling drops, as it did at 128 here. Start above the answer length, say 512 to 768, check the token limit, and measure.

    2. With chunk size 512 and 25% overlap, how many chunks does a 952,548-character text produce, roughly?

    Overlap here is a prefix and doesn't change the number of base chunks, which is about 952,548 ÷ (average chunk length). With a sliding-window splitter the step is 384, so about 952,548 ÷ 384 ≈ 2,480 chunks, a third more than without overlap.

    3. Overlap raised "answerable" from 57 to 66 at 128 characters but recall moved by one question. Why might that be?

    Being answerable only means a chunk holding the span exists; the retriever still has to rank it. Overlapped chunks also compete with near-duplicates of themselves for the same slots, so some of the new ceiling goes unused.
