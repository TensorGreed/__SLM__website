    Embedding dimensions vs quality: how small can the vectors get?

    More dimensions let an embedding hold more distinctions, but quality usually falls slowly as you cut them, and storing each number in fewer bits costs even less: int8 keeps nearly all of it at a quarter of the memory. How far you can go depends on the model and the corpus, so measure retrieval at each size rather than trusting a model's headline dimension. On 80 questions about IRS Publication 17, all-MiniLM-L6-v2 at 384 float32 dimensions found 57 answers in its top 5; int8 also found 57, 48-byte binary vectors found 54, and PCA down to 128 dimensions found 54.

    Runs on: CPU, about two minutes for every block on the page once the models are downloaded Updated: 26 Nov 2026

    Tested on 26 Nov 2026 · Python 3.12.3 · sentence-transformers 3.3.1 · transformers 4.46.3 · torch 2.5.1 · scikit-learn 1.9.1 · pypdf 5.1.0 · numpy 2.1.3 · CPU (20-core Arm, no GPU)

    Where the bytes go

    An index holds one vector per chunk. At 384 float32 numbers that is 1,536 bytes a chunk, 1.5 GB for a million chunks; at 1,024 dimensions, 4 GB. Memory, disk and the time to compare a query against every vector all scale with it. There are two independent ways to shrink it:

    • Fewer dimensions. Keep the first d numbers (truncation), or project onto the d directions that vary most across your corpus (PCA). Matryoshka-trained (MRL) models are trained so that their first d numbers work on their own; ordinary models are not, so for them PCA should do better than truncation.
    • Fewer bits per dimension. int8 scalar quantization maps each dimension's range to 256 levels (4× smaller); binary keeps only the sign (32× smaller), compared by Hamming distance. A common pattern searches the binary index for candidates, then rescores them with full vectors.

    import hashlib, json, os, re, urllib.request
from pypdf import PdfReader

if not os.path.exists("p17.pdf"):
    urllib.request.urlretrieve("https://www.irs.gov/pub/irs-prior/p17--2025.pdf", "p17.pdf")
FURNITURE = re.compile(r"^(Userid:|AH XSL/XML Fileid|Page \d+ of \d+|The type and rule above).*$", re.M)

def clean(page):
    page = FURNITURE.sub("", page)                  # proof-sheet lines on every page
    page = re.sub(r"-[ \t]*\n(?=[a-z])", "", page)  # re-join words hyphenated at line ends
    page = re.sub(r"\s*\n\s*", " ", page)
    return re.sub(r" {2,}", " ", page).strip()

def split_keep(text, sep):
    if sep == "":
        return list(text)
    parts = text.split(sep)
    return [p + sep for p in parts[:-1]] + ([parts[-1]] if parts[-1] else [])

def recursive_split(text, size, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size:
        return [text]
    pieces = []
    for piece in split_keep(text, seps[0]):
        pieces += [piece] if len(piece) <= size else recursive_split(piece, size, seps[1:])
    chunks, buf = [], ""
    for p in pieces:                                # greedy packing, never over size
        if buf and len(buf) + len(p) > size:
            chunks.append(buf)
            buf = ""
        buf += p
    return chunks + [buf] if buf else chunks

text = "\n\n".join(clean(p.extract_text()) for p in PdfReader("p17.pdf").pages)
chunks = recursive_split(text, 512)
starts = [0]
for c in chunks[:-1]:
    starts.append(starts[-1] + len(c))

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json")
      for q in json.load(open(f))["questions"]]
gold = []                                           # chunks holding a whole evidence span
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    gold.append({j for j, s in enumerate(starts) if any(s <= a and b <= s + len(chunks[j]) for a, b in occ)})
print("sha256:", hashlib.sha256(open("p17.pdf", "rb").read()).hexdigest()[:16], "| chunks:", len(chunks),
      "| questions:", len(qs), "| with a relevant chunk:", sum(map(bool, gold)))

    import numpy as np
from sentence_transformers import SentenceTransformer
from sklearn.decomposition import PCA

docs, questions = [c.strip() for c in chunks], [q["question"] for q in qs]
mini = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device="cpu",
                           revision="1110a243fdf4706b3f48f1d95db1a4f5529b4d41")
mrl = SentenceTransformer("sentence-transformers/static-retrieval-mrl-en-v1", device="cpu",
                          revision="f60985c706f192d45d218078e49e5a8b6f15283a")
D1, Q1 = mini.encode(docs, batch_size=64, normalize_embeddings=True), mini.encode(questions, normalize_embeddings=True)
D2, Q2 = mrl.encode(docs, batch_size=64, normalize_embeddings=True), mrl.encode(questions, normalize_embeddings=True)
print("all-MiniLM-L6-v2:", D1.shape, "| static-retrieval-mrl-en-v1:", D2.shape)

unit = lambda X: X / np.linalg.norm(X, axis=1, keepdims=True)
def found(Q, D, score=lambda Q, D: Q @ D.T):
    top5 = np.argsort(-score(Q, D), axis=1)[:, :5]
    return sum(bool(set(top5[i]) & gold[i]) for i in range(len(qs)))

    Measured: cutting dimensions and bits

    Setup. The shared corpus: IRS Publication 17 (2025) in 2,170 chunks of up to 512 characters, 80 frozen questions (30 + 50), and a question counts as found when one of its top 5 chunks holds the whole evidence span. Two models at pinned revisions: all-MiniLM-L6-v2 (384 dimensions, not Matryoshka-trained) and static-retrieval-mrl-en-v1 (1,024 dimensions, Matryoshka-trained, a static model with no transformer, Apache-2.0). Truncated and PCA vectors are re-normalised. PCA is fitted on the chunk vectors. int8 uses each dimension's minimum and maximum over the corpus.

    print(f"{'dims':>6}{'MiniLM: first d':>17}{'MiniLM: PCA to d':>18}{'MRL model: first d':>20}")
for d in (1024, 512, 384, 256, 128, 64, 32):
    cells = []
    if d <= 384:
        cells.append(f"{found(unit(Q1[:, :d]), unit(D1[:, :d])):>14}/80")
        pca = PCA(n_components=d, random_state=0).fit(D1) if d < 384 else None
        cells.append(f"{found(unit(pca.transform(Q1)), unit(pca.transform(D1))) if pca else found(Q1, D1):>15}/80")
    else:
        cells += [f"{'':>17}", f"{'':>18}"]
    cells.append(f"{found(unit(Q2[:, :d]), unit(D2[:, :d])):>17}/80")
    print(f"{d:>6}" + "".join(cells))

# fewer bits per number, all 384 MiniLM dimensions
lo, hi = D1.min(axis=0), D1.max(axis=0)                       # per-dimension range, from the corpus
to_int8 = lambda X: np.clip(np.round((X - lo) / (hi - lo) * 255 - 128), -128, 127).astype(np.int8)
int8_score = lambda Q, D: Q @ D.astype(np.float32).T          # float query against int8 documents
bits = lambda X: np.packbits(X > 0, axis=1)
hamming = lambda Q, D: -np.unpackbits(bits(Q)[:, None, :] ^ bits(D)[None, :, :], axis=2).sum(2)
print(f"\n{'MiniLM, 384 dims':<22}{'bytes a vector':>15}{'found in top 5':>16}")
print(f"{'float32':<22}{384 * 4:>15}{found(Q1, D1):>13}/80")
print(f"{'int8 (scalar)':<22}{384:>15}{found(to_int8(Q1).astype(np.float32), to_int8(D1), int8_score):>13}/80")
print(f"{'binary (sign bits)':<22}{384 // 8:>15}{found(Q1, D1, hamming):>13}/80")
cand = np.argsort(hamming(Q1, D1), axis=1)[:, ::-1][:, :50]   # binary search for 50, then rescore in float32
rescored = [c[np.argsort(-(D1[c] @ Q1[i]))][:5] for i, c in enumerate(cand)]
print(f"{'binary, rescore top 50':<22}{384 // 8:>15}{sum(bool(set(r) & gold[i]) for i, r in enumerate(rescored)):>13}/80")

    • Dimensions fell off slowly, then fast. MiniLM truncated from 384 to 128 dimensions lost 7 of 57 found questions; at 32 it lost 24.
    • PCA beat truncation for the ordinary model at every size: 54 against 50 at 128 dimensions, 44 against 33 at 32. PCA keeps the directions that vary most across this corpus; truncation keeps whichever 128 came first.
    • The Matryoshka model didn't do better here. Its full 1,024 dimensions found 54, its 384 found 57 (the difference is noise at this size), and below 256 it fell as fast as truncated MiniLM. MRL makes truncation possible for a model; it doesn't make a smaller model better than a stronger one, and this static model trades quality for speed.
    • Bits were cheaper than dimensions. int8 lost nothing (57 at a quarter of the memory). Binary lost three questions at 1/32 of the memory, and rescoring its top 50 with the float vectors recovered two of them, though that needs the float vectors on disk.

    Limits: one corpus, 80 questions, and gaps of two or three questions here are within noise; only the large drops (32 dimensions, and truncation versus PCA at 32) stand out, and those were not tested for significance either. PCA fitted on the test corpus itself is a little optimistic.

    Pitfalls

    • Truncating a model that wasn't trained for it. Ordinary models spread information across all dimensions; at 32 dimensions truncation found 33 against PCA's 44 (table above). Matryoshka training is what makes the first d dimensions usable alone (Kusupati et al., 2022).
    • Forgetting to re-normalise. A truncated unit vector is no longer unit length, and dot-product scores then mix length into the ranking; divide by the norm again, as the code does (cosine, dot and L2).
    • Calibrating int8 on too little data. The per-dimension ranges come from the vectors you fit on; ranges from a small or unrepresentative sample clip later vectors. The sentence-transformers embedding quantization guide notes that the calibration set has a large influence on quality.
    • Trusting a benchmark's dimension curve. How much a model loses at 128 dimensions on a public benchmark is not what it loses on your documents; the MRL model here peaked at 384, not 1,024. Measure on your own queries, as on the choosing a model page.

    In BrewSLM: passage retrieval ranks with BM25 and an optional cross-encoder, not stored vectors, so there is no embedding index to shrink; see reranking.

    Practice

    1. You have 10 million chunks and 768-dimensional float32 vectors. How much memory, and what would int8 save?

    10,000,000 × 768 × 4 bytes ≈ 30.7 GB. int8 is a quarter of that, about 7.7 GB; binary would be about 0.96 GB.

    2. Why did PCA beat truncation for MiniLM but not by much at 256 dimensions?

    At 256 most of the information is still there either way (56 against 53 found). As d shrinks, choosing the directions with the most variance matters more, so the gap grows: 44 against 33 at 32 dimensions.

    3. Binary search then float rescoring recovered two questions. What does that design cost?

    You still keep the float vectors, on disk or in slower memory, and pay a second scoring step for the candidates. You save fast memory and search time, not total storage.
