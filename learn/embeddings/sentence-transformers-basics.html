    sentence-transformers basics: from install to a saved index

    sentence-transformers is an open-source Python library that loads an embedding model from the Hugging Face Hub and turns text into vectors with one call, model.encode(texts), then compares them with helpers such as util.semantic_search. The settings that matter most are the pinned model revision, normalize_embeddings, batch_size and max_seq_length, because text past that many word pieces is silently cut. On IRS Publication 17 cut into 1,024-character chunks, lowering all-MiniLM-L6-v2's limit from 256 to 128 word pieces dropped top-5 retrieval from 64 to 51 of 80 questions, since 33 of the answers start after word piece 128.

    Runs on: CPU, about three minutes for every block on the page once the model is downloaded Updated: 26 Nov 2026

    Tested on 26 Nov 2026 · Python 3.12.3 · sentence-transformers 3.3.1 · transformers 4.46.3 · torch 2.5.1 · pypdf 5.1.0 · numpy 2.1.3 · CPU (20-core Arm, no GPU)

    What the library does

    A sentence-transformers model is a short pipeline of modules: a transformer that turns word pieces into one vector each, a pooling layer that averages them into one vector for the text, and often a normalisation layer that scales it to length 1. The library downloads the model, runs that pipeline in batches on CPU or GPU, and adds the utilities around it: similarity functions, search over a matrix of vectors, and training code. It is open source (Apache-2.0) and is what most of the embedding models on the Hub are published for.

    This page covers the calls you need for a first index, then measures the setting people most often miss.

    Printing the model shows its modules: a BERT transformer that reads at most 256 word pieces, mean pooling into 384 numbers, and a Normalize() layer, so this model's vectors already have length 1 whether or not you ask. Other models differ (CLS pooling, no normalisation, a 512 limit), which is why printing the model is worth doing once. The corpus for the rest of the page is the one the RAG pages use: IRS Publication 17 (2025) and 80 frozen questions (30 + 50).

    import hashlib, json, os, re, urllib.request
from pypdf import PdfReader

if not os.path.exists("p17.pdf"):
    urllib.request.urlretrieve("https://www.irs.gov/pub/irs-prior/p17--2025.pdf", "p17.pdf")
FURNITURE = re.compile(r"^(Userid:|AH XSL/XML Fileid|Page \d+ of \d+|The type and rule above).*$", re.M)

def clean(page):
    page = FURNITURE.sub("", page)                  # proof-sheet lines on every page
    page = re.sub(r"-[ \t]*\n(?=[a-z])", "", page)  # re-join words hyphenated at line ends
    page = re.sub(r"\s*\n\s*", " ", page)
    return re.sub(r" {2,}", " ", page).strip()

def split_keep(text, sep):
    if sep == "":
        return list(text)
    parts = text.split(sep)
    return [p + sep for p in parts[:-1]] + ([parts[-1]] if parts[-1] else [])

def recursive_split(text, size, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size:
        return [text]
    pieces = []
    for piece in split_keep(text, seps[0]):
        pieces += [piece] if len(piece) <= size else recursive_split(piece, size, seps[1:])
    chunks, buf = [], ""
    for p in pieces:                                # greedy packing, never over size
        if buf and len(buf) + len(p) > size:
            chunks.append(buf)
            buf = ""
        buf += p
    return chunks + [buf] if buf else chunks

text = "\n\n".join(clean(p.extract_text()) for p in PdfReader("p17.pdf").pages)
chunks = recursive_split(text, 512)
starts = [0]
for c in chunks[:-1]:
    starts.append(starts[-1] + len(c))

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json")
      for q in json.load(open(f))["questions"]]
gold = []                                           # chunks holding a whole evidence span
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    gold.append({j for j, s in enumerate(starts) if any(s <= a and b <= s + len(chunks[j]) for a, b in occ)})
print("sha256:", hashlib.sha256(open("p17.pdf", "rb").read()).hexdigest()[:16], "| chunks:", len(chunks),
      "| questions:", len(qs), "| with a relevant chunk:", sum(map(bool, gold)))

    Output

    import time

docs = [c.strip() for c in chunks]
t0 = time.time()
index = model.encode(docs, batch_size=64, normalize_embeddings=True, convert_to_numpy=True)
print(f"encoded {len(docs)} chunks to {index.shape} {index.dtype} in {time.time() - t0:.1f} s")
np.save("index.npy", index)                                     # vectors: one row per chunk, same order as docs
reloaded = np.load("index.npy")
print("saved and reloaded:", reloaded.shape, "identical:", bool((reloaded == index).all()))

query = model.encode("Can I deduct travel to a stockholders' meeting?", normalize_embeddings=True)
hits = util.semantic_search(query, reloaded, top_k=3)[0]        # cosine similarity, best first
for h in hits:
    print(f"{h['score']:.3f}  chunk {h['corpus_id']}: {' '.join(docs[h['corpus_id']].split())[:90]}")

    Three things in that block. encode takes a list and batches it itself; batch_size changes speed and memory, not the vectors (up to floating-point noise). np.save is a perfectly good index for a few thousand chunks: the row number is the chunk id, so keep the chunks in the same order. And util.semantic_search scores by cosine and returns corpus_id and score per hit.

    Note what the search returned: three passages about what you can't deduct, none of them the sentence about stockholders' meetings that the what-is-an-embedding page matched easily. Against four short sentences the answer stood out; among 2,170 chunks of up to 512 characters, each about several things, it didn't make the top 3. That gap is what the reranking page addresses.

    Measured: what truncation at max_seq_length costs

    Setup. max_seq_length is the number of word pieces the model reads; anything after it is dropped before the transformer sees it, with no warning. To make the effect visible the corpus is cut into larger chunks, up to 1,024 characters (1,057 chunks), and encoded three times with the limit at 64, 128 and 256 (the model's default; its card says training inputs were cut at 128 tokens, so positions past 128 work but were less trained). A question counts as found when one of its top 5 chunks holds the whole evidence span.

    big = recursive_split(text, 1024)
big_starts = [0]
for c in big[:-1]:
    big_starts.append(big_starts[-1] + len(c))
big_gold = []
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    big_gold.append({j for j, s in enumerate(big_starts) if any(s <= a and b <= s + len(big[j]) for a, b in occ)})
n_tok = np.array([len(model.tokenizer(c.strip())["input_ids"]) for c in big])
print(f"{len(big)} chunks of up to 1,024 characters; word pieces per chunk: median {int(np.median(n_tok))},"
      f" over 128: {(n_tok > 128).mean():.0%}, over 256: {(n_tok > 256).mean():.0%}")

# where in its chunk does each answer start? (fraction of the chunk's word pieces before the evidence)
pos = []
for i, q in enumerate(qs):
    for j in big_gold[i]:
        k = big[j].find(q["evidence"])
        pos.append(len(model.tokenizer(big[j][:k].strip())["input_ids"]) - 2)
        break
pos = np.array(pos)
print(f"evidence starts after word piece: median {int(np.median(pos))}, after 128: {(pos > 128).sum()} of {len(pos)}")

q_vecs = model.encode([q["question"] for q in qs], normalize_embeddings=True)
print(f"\n{'max_seq_length':<16}{'found in top 5':>16}   encode time")
for L in (64, 128, 256):
    model.max_seq_length = L
    t0 = time.time()
    V = model.encode([c.strip() for c in big], batch_size=64, normalize_embeddings=True)
    secs = time.time() - t0
    top5 = np.argsort(-(q_vecs @ V.T), axis=1)[:, :5]
    found = sum(bool(set(top5[i]) & big_gold[i]) for i in range(len(qs)))
    print(f"{L:<16}{found:>13}/80   {secs:.0f} s")
model.max_seq_length = 256

    Output (times vary)

    1057 chunks of up to 1,024 characters; word pieces per chunk: median 214, over 128: 93%, over 256: 13%
evidence starts after word piece: median 93, after 128: 33 of 79

max_seq_length    found in top 5   encode time
64                         44/80   16 s
128                        51/80   28 s
256                        64/80   51 s
    • Most chunks were cut at 128. The median 1,024-character chunk is 214 word pieces; 93% are over 128 and 13% are over 256, so even the default loses the end of some.
    • Recall followed where the answers sit. Of the 79 answers that fit in a chunk, 33 start after word piece 128. At a limit of 128 the model never reads them, and top-5 recall fell from 64 to 51; at 64 it fell to 44.
    • Shorter limits are faster, roughly in proportion, which is the only reason to lower one on purpose.

    Limits: one model, one corpus, 80 questions, and no significance test on these gaps; the mechanism (answers past the cut) is the stronger evidence. With 512-character chunks, as on the other pages, few chunks reach 256 and the setting matters much less.

    Variations and parameters

    ArgumentWhat it doesUsed here
    revision=Pins the model files to one Hub commit, so the vectors don't change under you.A full commit hash
    device="cpu", "cuda" or "mps"; the default picks a GPU if there is one."cpu"
    normalize_embeddings=Scales vectors to length 1, so a dot product is the cosine.True
    batch_size=Texts per forward pass: speed and memory only.64
    max_seq_lengthWord pieces read per text; the rest is dropped. Raising it past the model's default is possible but untested.256 (64 and 128 measured)
    prompt= / prompt_name=Adds an instruction prefix for models that expect one (e5, bge queries).Not needed for MiniLM

    Pitfalls

    • Silent truncation. Text past max_seq_length is dropped with no warning; count word pieces with model.tokenizer as the measurement does. The sentence-transformers usage docs describe the limit.
    • Raising the limit past what the model supports. This model's default is 256 and it was trained on inputs cut at 128 tokens (model card); its position table stops at 512. Text read past the training length still helped here (256 beat 128), but quality there is less tested, so measure before relying on it.
    • Losing the row order. A saved matrix is only an index if row i is still chunk i. Save the chunk ids or texts next to it, and rebuild both together; the encode block relies on the list order.
    • Downloading on every run. Models are cached under HF_HOME; in containers, mount that cache or the first query of every deploy waits for a download (Hub cache guide).

    In BrewSLM: the dataset diagnostics and curriculum ordering load all-MiniLM-L6-v2 through sentence-transformers; the diagnostics fall back to hashed vectors when it isn't installed, while curriculum ordering refuses to run (clustering and dedup).

    Practice

    1. Your chunks are about 400 word pieces and the model's limit is 256. What are your options?

    Cut smaller chunks (the usual fix), pick a model trained on longer inputs (512 or more), or embed overlapping windows of each chunk and keep the best-scoring one. Raising max_seq_length to 512 runs, but the model was trained on 128-token inputs, so measure it before trusting it.

    2. Does batch_size change the embeddings?

    No, only speed and memory; results can differ in the last decimal places because padding and batched arithmetic run in a different order. Pick the largest batch that fits in memory.

    3. How would you check whether a model normalises its own output?

    Print the model and look for a Normalize() module, or encode a few texts without normalize_embeddings and check that every vector's length is 1.
