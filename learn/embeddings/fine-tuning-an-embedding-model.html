    Fine-tuning an embedding model: a small run on CPU

    Fine-tuning an embedding model means continuing its contrastive training on pairs from your own domain, so that your queries land nearer the passages that answer them; with a small model it runs on a CPU in minutes, and it needs no labels if you build pairs from the documents themselves. The catch is proving it helped: you need held-out labelled queries and a paired comparison, and the gain is often small. One epoch on 1,290 sentence-from-passage pairs from IRS Publication 17, about a minute on CPU, moved all-MiniLM-L6-v2 from 57 to 61 of 80 questions found in the top 5, a gain the paired test can't separate from noise (p = 0.29).

    Runs on: CPU, about ten minutes for every block on the page once the model is downloaded Updated: 26 Nov 2026

    Tested on 26 Nov 2026 · Python 3.12.3 · sentence-transformers 3.3.1 · transformers 4.46.3 · torch 2.5.1 · pypdf 5.1.0 · numpy 2.1.3 · CPU (20-core Arm, no GPU)

    Contrastive training in one paragraph

    Embedding models are trained on pairs that belong together: a query and the passage that answers it. A batch holds 32 such pairs. Every query is scored against all 32 passages, and a cross-entropy loss pushes its own passage's score above the other 31, which serve as negatives for free. This is the multiple-negatives ranking loss that most sentence-transformers models were trained with. Fine-tuning runs the same loss on pairs from your own domain, starting from a pretrained model, so it learns which texts your queries should land near.

    The hard part is the pairs. Labelled query-passage pairs are expensive; this page uses a label-free trick instead, the inverse cloze task (Lee et al., 2019): take one sentence out of a passage and train the model to find the rest of the passage from it. A sentence is a rough stand-in for a question about its passage, and every chunk of the corpus supplies one.

    import hashlib, json, os, re, urllib.request
from pypdf import PdfReader

if not os.path.exists("p17.pdf"):
    urllib.request.urlretrieve("https://www.irs.gov/pub/irs-prior/p17--2025.pdf", "p17.pdf")
FURNITURE = re.compile(r"^(Userid:|AH XSL/XML Fileid|Page \d+ of \d+|The type and rule above).*$", re.M)

def clean(page):
    page = FURNITURE.sub("", page)                  # proof-sheet lines on every page
    page = re.sub(r"-[ \t]*\n(?=[a-z])", "", page)  # re-join words hyphenated at line ends
    page = re.sub(r"\s*\n\s*", " ", page)
    return re.sub(r" {2,}", " ", page).strip()

def split_keep(text, sep):
    if sep == "":
        return list(text)
    parts = text.split(sep)
    return [p + sep for p in parts[:-1]] + ([parts[-1]] if parts[-1] else [])

def recursive_split(text, size, seps=("\n\n", "\n", ". ", " ", "")):
    if len(text) <= size:
        return [text]
    pieces = []
    for piece in split_keep(text, seps[0]):
        pieces += [piece] if len(piece) <= size else recursive_split(piece, size, seps[1:])
    chunks, buf = [], ""
    for p in pieces:                                # greedy packing, never over size
        if buf and len(buf) + len(p) > size:
            chunks.append(buf)
            buf = ""
        buf += p
    return chunks + [buf] if buf else chunks

text = "\n\n".join(clean(p.extract_text()) for p in PdfReader("p17.pdf").pages)
chunks = recursive_split(text, 512)
starts = [0]
for c in chunks[:-1]:
    starts.append(starts[-1] + len(c))

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json")
      for q in json.load(open(f))["questions"]]
gold = []                                           # chunks holding a whole evidence span
for q in qs:
    occ = [m.span() for m in re.finditer(re.escape(q["evidence"]), text)]
    gold.append({j for j, s in enumerate(starts) if any(s <= a and b <= s + len(chunks[j]) for a, b in occ)})
print("sha256:", hashlib.sha256(open("p17.pdf", "rb").read()).hexdigest()[:16], "| chunks:", len(chunks),
      "| questions:", len(qs), "| with a relevant chunk:", sum(map(bool, gold)))

    import random

held_out = set().union(*gold)                    # chunks that answer a test question: never trained on
def make_pairs(skip):
    pairs = []
    for j, c in enumerate(chunks):
        if j in skip:
            continue
        sents = [s for s in re.split(r"(?<=[.?!]) (?=[A-Z])", " ".join(c.split())) if len(s) >= 40]
        if len(sents) >= 3:
            k = random.Random(j).randrange(len(sents))         # one sentence is the "query" ...
            pairs.append((sents[k], " ".join(sents[:k] + sents[k + 1:])))   # ... the rest of its chunk the target
    return pairs

pairs = make_pairs(held_out)
print(len(held_out), "chunks held out;", len(pairs), "training pairs from the other", len(chunks) - len(held_out))
print("example query: ", pairs[7][0][:110])
print("example target:", pairs[7][1][:110], "...")

    The chunks that hold an evidence span for any of the 80 test questions are held out: no pair comes from them, so the model never trains on the text it will be asked to find. The other 2,090 chunks supply 1,290 pairs; chunks with fewer than three sentences of 40 characters or more, such as table rows, give none. The example shows the weakness of the trick: the "query" is a list of standard-deduction amounts, nothing like a question.

    The loop below is plain PyTorch around a sentence-transformers model: tokenize, run the model to get pooled embeddings, normalise, score every query against every passage in the batch, and apply cross-entropy with the diagonal as the right answers. One epoch, learning rate 2e-5, batch 32, inputs cut at 128 word pieces to keep it quick on a CPU.

    import math, time
import numpy as np
import torch
import torch.nn.functional as F
from sentence_transformers import SentenceTransformer

torch.manual_seed(0)
torch.set_num_threads(8)
REPO, REV = "sentence-transformers/all-MiniLM-L6-v2", "1110a243fdf4706b3f48f1d95db1a4f5529b4d41"

def embed(model, texts):                                        # differentiable forward pass
    features = model.tokenize(texts)
    return F.normalize(model(features)["sentence_embedding"], dim=-1)

def train(pairs, epochs=1, batch_size=32, lr=2e-5, scale=20.0):
    model = SentenceTransformer(REPO, device="cpu", revision=REV)
    model.max_seq_length = 128
    opt = torch.optim.AdamW(model.parameters(), lr=lr)
    model.train()
    order = list(range(len(pairs)))
    for epoch in range(epochs):
        random.Random(epoch).shuffle(order)
        for step in range(0, len(order) - batch_size + 1, batch_size):
            batch = [pairs[i] for i in order[step:step + batch_size]]
            q, d = embed(model, [a for a, _ in batch]), embed(model, [b for _, b in batch])
            # in-batch negatives: each query's target is its own passage, the other 31 are wrong answers
            loss = F.cross_entropy(scale * q @ d.T, torch.arange(len(batch)))
            opt.zero_grad()
            loss.backward()
            opt.step()
    model.eval()
    return model, loss.item()

def evaluate(model):
    model.max_seq_length = 256
    with torch.no_grad():
        D = model.encode([c.strip() for c in chunks], batch_size=64, normalize_embeddings=True)
        Q = model.encode([q["question"] for q in qs], normalize_embeddings=True)
    ranked = np.argsort(-(Q @ D.T), axis=1)
    found = [bool(set(ranked[i, :5]) & gold[i]) for i in range(len(qs))]
    rr = [next((1 / (r + 1) for r, j in enumerate(ranked[i, :100]) if j in gold[i]), 0.0) for i in range(len(qs))]
    return found, float(np.mean(rr))

def mcnemar(x, y):
    b = sum(p and not q for p, q in zip(x, y))
    c = sum(q and not p for p, q in zip(x, y))
    p = min(1.0, 2 * sum(math.comb(b + c, i) for i in range(min(b, c) + 1)) / 2 ** (b + c))
    return f"{b} vs {c}, p = {p:.3f}"

base_found, base_mrr = evaluate(SentenceTransformer(REPO, device="cpu", revision=REV))
t0 = time.time()
tuned, last_loss = train(pairs)
print(f"trained 1 epoch on {len(pairs)} pairs in {time.time() - t0:.0f} s; last batch loss {last_loss:.2f}")
tuned_found, tuned_mrr = evaluate(tuned)
print(f"\n{'':<34}{'found in top 5':>15}{'MRR':>8}")
print(f"{'base all-MiniLM-L6-v2':<34}{sum(base_found):>12}/80{base_mrr:>8.3f}")
print(f"{'fine-tuned, test chunks held out':<34}{sum(tuned_found):>12}/80{tuned_mrr:>8.3f}")
print("fine-tuned vs base:", mcnemar(tuned_found, base_found))

base all-MiniLM-L6-v2                       57/80   0.579

    One epoch over 1,290 pairs is 40 batches. The loss for a batch of 32 starts near ln 32 ≈ 3.5 when the model can't tell its own passage from the others; the last batch ended at 1.82.

    • A small gain, not a proven one. 57 to 61 found in the top 5, MRR 0.579 to 0.589: six questions gained and two lost, p = 0.29. At this size the honest reading is "it may help, a little".
    • The pairs are a stand-in. A sentence from a passage is not a user question; many are list items or figures, like the example. Questions generated per passage by a language model, or real queries with clicked results, make closer pairs.

    Measured: what if the test chunks are in the training data?

    The 80 chunks that hold a test answer were held out above. Here the same training runs with them included, so 62 more pairs come from exactly the passages the evaluation looks for. That is the usual way a fine-tuning result gets inflated without anyone meaning to.

    leaky_pairs = make_pairs(set())
leaky, _ = train(leaky_pairs)
leaky_found, leaky_mrr = evaluate(leaky)
print(f"{len(leaky_pairs)} pairs, including the {len(leaky_pairs) - len(pairs)} from chunks that answer test questions")
print(f"{'fine-tuned, test chunks included':<34}{sum(leaky_found):>12}/80{leaky_mrr:>8.3f}")
print("included vs held out:", mcnemar(leaky_found, tuned_found))

    Output (times vary)

    1352 pairs, including the 62 from chunks that answer test questions
fine-tuned, test chunks included            62/80   0.593
included vs held out: 3 vs 2, p = 1.000

    With the test chunks included the model found 62, one more than with them held out (3 gained, 2 lost, p = 1.0). The leak was small here because the pairs are sentence-to-passage rather than question-to-passage and the leaked pairs are under 5% of the data; with generated questions per passage, training on the test passages would teach the model the test directly. The rule doesn't depend on the size of the effect: decide what is held out before you build the training set.

    Limits: one run, one seed, one epoch, one learning rate, 80 test questions. A second seed could move the result by a question or two either way, which is the size of the gain.

    Pitfalls

    • Training on the passages you test on. Hold out every passage that answers an evaluation query before building pairs, as the pairs block does. Measured here the leak was small; with question-style pairs it would not be (comparison above).
    • Duplicate texts inside a batch. In-batch negatives assume every other passage is wrong; a repeated passage in the batch becomes a "negative" that is actually right. The sentence-transformers docs suggest a no-duplicates batch sampler (MultipleNegativesRankingLoss).
    • Calling a small gain a win. Four questions on 80 is p = 0.29 here. Report the paired test, or use the lift calculator.
    • Forgetting to re-embed. A fine-tuned model is a new model: every stored vector must be recomputed with it (mixing models).

    In BrewSLM: fine-tuning targets the language model, not the embedder; embeddings come from a stock all-MiniLM-L6-v2. The same held-out rule applies to its training data (data gates).

    Practice

    1. With a batch of 32 pairs, what loss would a model that can't tell the passages apart get?

    Each query's right passage gets probability 1/32, so the cross-entropy is ln 32 ≈ 3.47. A last-batch loss of 1.82 is a geometric-mean probability of about e−1.82 ≈ 16% for the right passage in that batch, far above chance.

    2. Your fine-tuned embedder finds 70 of 80 against the base model's 66. What do you check before shipping it?

    That no training pair came from the test passages, that the comparison is paired on the same queries (and what the test says), that a second seed gives a similar gain, and that general queries outside your test set didn't get worse.

    3. Why might a bigger off-the-shelf model be a better first step than fine-tuning?

    It costs nothing to train and no pairs to build. On this corpus, swapping MiniLM for bge-base-en-v1.5 gained 12 questions (choosing a model), three times what fine-tuning gained here.
