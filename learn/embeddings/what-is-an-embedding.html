    What is an embedding? Text as a vector of numbers

    A text embedding is a fixed-length list of numbers that a model produces for a piece of text, arranged so that texts with similar meaning get vectors pointing in similar directions. That turns "how alike are these two texts?" into arithmetic, usually cosine similarity, which is what semantic search, RAG retrieval, clustering and deduplication run on. On 80 questions about IRS Publication 17, a 23-million-parameter embedding model placed 71 of them nearest their own answer span out of all 80 spans, against 64 for word-count (TF-IDF) vectors, a gap too small at this size to call more than suggestive.

    Runs on: CPU, under a minute for every block on the page once the model is downloaded Updated: 26 Nov 2026

    Tested on 26 Nov 2026 · Python 3.12.3 · sentence-transformers 3.3.1 · transformers 4.46.3 · torch 2.5.1 · scikit-learn 1.9.1 · numpy 2.1.3 · CPU (20-core Arm, no GPU)

    From text to a point in space

    An embedding model reads a text and outputs a vector: 384 numbers for all-MiniLM-L6-v2, the model used here, 768 or 1,024 for larger ones. Inside, a transformer produces one vector per token, and a pooling step (usually the mean) turns those into one vector for the whole text. Sentence-embedding models are then trained on pairs of texts that belong together, such as a question and its answer or two paraphrases, so that pairs end up close and unrelated texts far apart.

    Three things follow.

    • Only directions and distances mean anything. Dimension 17 is not "the tax dimension". You compare vectors with each other, usually by the cosine of the angle between them.
    • Similarity is what the training said it is. A model trained on question-answer pairs puts a question near its answer; one trained on paraphrases puts paraphrases together. The two are not the same notion.
    • Vectors from different models don't mix. Each model has its own space; comparing a vector from one with a vector from another is meaningless.

    This is not the same as the token embeddings inside a language model, which map each token to a vector before the transformer runs. The Academy lesson on tokens and embeddings covers those.

    Embed four sentences

    Install:

    pip install torch==2.5.1 --index-url https://download.pytorch.org/whl/cpu
pip install sentence-transformers==3.3.1 transformers==4.46.3 tokenizers==0.20.3 \
    huggingface_hub==0.36.2 scikit-learn==1.9.1 numpy==2.1.3
    import numpy as np
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2", device="cpu",
                            revision="1110a243fdf4706b3f48f1d95db1a4f5529b4d41")
texts = ["Can I deduct my travel to a shareholders' meeting?",
         "You can't deduct expenses you pay to attend stockholders' meetings.",
         "Interest on U.S. savings bonds is exempt from state and local taxes.",
         "The cat slept on the warm windowsill."]
vecs = model.encode(texts, normalize_embeddings=True)
print("shape:", vecs.shape, "| first five numbers of text 0:", np.round(vecs[0, :5], 3))
print("length of each vector:", np.round(np.linalg.norm(vecs, axis=1), 3))
sims = vecs @ vecs.T                         # unit vectors: dot product = cosine similarity
for i, t in enumerate(texts):
    print(f"{t[:34]:<34}", " ".join(f"{s:5.2f}" for s in sims[i]))

    The question and the sentence that answers it share almost no words ("shareholders'" against "stockholders'", "travel" against "expenses"), yet they score 0.67, each other's nearest neighbour by far. The sentence about savings bonds scores 0.10 against the question, and the cat −0.11. The vectors all have length 1 because normalize_embeddings=True; the numbers themselves (−0.013, −0.032, 0.071, …) carry no meaning one by one.

    Measured: does each question land nearest its own answer?

    The 80 frozen questions the RAG pages use (30 + 50, drafted with an AI assistant from IRS Publication 17) each come with a short verbatim evidence span from the publication that answers them. Embed all 80 questions and all 80 spans, and ask: for each question, is its own span the closest of the 80? Chance is 1 in 80. The baseline is TF-IDF, a vector of word counts weighted by rarity, which can only match shared words.

    import json
from sklearn.feature_extraction.text import TfidfVectorizer

qs = [q for f in ("pub17-chunking-questions.json", "pub17-more-questions.json") for q in json.load(open(f))["questions"]]
questions, spans = [q["question"] for q in qs], [q["evidence"] for q in qs]

def report(name, sims):
    rank = (-sims).argsort(axis=1).argsort(axis=1)[np.arange(len(qs)), np.arange(len(qs))]   # 0 = own span first
    own, others = np.diag(sims), sims[~np.eye(len(qs), dtype=bool)]
    print(f"{name:<18} own span nearest: {int((rank == 0).sum()):>2}/80 | in top 5: {int((rank < 5).sum()):>2}/80"
          f" | mean similarity, own {own.mean():.2f} vs others {others.mean():.2f}")
    return rank == 0

dense = report("all-MiniLM-L6-v2", model.encode(questions, normalize_embeddings=True)
               @ model.encode(spans, normalize_embeddings=True).T)
tfidf = TfidfVectorizer().fit(questions + spans)
sparse = report("TF-IDF", (tfidf.transform(questions) @ tfidf.transform(spans).T).toarray())
print("nearest only with embeddings:", int((dense & ~sparse).sum()), "| only with TF-IDF:", int((sparse & ~dense).sum()))
i = int(np.flatnonzero(dense & ~sparse)[0])
print("example:", questions[i], "->", spans[i])

    Output

    all-MiniLM-L6-v2   own span nearest: 71/80 | in top 5: 77/80 | mean similarity, own 0.62 vs others 0.16
TF-IDF             own span nearest: 64/80 | in top 5: 74/80 | mean similarity, own 0.29 vs others 0.03
nearest only with embeddings: 11 | only with TF-IDF: 4
example: What numbers am I allowed to use for a Self-Select PIN when e-filing? -> A PIN is any combination of five digits you choose except five zeros
    • The embedding model put 71 of 80 questions nearest their own span (77 in its top 5), where chance would manage one. TF-IDF managed 64, which is a strong baseline here: the questions reuse many of the spans' words. Eleven questions were matched only by the embeddings and four only by TF-IDF; with an exact McNemar test that is p = 0.12, suggestive rather than settled. The example shows the kind of win: "Self-Select PIN" against "a PIN is any combination of five digits".
    • The similarity scale is compressed. A question and its own span averaged 0.62; a question and someone else's span still averaged 0.16, because everything in a tax guide is somewhat alike to a general-purpose model. Thresholds have to be set on your own data, not taken from another corpus.

    Limits: 80 short spans, all from one document, which is far easier than finding the span among a corpus of 2,170 chunks (the dense retrieval page does that). One small model; the questions were drafted with an AI assistant and paraphrase the spans on purpose.

    Pitfalls

    • Reading single dimensions. Individual coordinates have no stable meaning; only comparisons between vectors from the same model do (sentence-transformers docs on similarity).
    • Mixing models or revisions. Re-embedding half a corpus with a newer model leaves two incompatible halves, and nothing errors. Pin the revision, as the code does with the revision argument (SentenceTransformer API), and re-embed everything when you change it.
    • Long inputs are cut. This model reads 256 word pieces and drops the rest (model card), so a long document's vector describes its beginning.
    • Assuming a fixed threshold. "Above 0.8 means duplicate" depends on the model and the corpus; here non-matching question-span pairs averaged 0.16, not 0 (output above).

    In BrewSLM: all-MiniLM-L6-v2 embeddings drive the dataset diagnostics that flag near-duplicate training rows and order rows by difficulty; see clustering and dedup.

    Practice

    1. Two texts have embeddings with cosine similarity 0.62 under one model and 0.41 under another. Which pair is "more similar"?

    The question has no answer. Scores are only comparable within one model. Compare rankings inside each model, or look at where 0.62 and 0.41 fall among that model's scores for known similar and unrelated pairs.

    2. Why did the embedding model match questions TF-IDF missed?

    TF-IDF scores shared words only. The embedding model was trained on pairs with different wording, so "shareholders' meeting" and "stockholders' meetings", or "numbers allowed for a PIN" and "any combination of five digits", end up close even when few words are shared. TF-IDF still won four questions, where an exact rare word was the best clue.

    3. How many bytes does one 384-dimensional float32 embedding take?

    384 × 4 = 1,536 bytes. A million of them take about 1.5 GB.
