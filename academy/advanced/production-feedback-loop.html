    Production feedback loop: log → tag → augment → retrain

    After this lesson you can wire request/response logging at your endpoint with PII redaction and a sampling budget, tag bad rows (manually, from drift signals, from user feedback), convert tags into SFT examples, and retrain on a measured cadence — closing the loop that Lesson 4.9's regression and drift signals open.

    Level: advanced Read time: ~10 min Prerequisites: Observability & drift in production Verified: 13 Nov 2026

    Lesson 4.9 ended with a question: a regression alert or an input-drift signal tells you that something got worse — what do you do about it? If the cause is input drift, you retrain; a regression on the frozen answer key usually means a serving fix first. Retrain on what? That's the question this lesson answers. The "what" is production rows you collected, tagged, and curated. Without that data-collection loop, drift is a fire alarm with no water nearby.

    Drift detects; the loop supplies

    Lesson 4.9 separated two signals. BrewSLM's drift check re-runs your frozen gold set (the answer key under Data → Labels) against the deployed model, so it catches deployment regressions; it can't see new kinds of traffic, because those aren't in a set curated months ago. Input drift shows up only in what production actually receives — input monitoring and freshly labelled samples of recent traffic. Either way, the feedback loop's job is to make sure that, when you need to retrain, you have recent real inputs the model got wrong, with corrections, ready for the next training round.

    Two halves of one cycle

    Signals (Lesson 4.9) = the gold-set regression check, plus input monitoring and fresh labels on recent traffic. They catch the problem. Feedback loop (this lesson) = continuous logging + tagging + conversion of production rows into training examples. Supplies the cure. You need both — signals without the loop are alarms without action; the loop without signals is data piling up with no sign that it's needed.

    Step 1: log requests and responses

    A thin handler around your inference endpoint writes a record per request it decides to keep. Pydantic for the schema; the file write runs in a worker thread (asyncio.to_thread) so it doesn't block the event loop. BrewSLM doesn't host or log your production traffic — this is code you run at your own endpoint.

    import asyncio, secrets, time
from datetime import datetime, timezone
from typing import Optional
from pydantic import BaseModel
from fastapi import FastAPI, Request

class LogEntry(BaseModel):
    request_id: str
    ts: datetime
    model_version: str
    prompt: str
    response: str
    latency_ms: int
    user_id_hash: Optional[str] = None   # keyed hash, never raw
    response_logprob: Optional[float] = None
    tags: list[str] = []                  # filled in later by the tagger

app = FastAPI()
LOG_PATH = "data/inference.jsonl"

def write_log(entry: LogEntry) -> None:
    with open(LOG_PATH, "a") as f:
        f.write(entry.model_dump_json() + "\n")

@app.post("/chat")
async def chat(req: Request):
    body = await req.json()
    prompt = body["prompt"]
    ts = datetime.now(timezone.utc)
    t0 = time.perf_counter()
    response, logprob = generate(prompt)        # your model.generate(...) wrapper
    latency = int((time.perf_counter() - t0) * 1000)

    entry = LogEntry(
        request_id=secrets.token_hex(8),
        ts=ts,
        model_version="router-v6",              # match what's deployed
        prompt=redact_pii(prompt),              # see Step 2
        response=redact_pii(response),          # outputs echo PII too
        latency_ms=latency,
        user_id_hash=hash_user(body.get("user_id")),
        response_logprob=logprob,               # mean log-prob per output token
    )
    if should_log_full(entry):                  # the sampling budget, Step 2
        await asyncio.to_thread(write_log, entry)   # file write off the event loop
    return {"response": response, "request_id": entry.request_id}

    Step 2: privacy and cost

    Two things make naive "log everything" wrong in production:

    • Privacy. Inputs and outputs contain user data. Log raw strings and you've created a privacy liability. Redact PII at log time: emails, phone numbers, addresses, government IDs. Redact the model's response too — outputs echo PII all the time. Replace user identifiers with a keyed hash (HMAC with a secret): a plain hash of a short id can be reversed by hashing guesses. A keyed hash is still personal data (pseudonymised, not anonymous), so set a retention period and tell users what you log.
    • Cost. At 100 requests/second, raw logging is several GB/day of mostly-redundant text. Storage and search cost real money. Sample. Keep all the rows you'll actually use (low-confidence, flagged, post-drift); reservoir-sample the rest.
    import hashlib, hmac, os, random, re

_PII_PATTERNS = [
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "[EMAIL]"),
    (re.compile(r"\b\d{3}[-.\s]?\d{3}[-.\s]?\d{4}\b"), "[PHONE]"),
    (re.compile(r"\b\d{3}-\d{2}-\d{4}\b"), "[SSN]"),
]

def redact_pii(text: str) -> str:
    for pat, tag in _PII_PATTERNS:
        text = pat.sub(tag, text)
    return text

# Keyed hash (HMAC): without the secret key, nobody can recover an id by
# hashing guesses. Keep the key out of the logs and the repo.
_ID_KEY = os.environ["LOG_ID_HMAC_KEY"].encode()

def hash_user(uid: str | None) -> str | None:
    if not uid: return None
    return hmac.new(_ID_KEY, uid.encode(), hashlib.sha256).hexdigest()[:16]

# Sampling budget: log 100% of low-confidence/flagged, ~5% of healthy responses.
def should_log_full(entry: LogEntry) -> bool:
    if entry.response_logprob is not None and entry.response_logprob < -1.0:
        return True                              # uncertain — always log (tune the cut-off)
    return random.random() < 0.05                # 5% healthy sample

    Step 3: tag bad responses

    Tags are how you turn a stream of logs into a queue of training examples. Three sources:

    1. Manual: an operator reviews a queue of low-confidence rows + drift-period rows and tags them. Slow but high-quality.
    2. Auto-tag around an alert: every row in the hours before a regression or input-drift alert (Lesson 4.9) gets a "drift_window" tag automatically. These are not known failures — most may be fine. Treat them as a pool to sample for review, alongside sharper signals such as user negatives, low confidence or an out-of-distribution score.
    3. User feedback: thumbs-down, "regenerate," "report" buttons all map to a "user_negative" tag.

    Tags are opaque strings on the log entry. Anything you might later want to filter by becomes a tag.

    # Auto-tag the window before an alert (pass the alert time as a UTC-aware datetime)
import json
from datetime import timedelta

def tag_drift_window(drift_ts: datetime, window=timedelta(hours=12)) -> int:
    start = drift_ts - window
    out: list[dict] = []
    with open(LOG_PATH) as f:
        for line in f:
            entry = json.loads(line)
            if start <= datetime.fromisoformat(entry["ts"]) <= drift_ts:
                if "drift_window" not in entry["tags"]:
                    entry["tags"].append("drift_window")
            out.append(entry)
    with open(LOG_PATH, "w") as f:
        for e in out: f.write(json.dumps(e) + "\n")
    return sum(1 for e in out if "drift_window" in e["tags"])

    Step 4: convert tags into training examples

    This is where the loop closes. Filtered + tagged log rows become SFT pairs.

    from datasets import Dataset

def logs_to_sft(log_path: str, tags: set[str], gold_corrections: dict[str, str]) -> Dataset:
    """Pull tagged rows, replace the bad response with the corrected one.

    gold_corrections maps request_id -> the corrected completion an operator wrote.
    """
    rows = []
    with open(log_path) as f:
        for line in f:
            e = json.loads(line)
            if not (set(e["tags"]) & tags):  # only rows with at least one matching tag
                continue
            corrected = gold_corrections.get(e["request_id"])
            if not corrected:
                continue                             # untagged corrections are dropped
            rows.append({
                "messages": [
                    {"role": "user",      "content": e["prompt"]},
                    {"role": "assistant", "content": corrected},
                ]
            })
    return Dataset.from_list(rows)

    The corrected completion comes from the operator review (Step 3, source 1) or from a re-run of a stronger model whose output was verified. Either way, every example carries a correction the model should have produced, not just a flag of "this was wrong."

    Step 5: retrain cadence

    How often is the harder question. Three honest patterns:

    • On an input-drift signal. When input monitoring or fresh labels show the traffic has moved and you have at least N (say 100) tagged-and-corrected rows, retrain. (A gold-set regression alert usually means a serving fix, not a retrain — Lesson 4.9.) Skip retrain if you don't — collect more first; and when you retrain, mix the corrections with a replay of the original training set. Training on the new rows alone is what causes catastrophic forgetting (Lesson 1.22), whatever their number.
    • Cadenced. Weekly or monthly, whether drift fired or not. Cheap if your training pipeline is automated (Track 3); useful for slow-moving distributions that drift would never trip.
    • On capability gap. When a specific failure cluster (Track 3, Lesson 3.13; Results → Failures for eval misses, Ship → Monitor for run-log errors) crosses a count threshold, retrain on that cluster. The targeted version of augment_from_cluster in production.

    Don't ship a regression — re-run the eval suite

    Every retrain has to clear the same eval-pack gates the previous deploy cleared (Track 3, Lesson 3.13's required gates — the pass/fail rules on Results → Verdict in the BrewSLM UI). Otherwise you fix the new failures and reintroduce the old ones. The promotability decision is your safety net; treat it as such.

    Key idea

    Regression and drift signals (Lesson 4.9) catch the problem; the feedback loop supplies the cure. Log with PII redaction and a sampling budget, tag bad rows (manual / drift / user), convert tagged rows to SFT examples using operator corrections, and retrain on a measured cadence, mixing corrections with replay of the original data — every retrain re-clearing the eval-pack gates the previous deploy cleared.

    Key terms

    Production logging
    Recording request/response pairs at the inference endpoint into a queryable, append-only log (commonly JSONL).
    PII redaction
    Replacing personal identifiers in logged text with tokens like [EMAIL] before disk; hashing user ids.
    Sampling budget
    The rule that decides which rows get logged; full logging is too expensive at scale. Keep all interesting rows (low-confidence, flagged, drift-window), sample the rest.
    Tag
    An opaque string attached to a log entry that marks it as candidate training data (e.g. drift_window, user_negative, operator_review).
    Operator correction
    The corrected completion an operator (or stronger model) wrote for a tagged bad row; the source of the SFT example.
    Retrain cadence
    The trigger for when to retrain: on drift signal, on schedule, or on a failure-cluster count threshold.
