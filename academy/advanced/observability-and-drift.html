    Observability and drift in production

    After this lesson you can explain how the RunEvent spine makes a pipeline observable, tell input drift apart from a deployment regression, say what BrewSLM's drift check does and doesn't catch, and decide when a production model needs retraining.

    Level: advanced Read time: ~9 min Prerequisites: Serving and inference optimization Verified: 12 Nov 2026

    A deployed model meets inputs you never trained on, and the world it learned keeps moving. Observability is how you notice when it stops being good — before your users do.

    The RunEvent spine, recapped

    From Track 3: the instrumented stages (ingestion, training, eval, export, deployment and a few more; not every stage) emit a RunEvent via emit_event() — a severity (info / warning / error / critical) plus, for error and critical events, a reason code that is checked at runtime against a fixed taxonomy. Only some of the declared reason codes are actually emitted today (for example, deployment_drift_detected is declared but not emitted). One stream feeds the observability surfaces: the run-event timeline and failure clusters on Ship → Monitor, and the support bundle. The emission is best-effort (wrapped in try/except at each call site), so a bug in observability can never break the actual data or training path. That single design choice is what makes the whole pipeline debuggable after the fact.

    Drift: quality decays quietly

    A model that scored 0.93 on launch-day traffic can be at 0.80 on today's traffic six months later without anyone touching it — because the inputs drifted. New slang, new product names, a new kind of customer. This is input drift, and it's invisible unless you measure for it.

    Note what can't reveal it: re-scoring a frozen gold set on a frozen model. Same model, same rows — same score, whatever production inputs do. Detecting input drift takes two things:

    • Watching the input distribution — embedding or feature shift against your training data, the rate of out-of-distribution inputs, a change in the predicted-label mix.
    • Fresh labels — label a small sample of recent traffic regularly and score the model on it. That is the number that actually moves when the world does.

    BrewSLM's drift check: a deployment regression check

    BrewSLM's Ship → Deploy stage (Track 3) has a drift check on every served version. Despite the name, it is a deployment regression check: it exact-match-scores the same gold rows — the answer key under Data → Labels, the first 50 rows by default (up to 500 via the API) — against the deployed model and compares the pass rate with the baseline: the latest exact-match eval of the run behind the deployment. You supply the live model's predictions — bring your own inference client and paste them into the check's form (the API and CLI can also call an endpoint URL themselves, as a proof of concept) — and run it on whatever cadence you choose; nothing schedules it for you.

    It flags drift when |current − baseline| > tolerance, with a default tolerance of 0.05 in absolute pass rate. That rule is two-sided (an improvement also fires) and is a fixed threshold, not a significance test. Because the rows are frozen, a change means the deployed model now answers them differently: a wrong artifact, a quantized build, a different chat template or decoding settings, a provider change. That is exactly what it is good at catching.

    Read a small Δ with care. On the 50 rows the UI checks by default, 0.93 → 0.86 is a swing of three or four rows and can easily be noise. Because both runs score the same rows, compare them paired: count the rows that flipped each way and run McNemar's test on those two counts.

    Your gold set keeps working

    The gold set you curated for evaluation (the answer key) doesn't retire at launch — it becomes the regression sensor that catches a broken deployment for as long as you keep running the check. For input drift, pair it with input monitoring and freshly labelled samples; a frozen set can't see new traffic.

    When to retrain

    A signal tells you that something changed; deciding what to do is judgment:

    • Drift check flags a regression → check the serving side first: the deployed artifact, chat template, decoding settings and quantization. Same rows scoring differently is almost always a serving change, and the fix is a redeploy, not a retrain.
    • Input drift (from input monitoring, or a falling score on freshly labelled recent traffic) → gather recent real inputs, add them (via the review queue under Data → Generate → Details), re-split on Data → Split, re-train, re-evaluate against the same pass/fail rules on Results → Verdict. The Track 3 loop, triggered by a signal instead of a hunch.
    • New failure clusters (Ship → Monitor, or Results → Failures for eval misses) → a targeted data fix (augment_from_cluster), not a full retrain.
    • Stable → leave it alone. Retraining a healthy model just risks regressions.

    Key idea

    The RunEvent spine makes the pipeline observable; best-effort emission means observability never breaks the data path. BrewSLM's drift check re-runs your gold set (the answer key) against the deployed model — a deployment regression check that fires on |Δ| > 0.05 and points at the serving setup. Input drift needs input monitoring plus fresh labels on recent traffic; that is the signal to gather new data and retrain through the same pass/fail rules.

    Key terms

    observability
    The ability to see what the pipeline did and how the live model is performing.
    RunEvent spine
    The one event stream the instrumented stages emit to, feeding the monitoring surfaces; best-effort so it can't break the data path.
    drift
    Production quality decay caused by input distributions changing over time; detected by input monitoring plus fresh labels on recent traffic.
    drift check (deployment regression check)
    BrewSLM's exact-match re-run of the gold set (answer key) against the deployed model, compared with the training baseline; flags |Δ| above a tolerance (default 0.05). Catches serving regressions, not input drift. In BrewSLM: Ship → Deploy → Run drift check.
    support bundle
    A consumer of the RunEvent stream packaging the events/state needed to debug an issue.
    retrain trigger
    Using an input-drift signal or new failure clusters to decide when to gather data and retrain.
