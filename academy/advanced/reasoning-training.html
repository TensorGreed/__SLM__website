    Reasoning training: CoT SFT, process supervision, GRPO

    After this lesson you can distinguish the three things people mean by "reasoning training" (CoT SFT, process supervision via PRM, outcome supervision via ORM-style RL), build a CoT SFT dataset that trains on the trace plus the answer, choose between PRM and ORM for your data budget, recognise why GRPO is the practical RL recipe for SLM-scale reasoning (no value network, group-relative advantage), and avoid the most common honest-metrics failure — calling a model that learned to emit <think> tags a "reasoning" model without verifier-grounded eval.

    Level: advanced Read time: ~17 min Prerequisites: Preference tuning: DPO & ORPO Verified: 13 Nov 2026

    "Reasoning training" arrived as a single banner after the first reasoning-focused hosted models in late 2024, DeepSeek-R1 (DeepSeek-AI 2025, arXiv 2501.12948), and the wave of distilled reasoning SLMs that followed. The label covers at least three different techniques that get cited interchangeably — chain-of-thought SFT, process-supervised RL with a step-level reward model, and outcome-supervised RL with a verifier — and they don't optimise the same thing, don't need the same data, and don't fail in the same ways. For an SLM team, the difference between picking the right one and picking the wrong one is roughly the difference between a model that does multi-step work and a model that has learned to look like it does.

    The three techniques the label covers

    • Chain-of-thought SFT — supervised fine-tuning where each example is prompt → reasoning trace → final answer, and the loss covers both the trace and the answer. The simplest, the most data-efficient, and the right starting point unless you have very strong reasons to skip it.
    • Process supervision (PRM) — train a process reward model that scores each step of a reasoning trace, then use it as a reward signal to fine-tune the model with RL. Higher fidelity than outcome reward; far more expensive to collect data for (step-level labels from humans, as in PRM800K from Lightman et al. 2023, arXiv 2305.20050, or estimated from Monte Carlo rollouts, as in Math-Shepherd, Wang et al. 2024, arXiv 2312.08935).
    • Outcome supervision (ORM) + RL — only the final answer is rewarded (by a verifier: a math executor, a code runner, a unit test, a string-match). The model is trained with RL to produce traces that lead to verifier-passing answers. Cheaper data, harder optimisation, the recipe behind R1-style models. (Strictly, an ORM is a learned outcome reward model (Cobbe et al. 2021, arXiv 2110.14168); a rule-based checker is usually called a verifiable reward, as in RLVR. This lesson uses ORM loosely for both.)

    The three are layered, not exclusive: CoT SFT is usually the warm-start, and one of PRM/ORM follows. Skipping the SFT warm-start with cold RL is possible but quality is typically worse on small models.

    At small scale, distillation usually beats RL

    The most useful single result for an SLM team is in the DeepSeek-R1 paper's §4.1, "Distillation v.s. Reinforcement Learning". The authors ran large-scale RL (over 10K steps on math, code and STEM data) directly on Qwen-32B-Base, and separately fine-tuned the same base on reasoning traces generated by their large RL-trained model. The distilled model was better on every benchmark they report, for example 72.6 vs 47.0 pass@1 on AIME 2024. Their conclusion: distilling a stronger model into a smaller one works very well, while a small model relying on large-scale RL needs enormous compute and may still not match distillation.

    For an SLM that is usually the order of operations: CoT SFT on verified traces is the main lever, and RL is the polish, applied after SFT on tasks where a verifier exists and the model already passes some of the time (see zero-variance groups below). Two cautions. That result is for a 32B base, so read it as a strong prior for smaller models, not a measurement on them. And traces generated by another model carry that model's licence and terms of use: check them before you train on the traces or publish the result, and record which model and which version produced them.

    Chain-of-thought SFT, in detail

    The data shape is the lesson's most concrete artefact:

    # one example
ex = {
  "prompt": "Mira has 3 apples. She buys 4 more, eats 1, then gives half to her brother. How many does she have?",
  "trace":  "Start: 3 apples. Buy 4 → 3 + 4 = 7. Eat 1 → 7 - 1 = 6. Give half away → 6 / 2 = 3.",
  "answer": "3"
}

# render with the model's own chat template, not hand-typed role markers
messages = [
    {"role": "user",      "content": ex["prompt"]},
    {"role": "assistant", "content": f"<think>{ex['trace']}</think>{ex['answer']}"},
]
text = tok.apply_chat_template(messages, tokenize=False)

# <think> is plain text to many SLM tokenizers: check how it splits
print(tok.tokenize("<think>"))            # several pieces, not one token
# to make it one token, add it and grow the embeddings
#   tok.add_special_tokens({"additional_special_tokens": ["<think>", "</think>"]})
#   model.resize_token_embeddings(len(tok))
#   under LoRA, also train those rows: LoraConfig(..., modules_to_save=["embed_tokens", "lm_head"])

# loss mask: compute loss on the trace AND the answer (NOT the prompt — Lesson 1.3)
# TRL: split into prompt=[user turn], completion=[assistant turn] (Lesson 4.12)

    Three things this pattern gets right that hand-rolled versions usually get wrong:

    • The loss is on both the trace and the answer. Computing loss only on the answer teaches the model to skip the trace; computing it only on the trace lets it emit answers that don't follow from it.
    • The trace and the answer are wrapped with the same chat-template tokens (Lesson 1.4) the model already speaks, via apply_chat_template. Inventing new role markers that the tokenizer splits into multiple pieces silently degrades training; if you want <think> as one token, add it as a special token and resize the embeddings, as in the comments above.
    • The dataset is verifier-clean: every trace ends in the correct answer. Noisy traces (right answer, wrong arithmetic) teach the model to mimic the noise. Filter aggressively before training.

    Process supervision vs outcome supervision

    Two ways to score a reasoning trace once the model can produce one:

    • Outcome reward (ORM) — run a verifier on the final answer. Math problem? Execute the arithmetic. Code problem? Run the unit tests. Multiple-choice? String-match the letter. Reward = 1 if verifier passes, 0 otherwise (or graded). Cheap because the data is just (prompt, gold answer); the trace doesn't need labels.
    • Process reward (PRM) — train a separate model on step-level labels, human or rollout-estimated: "is this step correct given the steps before it?". Use the PRM to score every step of a candidate trace at training time. Higher fidelity (rewards correctness of reasoning, not just the answer) but the data is expensive — collecting step-level labels at scale was the most labour-intensive part of the early reasoning-model work.

    The practical reality at SLM scale: ORM is what most reproductions of the R1 recipe use, because outcome verifiers are cheap to write for math and code (the two domains where almost all public reasoning benchmarks live) and the data scales with no human labellers. PRM gives better local signal but the data cost dominates.

    GRPO: why it beats PPO for SLM-scale RL

    Proximal Policy Optimisation (PPO) is the canonical RL fine-tuning algorithm — it needs a policy network (the model you're training) and a value network (a critic that estimates expected reward). For SLM-scale reasoning, PPO has two problems: training a competent critic on noisy reasoning rewards is itself hard, and the critic is one more model to hold in memory with its weights, gradients and optimizer state (alongside the policy, the frozen reference and, often, a reward model).

    Group Relative Policy Optimisation (GRPO) — introduced in DeepSeekMath (Shao et al. 2024, arXiv 2402.03300) and used in DeepSeek-R1's public recipe — solves both by dropping the critic entirely. The advantage is computed group-relative:

    1. For each prompt, sample G completions from the current policy (e.g. G = 8).
    2. Score each completion with the verifier or PRM.
    3. Compute the advantage of each sample as (reward - group_mean) / group_std. No value network needed.
    4. Apply a PPO-style clipped policy-gradient update, with two differences: every token of a completion gets that completion's one advantage, and the KL penalty to the frozen reference, when there is one, is added to the loss rather than folded into the reward. Current recipes often drop it (β = 0), which also means no reference model in memory.

    The wins for an SLM team: no critic to train (one fewer model's weights, gradients and optimizer state), no critic instability to debug, and the group-relative normalisation handles reward scaling automatically — which matters because verifier rewards are usually 0/1 and would otherwise need careful baseline subtraction. The cost: G× the rollouts per step, which makes inference throughput the new bottleneck. vLLM-style rollouts are basically mandatory.

    # sketch of one GRPO step, after CoT SFT warm-start
G = 8                                              # group size
for prompt, gold in batch:
    completions = policy.sample(prompt, n=G, temperature=0.7)
    rewards = [verifier(c, gold) for c in completions]   # 0 or 1
    mean, std = stats(rewards)
    advantages = [(r - mean) / (std + 1e-6) for r in rewards]
    loss = grpo_loss(policy, ref_policy, prompt, completions, advantages,
                     kl_beta=0.0)    # DeepSeekMath used 0.04; TRL's GRPOConfig defaults to 0.0
    loss.backward(); optimiser.step()

    Known biases, and what current defaults do about them

    The 2024 formula has two built-in biases, both analysed in "Understanding R1-Zero-Like Training" (Liu et al. 2025, arXiv 2503.20783, the Dr. GRPO paper):

    • Length bias. The original loss averages each completion's token losses over its own length. A short correct answer then gets a bigger push per token than a long one, and a long wrong answer is penalised less per token than a short wrong one, so wrong answers drift longer during training. Dr. GRPO normalises by a constant instead; DAPO (Yu et al. 2025, arXiv 2503.14476) averages over all tokens in the batch.
    • Difficulty bias. Dividing by the group's standard deviation gives prompts with a small spread (nearly all right or nearly all wrong) a larger weight. Dr. GRPO drops the division.

    DAPO adds three more fixes: a higher upper clip ("clip-higher", εhigh = 0.28 with εlow = 0.2) so rare good tokens can grow, dynamic sampling that drops groups where every sample got the same reward and samples more prompts to fill the batch, and excluding or shaping truncated completions so a cut-off answer is not punished as wrong. TRL's GRPOConfig (1.17) has absorbed several of these as defaults. This instantiates on a CPU-only machine:

    import torch
from trl import GRPOConfig

use_bf16 = torch.cuda.is_available() and torch.cuda.is_bf16_supported(including_emulation=False)
args = GRPOConfig(
    output_dir="grpo-run",
    num_generations=8,                 # G, the group size (default 8)
    max_completion_length=512,
    learning_rate=1e-6,                # the default; RL steps are small
    beta=0.0,                          # the default: no KL term, no reference model loaded
    loss_type="dapo",                  # the default; "dr_grpo" and "grpo" are the alternatives
    scale_rewards="group",             # the default; "none" drops the std division (Dr. GRPO)
    epsilon=0.2, epsilon_high=0.28,    # DAPO's "clip-higher"; epsilon_high defaults to epsilon
    mask_truncated_completions=True,   # DAPO: truncated completions don't count in the loss
    bf16=use_bf16,                     # GRPOConfig defaults to bf16=True; off on CPU
    report_to=[],
)
print(args.beta, args.loss_type, args.scale_rewards, args.temperature)   # 0.0 dapo group 1.0

    Defaults move between TRL releases, so print them for the version you install, and put the values you rely on in your config explicitly.

    Zero-variance groups: why task difficulty decides whether RL learns

    The group-relative advantage has a blind spot. If all G samples for a prompt get the same reward, every advantage is zero and the prompt contributes no gradient at all:

    import statistics as st

def advantages(rewards, eps=1e-4):
    mean, std = st.fmean(rewards), st.pstdev(rewards)
    return [round((r - mean) / (std + eps), 2) for r in rewards]

print(advantages([0, 0, 0, 0, 0, 0, 0, 0]))   # all wrong: [0.0, ...] -> no gradient
print(advantages([1, 0, 0, 0, 0, 0, 0, 0]))   # one right: [2.64, -0.38, -0.38, ...]
for p in (0.05, 0.1, 0.5, 0.9):                # per-sample pass rate
    print(p, round((1 - p) ** 8 + p ** 8, 2))  # chance a group of 8 is all-same
# 0.05 0.66 | 0.1 0.43 | 0.5 0.01 | 0.9 0.43

    A small model that solves 5% of a task's prompts wastes about two thirds of its groups; at 10% it wastes over 40%, and the same happens on prompts it already solves 90% of the time. Before RL, measure the starting pass rate per prompt with G samples, and keep prompts the model gets right sometimes but not always (dynamic sampling does this filtering during training). If most prompts are all-wrong, the model is not ready for RL on that task: do more CoT SFT, or pick easier prompts first. TRL logs the share of zero-variance groups as frac_reward_zero_std; watch it the way you watch the loss.

    The math-and-code bias of public reasoning benchmarks

    Read any reasoning model card and the numbers are on GSM8K, MATH, HumanEval, MBPP, sometimes AIME. There's a reason: those are the domains with cheap automatic verifiers. The verifier writes itself for math (execute the arithmetic) and for code (run the tests); writing a verifier for "is this a good plan?" or "is this a correct legal analysis?" is the actual hard problem nobody has solved at scale. So reasoning models are trained where the verifiers are, and they're reported on benchmarks that ride the same rails.

    What this means for an SLM project:

    • If your task is math or code or anything with a clear binary verifier, reasoning training is a real lever — the R1-style recipe transfers.
    • If your task is open-ended reasoning (planning, summarisation, multi-step writing, legal analysis), the public benchmarks tell you almost nothing about what to expect on your task, and the recipes don't obviously apply because there's no verifier to plug in.
    • GSM8K and MATH contamination is now widely-documented (Lesson 2.17); the canonical-vs-paraphrased gap is the contamination tell. Treat the headline numbers with the same caution as any other public benchmark.

    The caveat — small-model "reasoning" is often format-following

    The most common way a small-model team declares "reasoning" success: training on R1-distilled traces, generating outputs that emit <think> tags and verbose multi-step prose, observing that the outputs "look like reasoning," and shipping. The model learned the format of a reasoning trace. Whether the trace is correct end-to-end — whether the arithmetic in step 2 is actually right — is a separate question that only verifier-grounded eval can answer. Reporting trace-emission rate as a reasoning metric is the new vanity number. Always run the math executor / code runner / step-level checker before quoting a reasoning gain.

    The minimum honest evaluation

    If you train a reasoning SLM, the report has three numbers, in this order:

    1. Verifier-pass rate on a held-out test set the model didn't see during training. Math executor, unit tests, string-match — whatever the task admits. This is the only number that measures the thing "reasoning training" is supposed to improve. Compare it with the pre-RL checkpoint on the same prompts, paired, before calling a few points a gain.
    2. General-capability drift on MMLU / HellaSwag / your task gold set (Lesson 2.17). RL on narrow reasoning data is a textbook recipe for catastrophic forgetting; if general-capability scores dropped 5 points, your "reasoning" gain is partly other-skill loss.
    3. Trace-format rate, reported separately from verifier-pass rate. The two together let a reader see whether you have format-following only (high trace rate, low verifier pass) or genuine reasoning (both high). One number hides the failure mode.

    Small test sets: is the difference real?

    Score both models on the same rows and look at the change row by row (a paired comparison), not just at the two headline numbers. On a small test set one answer moves the score a lot: one row in 20 is 5 points, one in 50 is 2.

    BrewSLM pairs the rows, counts how many got better, worse or stayed the same, and puts a 95% confidence interval (a paired t-interval) around the mean change. If the interval includes zero, the change is within noise: the data cannot tell a gain from a loss. Under 5 paired rows it gives no verdict.

    Worked example: 50 test rows
    Base model22 right (44%)
    Fine-tuned26 right (52%): +8 points
    Row by row6 better, 2 worse, 42 the same
    95% interval−3 to +19 points: within noise
    Visible gapabout 16 points at this size; about 500 rows to see a 5-point change

    Habits that keep a small test honest:

    • Compare like with like: same rows, same answer key, same scoring and decoding settings. BrewSLM's Compare gives no verdict when the answer key, judge or scoring differ.
    • Practice, then final: iterate against the practice answer key and score the final one rarely. A set you consult on every decision ends up fitted to your choices.
    • Small slices are noise: a per-class or per-entity score on a handful of rows swings on one row. Show the row count next to it.
    • Seeds: two or three training seeds show how much runs vary; with that few the interval is wide, so read the spread as a rough sign of the noise, not as a test.

    Further reading: Evan Miller, "Adding Error Bars to Evals" (arXiv 2411.00640).

    Key idea

    "Reasoning training" is three techniques, not one: CoT SFT (warm-start, train on trace + answer), process or outcome supervision (PRM vs ORM, depending on data budget), and at SLM scale GRPO as the practical RL recipe (no critic, group-relative advantage), used as polish after CoT SFT on verified traces, which is usually the bigger lever. Pick by data shape and verifier availability, not by what sounds rigorous. And separate verifier-pass rate from trace-format rate in the report — without that separation, "reasoning" on small models is mostly the model learning to emit a <think> tag.

    Key terms

    Reasoning training
    An umbrella term covering chain-of-thought SFT, process-supervised RL, and outcome-supervised RL — techniques aimed at producing multi-step traces that a verifier can score, not just final answers.
    Chain-of-thought SFT
    Supervised fine-tuning where each example is prompt → reasoning trace → final answer, with the loss covering both the trace and the answer. The standard warm-start before any RL-based reasoning step.
    Process supervision
    Scoring each step of a reasoning trace with a separately-trained reward model (the PRM). Higher fidelity than outcome reward; data is expensive because the labels are step-level, from human annotators or rollout estimates.
    Outcome supervision
    Scoring only the final answer with a verifier (math executor, code runner, string-match). Cheap data, harder optimisation; the recipe behind R1-style training.
    PRM (Process Reward Model)
    A reward model trained on step-level labels (human or rollout-estimated). Scores each step of a candidate trace, at RL training time or to rerank best-of-N samples at inference.
    ORM (Outcome Reward Model)
    Strictly, a learned model that scores final answers; used loosely here for any outcome-level reward, including a deterministic verifier (reward = 1 if it passes, 0 otherwise), which the literature calls a verifiable reward (RLVR).
    GRPO (Group Relative Policy Optimisation)
    RL fine-tuning algorithm used by DeepSeek-R1 and similar recipes. Drops PPO's value network; computes advantage group-relative across G samples per prompt (Shao et al. 2024, arXiv 2402.03300). The practical RL recipe at SLM scale, usually after CoT SFT.
    Dr. GRPO / DAPO
    2025 revisions of GRPO that remove its length bias (and, in Dr. GRPO, the std-normalisation difficulty bias); DAPO adds clip-higher, dynamic sampling and truncation handling. TRL's default loss_type is "dapo".
    Zero-variance group
    A group of G samples that all get the same reward; every advantage is zero, so the prompt gives no gradient. Common when a small model's pass rate on a task is near 0 or near 1.
    Verifier-grounded eval
    Evaluation that runs a deterministic checker (math executor, code runner, step checker) on the model's output. The only way to distinguish genuine reasoning from format-following.
    Trace-format rate
    Fraction of outputs that emit the expected reasoning-trace structure (<think> tags, multi-step prose). Must be reported separately from verifier-pass rate to expose format-following.
