    Public benchmarks & lm-evaluation-harness

    After this lesson you can use public benchmarks (MMLU, HellaSwag, ARC, GSM8K) as honest smoke checks against a checkpoint — not as the truth — run them with EleutherAI's lm-evaluation-harness, read few-shot vs zero-shot numbers correctly, recognise the contamination caveats that quietly inflate headline scores, and stop treating MMLU-65% as a project goal when your gold-set accuracy is the metric that actually pays the bills.

    Level: intermediate Read time: ~11 min Prerequisites: LLM-as-a-judge Updated: 13 Nov 2026

    Every SLM model card carries a constellation of benchmark names — MMLU, HellaSwag, ARC, GSM8K — followed by a percentage. They're convenient. They let you compare against the base, against the previous fine-tune, and against the wider model landscape with one number per axis. They are also widely misread: as the goal of fine-tuning rather than a smoke check, as a measure of your task quality rather than a sanity bar, and (worst) as ground truth in cases where the benchmark has leaked into pretraining. This lesson covers what each benchmark actually measures, how to run them, and how to read the numbers without being misled.

    What the standard benchmarks measure

    • MMLU (Massive Multitask Language Understanding) — multiple-choice questions across 57 subjects from elementary to professional. The closest thing to a general "what does this model know?" score. Usually reported 5-shot.
    • HellaSwag — pick the most plausible continuation of a short scenario from four options. Tests commonsense / world-model. Often reported 10-shot, but it is one of the least shot-sensitive benchmarks: the 175B model in Brown et al. 2020 (arXiv:2005.14165) scored 78.9 zero-shot vs 79.3 few-shot. State the shot count anyway.
    • ARC (Easy / Challenge) — grade-school science MCQs. ARC-Challenge filters for questions retrieval-based methods couldn't solve, making it harder.
    • GSM8K — grade-school math word problems requiring multi-step arithmetic reasoning. The shape that most predicts whether a chain-of-thought-style instruct model is doing real work.
    • TruthfulQA — questions designed to elicit common misconceptions; scores how often the model resists the wrong-but-popular answer.
    • WinoGrande — Winograd-style pronoun resolution; lightweight commonsense reasoning.

    None of these is your task. None of them measures the thing your fine-tune is supposed to do. They measure the substrate the fine-tune sits on top of.

    This is the 2023 "standard set" (the first Open LLM Leaderboard). Larger models saturated it, so the leaderboard's 2024 version moved to IFEval, BBH, MATH, GPQA, MuSR and MMLU-Pro, and MMLU itself has documented label errors (Gema et al. 2024, MMLU-Redux, arXiv:2406.04127). Pick by model size: a 135M model scores near the floor on GSM8K (SmolLM2-135M's model card reports 1.4 at 5-shot), so GSM8K can't detect a regression there. For models this small, use what their card reports: HellaSwag, ARC, PIQA, WinoGrande, MMLU in its cloze form.

    Few-shot vs zero-shot

    Almost every reported benchmark number has a shot count attached: MMLU 5-shot, HellaSwag 10-shot, GSM8K 8-shot CoT. The shot count is the number of labelled in-context examples prepended to the prompt before the question. On some tasks the difference between zero-shot and 5-shot is large, on others (HellaSwag) it is small; either way, reporting one and calling it the other is the most common honest-mistake in benchmark tables.

    Read the convention with the score:

    • Zero-shot tells you what the model knows without help. The honest measure of a base model's knowledge.
    • Few-shot tells you how well the model picks up a task from examples. The honest measure of in-context learning. Higher numbers, but they're measuring a different thing.
    • Instruct and base checkpoints can rank differently at different shot counts, and the direction varies by model and task. A common explanation is that instruct training favours templated single-turn answers over in-context learning, but treat that as a hypothesis to check, not a rule.

    lm-evaluation-harness, the standard tool

    EleutherAI's lm-evaluation-harness is the de-facto runner for these benchmarks. It supports hundreds of tasks under a unified evaluator, lets you point at a local Hugging Face checkpoint or a hosted endpoint, and reports per-task accuracy + standard error. It is a widely used runner for public model-card numbers.

    # install
pip install lm-eval

TASKS=hellaswag,arc_easy,arc_challenge,piqa,winogrande

# the base: the same Instruct checkpoint you fine-tuned from (Lesson 2.2)
lm-eval run \
  --model hf \
  --model_args pretrained=HuggingFaceTB/SmolLM2-135M-Instruct,dtype=bfloat16 \
  --tasks $TASKS \
  --batch_size 16 \
  --output_path eval/base

# your fine-tune: the same base plus your LoRA adapter
# (or pretrained=sft-out/merged for the merged model from Lesson 2.8)
lm-eval run \
  --model hf \
  --model_args pretrained=HuggingFaceTB/SmolLM2-135M-Instruct,peft=sft-out/adapter,dtype=bfloat16 \
  --tasks $TASKS \
  --batch_size 16 \
  --output_path eval/sft

    Three choices in those commands are deliberate. The base is the Instruct checkpoint, because that is what you fine-tuned; comparing against the raw pretrained model would mix your change with the model's own instruction tuning. There is no --num_fewshot, so every task runs at its own default (0-shot for these five); one --num_fewshot flag applies to every task in the list, so to match a published 10-shot HellaSwag number, run that task on its own with --num_fewshot 10. And both runs use the same prompt format. For chat-tuned checkpoints you can add --apply_chat_template (it turns on --fewshot_as_multiturn by default); if you do, add it to both runs. The older lm_eval --model … form without run still works.

    The output JSON has per-task accuracy and a standard error you should always report — a 0.4-point delta with a 0.6-point standard error is noise, not progress.

    How to read the numbers

    The four useful comparisons:

    1. Base vs SFT, same shot count — does SFT preserve substrate knowledge? A modest drop is normal (the fine-tune narrowed the model toward your task). A large drop on MMLU / HellaSwag is catastrophic forgetting; revisit Lesson 1.22's mitigations.
    2. Your fine-tune vs same-size peer models — places you in the landscape. Useful as a "do I have a competitive substrate?" check; not useful as a fine-tune goal.
    3. Across versions of your own fine-tune — for tracking regressions. If MMLU drops by 3 points between two runs, something changed in your data or recipe that you want to understand.
    4. Against the noise, not just the average — the stderr lm-eval reports is a per-model sampling error that assumes independent items; it is not the error of the difference between two models. Two runs on the same items need a paired comparison: compute a confidence interval on the per-item difference. As a rough guide, deltas under about 2–3× the reported SE can't be told apart from noise (Miller 2024, "Adding Error Bars to Evals", arXiv:2411.00640).

    Small test sets: is the difference real?

    Score both models on the same rows and look at the change row by row (a paired comparison), not just at the two headline numbers. On a small test set one answer moves the score a lot: one row in 20 is 5 points, one in 50 is 2.

    BrewSLM pairs the rows, counts how many got better, worse or stayed the same, and puts a 95% confidence interval (a paired t-interval) around the mean change. If the interval includes zero, the change is within noise: the data cannot tell a gain from a loss. Under 5 paired rows it gives no verdict.

    Worked example: 50 test rows
    Base model22 right (44%)
    Fine-tuned26 right (52%): +8 points
    Row by row6 better, 2 worse, 42 the same
    95% interval−3 to +19 points: within noise
    Visible gapabout 16 points at this size; about 500 rows to see a 5-point change

    Habits that keep a small test honest:

    • Compare like with like: same rows, same answer key, same scoring and decoding settings. BrewSLM's Compare gives no verdict when the answer key, judge or scoring differ.
    • Practice, then final: iterate against the practice answer key and score the final one rarely. A set you consult on every decision ends up fitted to your choices.
    • Small slices are noise: a per-class or per-entity score on a handful of rows swings on one row. Show the row count next to it.
    • Seeds: two or three training seeds show how much runs vary; with that few the interval is wide, so read the spread as a rough sign of the noise, not as a test.

    Further reading: Evan Miller, "Adding Error Bars to Evals" (arXiv 2411.00640).

    Why your gold set still matters more

    Three reasons the public benchmarks are insufficient on their own:

    • They measure substrate, not your task. A 5-point MMLU bump tells you nothing about whether your sentiment classifier is more accurate or your JSON extractor parses more reliably. Your task is your task.
    • They are multiple-choice or short-answer. Real outputs are free-form. MMLU accuracy correlates loosely with free-form helpfulness; LLM-as-a-judge (Lesson 2.16) and your gold set close the gap.
    • They're contaminated. Which brings us to —

    Contamination caveats

    Public benchmarks are widely scraped, widely indexed, and routinely end up in pretraining corpora. The fingerprint of a contaminated benchmark: the model gets the right answer on the canonical question but fails on lightly paraphrased versions of the same question. Several known contamination patterns:

    • MMLU has substantial overlap with publicly indexed test-bank questions; many model families have shown the canonical-vs-paraphrased gap.
    • HellaSwag contexts and ARC questions have appeared verbatim in pretraining web scrapes.
    • GSM8K — the original 8,500 problems have shown up in code repositories, blog posts, and instruction-tuning datasets. Re-renderings such as GSM-Hard (Gao et al. 2022) and GSM-Symbolic (Mirzadeh et al. 2024, arXiv:2410.05229), and the freshly written GSM1k (Zhang et al. 2024, arXiv:2405.00332), exist specifically to test whether a model learned the structure or memorised the corpus.

    Mitigations when you actually need a reliable number:

    • Run a paraphrased / re-rendered variant of the benchmark alongside the canonical one. A large canonical-paraphrased gap is the contamination tell.
    • Read the model card's contamination section if there is one. Many recent small-model reports publish decontamination or n-gram overlap checks.
    • Treat public benchmarks as relative, not absolute. Your fine-tune's delta vs your own base is harder to game than the absolute score.
    • Keep a small, private, never-published task gold set. That number is the one that matters. Private means less exposed to pretraining contamination, not immune: your own training rows can overlap the gold set (exact or near-duplicate), and a model that writes training data can copy examples from its prompt into it. Check train↔gold overlap before you trust the score.

    Honest beat — "MMLU 65%" is not a project goal

    It's a smoke check. The reason your stakeholder cares about the SLM is the task — whether the JSON parses, whether the extraction lands, whether the support reply was correct. Public-benchmark scores belong in the appendix of the model card, not the project's headline KPI. Build a gold set that measures the task; quote it; then report the substrate numbers as context.

    Key idea

    Public benchmarks are useful — for placing your model in the landscape, for catching catastrophic regressions during fine-tuning, for a shared vocabulary with the wider community. They are not useful as the truth, the project goal, or a substitute for a task-specific gold set. Run them with lm-evaluation-harness with the shot count published, compare against the checkpoint you actually fine-tuned, judge deltas against the noise of the difference, watch for the canonical-vs-paraphrased contamination signature, and remember that your private gold set is the one that the user pays for.

    Recap

    • Run benchmarks with lm-eval run at the task's default shot count, base and adapter under identical settings.
    • Judge a delta against the noise of the difference, ideally paired per item; a gap under about 2–3× the reported SE is not established.
    • Benchmarks catch broad regressions; your gold set measures your task; contamination limits what any public score means.

    Try it (5 minutes)

    lm-eval reports HellaSwag acc_norm 0.420 ± 0.005 for the base and 0.412 ± 0.005 for your adapter, on the same items. Did fine-tuning hurt general ability?

    Show answer

    Not established. The drop is 0.008, about 1.6× the reported SE of each score, which is under the 2–3× rough guide. Both runs used the same items, so the right test is paired: rerun with --log_samples (it needs --output_path), take the per-item differences and put a confidence interval on their mean. If that interval excludes zero, it's a real but small regression; if not, call it within noise and keep watching it on later runs.

    Key terms

    lm-evaluation-harness
    EleutherAI's open-source benchmark runner — a widely used tool for the MMLU / HellaSwag / ARC / GSM8K numbers in model cards.
    MMLU
    Massive Multitask Language Understanding: ~14k multiple-choice questions across 57 subjects. Usually reported 5-shot. The standard substrate-knowledge benchmark.
    HellaSwag
    Commonsense scenario-continuation MCQs; often reported 10-shot, though it changes little with shot count. Tests world-model plausibility.
    ARC
    AI2 Reasoning Challenge: grade-school science MCQs in Easy / Challenge splits.
    GSM8K
    Grade-school math word problems requiring multi-step arithmetic; the standard chain-of-thought benchmark.
    Few-shot vs zero-shot
    Few-shot prepends N labelled examples to the prompt; zero-shot prepends none. Different shot counts can produce very different scores on some tasks; the shot count must be reported with the number.
    Standard error (lm-eval)
    The per-model sampling error lm-evaluation-harness reports alongside accuracy, assuming independent items. To compare two models, use a paired interval on the difference; deltas under ~2–3× the reported SE are not distinguishable from noise.
    Benchmark contamination
    The benchmark's questions or answers appeared in the model's pretraining corpus; the model memorised rather than reasoned. The tell is a large gap between canonical and paraphrased versions of the same question.
    Substrate vs task
    Public benchmarks measure the substrate of general capability the fine-tune sits on; your gold set measures the task itself. Both matter, in that order.
