    Recipes and task handlers: the training config without the code

    After this lesson you can read a TrainingConfig as the declarative form of your Track 2 TrainingArguments + LoraConfig, tell BrewSLM's three kinds of "recipe" apart, and explain how the evaluation dispatcher picks the task handler that scores outputs.

    Level: intermediate Read time: ~10 min Prerequisites: Clean and prepare: the manifest is the source of truth

    In lesson 2.5 you wrote a LoraConfig and a TrainingArguments in Python. In BrewSLM that information lives in one declarative object, TrainingConfig — the same knobs you learned, without the boilerplate.

    TrainingConfig is your TrainingArguments, declared

    An excerpt of TrainingConfig (backend/app/schemas/training.py), with the field names as in the schema and the schema's defaults. base_model is required; the value shown is just an example.

    # TrainingConfig: field = default
base_model: HuggingFaceTB/SmolLM2-135M-Instruct   # required
training_mode: sft
task_type: causal_lm
use_lora: true
lora_r: 16
lora_alpha: 32
lora_dropout: 0.05
target_modules: auto        # all linear layers for causal LMs up to 2B params,
                            # q_proj + v_proj above that
learning_rate: 2.0e-4
optimizer: paged_adamw_8bit
lr_scheduler: cosine
warmup_ratio: 0.03
num_epochs: 3               # ignored while auto_epochs is on
auto_epochs: true           # sizes epochs to ~200 optimizer steps (on small data
                            # it shrinks gradient accumulation first)
batch_size: 4
gradient_accumulation_steps: 4   # effective batch 16 (before auto_epochs)
max_seq_length: 2048
bf16: true
gradient_checkpointing: auto
save_steps: 100             # a checkpoint every 100 optimizer steps

    Every field here is a concept you already own from Track 1 and built in Track 2: rank and alpha, target modules, the cosine schedule with warmup, effective batch size, bf16. Three defaults differ from a hand-written script: target_modules: auto picks the modules from the model's size, auto_epochs overrides num_epochs, and checkpoints are per step, not per epoch. TrainingConfig makes all of this one object instead of inline arguments, and a training preset is a named patch over it, so you can apply the same preset across projects or A/B two presets on the same data.

    Three things called "recipe"

    The word "recipe" means three different things in BrewSLM. Only one of them touches hyperparameters, and none of them is a hyperparameter file of its own:

    KindExamplesWhat it carriesWhere in the UI
    Task-shape recipe (services/recipe_service.py)qa-sft, classification, span-extraction, json-extraction, generic-sft, …The task shape: task profile, split adapter, scoring mode, default eval pack and a suggested base model. No hyperparameters of its own.Train → More options → Task type
    Training recipe (services/training_recipe_service.py)recipe.sft.safe, recipe.sft.balanced, recipe.lora.fast, recipe.distill.logits, …A patch applied to a TrainingConfigTrain → More options → Training presets
    Pipeline recipe (services/pipeline_recipe_service.py)recipe.pipeline.sft_default, recipe.pipeline.lora_fast, …An end-to-end composition that names a training recipe plus the steps around itTrain → More options → Pipeline presets

    In the workspace the config is behind the Train form: the task shape is the read-only Task line (its Change link opens Train → More options → Task type), the knobs above live under More options → Model and hyperparameters and LoRA and advanced training, named patches under More options → Training presets, and whole-pipeline presets under More options → Pipeline presets (/project/<id>/train?open=pipeline-presets).

    From Track 2

    TrainingConfig ↔ TrainingArguments + LoraConfig. save_steps ↔ save_steps (with save_strategy="steps"). There's nothing in it you didn't already set by hand — which is the whole point of having done it by hand first.

    The task-handler dispatcher

    Here's where the platform does more than your script did. At evaluation time, the manifest's task_profile routes to a task handler. Handlers are evaluation-only: a handler builds the eval prompts (build_prompts()) and scores each output (score()). Tokenization and the -100 loss mask are not the handler's job; they live in the trainer (backend/scripts/train.py). The dispatcher routes to one of a general set, and falls back to GenericHandler for a profile it doesn't know:

    ClassificationHandler        QAHandler
StructuredExtractionHandler  (six scoring modes: field_match, span_set,
                              finding_set, remediation, structured_plan,
                              multi_option)
RAGHandler                   AlignmentHandler
Seq2SeqHandler               VisionLanguageHandler
AudioTranscriptHandler       SafetyHandler
ToolCallHandler              GenericHandler (fallback)

    Our sentiment task routes to the ClassificationHandler. Notice the design: handlers are named after task shapes (classification, extraction, alignment), never after one narrow domain. A new use case is "which existing shape is this, and what scoring mode?" — not "write a new handler." That generality is why the same eleven stages serve wildly different projects.

    You set the config; the trainer and the handler do the rest

    So the division of labor is: TrainingConfig carries the hyperparameters you tuned by hand, the trainer does the tokenization and masking you wrote by hand, and the task handler, picked from the manifest's task profile, builds the eval prompts and scores the outputs. You pick a training preset or edit the config (or accept the default the Autopilot Planner proposes, under Settings → Tools) and the platform assembles a runnable train plan. Before it spends a GPU-hour on that plan, though, it runs preflight — the readiness line on the Train form and the Checks section under More options — the next lesson.

    Key idea

    TrainingConfig is your TrainingArguments + LoraConfig as declarative config, with training presets as named patches over it; the trainer runs your tokenize/mask code; a task handler is your eval-and-score code, picked by task shape. Together they reproduce your by-hand training and evaluation — declaratively, and general across task types.

    Key terms

    TrainingConfig
    The declarative training config (backend/app/schemas/training.py): base model, training mode, LoRA knobs, optimizer/schedule, batch, precision, save_steps.
    recipe
    Three different things: a task-shape recipe (the UI's Task type, no hyperparameters), a training recipe (a Training preset, a patch over TrainingConfig), or a pipeline recipe (a Pipeline preset).
    task-handler dispatcher
    Routes the manifest's task_profile to the evaluation handler for that task, with GenericHandler as the fallback.
    task handler
    A general, task-shape-named evaluation component (Classification, QA, StructuredExtraction, RAG, ToolCall, …) implementing build_prompts() and score().
    save_steps
    How often checkpoints are written during training, in optimizer steps (default 100).
