    Recipes and task handlers: the training config without the code

    After this lesson you can read a TrainingConfig as the declarative form of your Track 2 TrainingArguments + LoraConfig, tell BrewSLM's three kinds of "recipe" apart, and explain how the evaluation dispatcher picks the task handler that scores outputs.

    Level: intermediate Read time: ~13 min Prerequisites: Clean and prepare: the manifest is the source of truth Verified: 13 Nov 2026

    In lesson 2.5 you wrote a LoraConfig and a TrainingArguments in Python. In BrewSLM that information lives in one declarative object, TrainingConfig — the same knobs you learned, without the boilerplate.

    TrainingConfig is your TrainingArguments, declared

    An excerpt of TrainingConfig (backend/app/schemas/training.py), with the field names as in the schema and the schema's defaults. base_model is required; the value shown is just an example.

    # TrainingConfig: field = default
base_model: HuggingFaceTB/SmolLM2-135M-Instruct   # required
training_mode: sft
task_type: causal_lm
use_lora: true
lora_r: 16
lora_alpha: 32
lora_dropout: 0.05
target_modules: auto        # all linear layers for causal LMs up to 2B params,
                            # q_proj + v_proj above that
learning_rate: 2.0e-4
optimizer: paged_adamw_8bit
lr_scheduler: cosine
warmup_ratio: 0.03
num_epochs: 3               # ignored while auto_epochs is on
auto_epochs: true           # sizes epochs to ~200 optimizer steps (on small data
                            # it shrinks gradient accumulation first)
batch_size: 4
gradient_accumulation_steps: 4   # effective batch 16 (before auto_epochs)
max_seq_length: 2048
bf16: true
gradient_checkpointing: auto
save_steps: 100             # a checkpoint every 100 optimizer steps

    Every field here is a concept you already own from Track 1 and built in Track 2: rank and alpha, target modules, the cosine schedule with warmup, effective batch size, bf16. Three defaults differ from a hand-written script: target_modules: auto picks the modules from the model's size, auto_epochs overrides num_epochs, and checkpoints are per step, not per epoch. TrainingConfig makes all of this one object instead of inline arguments, and a training preset is a named patch over it, so you can apply the same preset across projects or A/B two presets on the same data.

    The three "auto" defaults

    These are the defaults you actually get, and each one is resolved at run time from your model and data, then written to the run's report (runtime_environment) so you can see what it chose:

    • auto_epochs: true (services/training_epoch_policy.py) aims for about 200 optimizer steps. On small data it first shrinks gradient accumulation (more, smaller updates beat re-reading the same rows), then adds epochs up to a ceiling: 4 epochs under 100 rows, 8 under 1,000, 3 above. For example, 1,606 training rows at batch 4 × accumulation 4 is 101 steps an epoch, so it runs 2 epochs (202 steps); 108 rows drops accumulation to 1 and runs 8 epochs of 27 steps (216). num_epochs is ignored while it is on. A request that sets num_epochs without saying anything about auto_epochs turns it off, so the count you typed is the count you get.
    • target_modules: auto (services/lora_target_policy.py) means every linear layer (attention and MLP, all-linear) for causal LMs up to 2B parameters, and the classic q_proj + v_proj above that or for other task types (using the model's own names for its query/value layers, so encoders work too). q/v alone under-fit SmolLM2-135M and Qwen2.5-1.5B in BrewSLM's measurements; all-linear costs about 1.6× the training time and a bigger adapter. An explicit list, or "all-linear", is never overridden.
    • gradient_checkpointing: auto (services/gradient_checkpointing_policy.py) is off for models up to 2B parameters, where activation memory is small and recomputing it only costs time, and on above that. It is also on, whatever the model size, when the longest tokenized training row is over 1,024 tokens (long passage prompts). An explicit true / false is honoured.

    Three things called "recipe"

    The word "recipe" means three different things in BrewSLM. Only one of them touches hyperparameters, and none of them is a hyperparameter file of its own:

    KindExamplesWhat it carriesWhere in the UI
    Task-shape recipe (services/recipe_service.py)qa-sft, classification, span-extraction, json-extraction, generic-sft, …The task shape: task profile, split adapter, scoring mode, default eval pack and a suggested base model. No hyperparameters of its own.Train → More options → Task type
    Training recipe (services/training_recipe_service.py)recipe.sft.safe, recipe.sft.balanced, recipe.lora.fast, recipe.distill.logits, …A patch applied to a TrainingConfigTrain → More options → Training presets
    Pipeline recipe (services/pipeline_recipe_service.py)recipe.pipeline.sft_default, recipe.pipeline.lora_fast, …An end-to-end composition that names a training recipe plus the steps around itTrain → More options → Pipeline presets

    In the workspace the config is behind the Train form: the task shape is the read-only Task line (its Change link opens Train → More options → Task type), the knobs above live under More options → Model and hyperparameters and LoRA and advanced training, named patches under More options → Training presets, and whole-pipeline presets under More options → Pipeline presets (/project/<id>/train?open=pipeline-presets).

    The task-handler dispatcher

    Here's where the platform does more than your script did. At evaluation time, the manifest's task_profile routes to a task handler. Handlers are evaluation-only: a handler builds the eval prompts (build_prompts()) and scores each output (score()). Tokenization and the -100 loss mask are not the handler's job; they live in the trainer (backend/scripts/train.py). The dispatcher routes to one of a general set, and falls back to GenericHandler for a profile it doesn't know:

    HandlerTask profile(s) it servesMetrics it produces
    ClassificationHandlerclassificationaccuracy, macro_f1, per-class precision / recall / F1, a confusion matrix (up to 20 labels), unparseable_rate; plus exact_match / f1 aliases
    QAHandlerqa, instruction_sft, chat_sft, language_modelingexact_match and f1 on the extracted answer span (after "Answer:", "Therefore:" and similar markers), answer_span_extracted_rate
    StructuredExtractionHandlerstructured_extraction, extractionDepends on the scoring mode in the manifest's output_schema: field_match (default): json_validity_rate, schema_compliance_rate, per-field exact match and F1; span_set: precision / recall / F1 over typed spans; finding_set: findings matched on label and line range, precision / recall / F1; remediation: remediation_pass_rate, patch_applies_rate; structured_plan: structured_plan_pass_rate, schema_valid_rate, field_match_rate
    RAGHandlerrag_qa, rag, grounded_qaexact_match / f1 against the gold answer, faithfulness (is the answer in the retrieved context), context recall (is the gold answer in it); plain EM/F1 when rows have no context
    AlignmentHandlerdpo, orpo, alignment, preferencepreference_accuracy (output closer to chosen than rejected), mean_alignment_margin
    Seq2SeqHandlerseq2seqBy sub-task: translation BLEU + chrF, summarization (default) ROUGE-1/2/L, paraphrase BLEU + ROUGE; length_ratio; EM/F1 aliases
    VisionLanguageHandlervision_language, image_captioning, vqacaptioning: BLEU-4, ROUGE-L, length_ratio; VQA: EM/F1
    AudioTranscriptHandleraudio_transcript, audio_transcription, speech_to_texttranscription: WER, CER; audio QA: EM/F1
    SafetyHandlersafety, refusalpass_rate (did it refuse) plus a pass rate per test type (prompt injection, jailbreak, …)
    ToolCallHandlertool_callingtool_selection_accuracy, tool_args_match_rate, tool_call_pass_rate (both right)
    GenericHandleranything else (fallback)the plain exact_match / f1 scoring

    Source: the register_handler(...) calls and handler classes in backend/app/services/eval_task_handler_service.py. When the manifest has no task profile, the run's own task type is used instead.

    Our sentiment task routes to the ClassificationHandler. Notice the design: handlers are named after task shapes (classification, extraction, alignment), never after one narrow domain. A new use case is "which existing shape is this, and what scoring mode?", not "write a new handler." That generality is why the same pipeline serves very different projects.

    You set the config; the trainer and the handler do the rest

    So the division of labor is: TrainingConfig carries the hyperparameters you tuned by hand, the trainer does the tokenization and masking you wrote by hand, and the task handler, picked from the manifest's task profile, builds the eval prompts and scores the outputs. You pick a training preset or edit the config (or accept the default the Autopilot Planner proposes, under Settings → Tools → Autopilot Planner) and the platform assembles a runnable train plan. Before it spends a GPU-hour on that plan, though, it runs preflight — the readiness line on the Train form and the Checks section under More options — the next lesson.

    Key idea

    TrainingConfig is your TrainingArguments + LoraConfig as declarative config, with training presets as named patches over it; the trainer runs your tokenize/mask code; a task handler is your eval-and-score code, picked by task shape. Together they reproduce your by-hand training and evaluation — declaratively, and general across task types.

    Key terms

    TrainingConfig
    The declarative training config (backend/app/schemas/training.py): base model, training mode, LoRA knobs, optimizer/schedule, batch, precision, save_steps.
    recipe
    Three different things: a task-shape recipe (the UI's Task type, no hyperparameters), a training recipe (a Training preset, a patch over TrainingConfig), or a pipeline recipe (a Pipeline preset).
    task-handler dispatcher
    Routes the manifest's task_profile to the evaluation handler for that task, with GenericHandler as the fallback.
    task handler
    A general, task-shape-named evaluation component (Classification, QA, StructuredExtraction, RAG, ToolCall, …) implementing build_prompts() and score().
    auto_epochs
    On by default: sizes epochs (and, on small data, gradient accumulation first) to about 200 optimizer steps; num_epochs is ignored while it is on.
    save_steps
    How often checkpoints are written during training, in optimizer steps (default 100).
