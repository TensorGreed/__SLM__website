    RunEvent taxonomy & Coach catalogue

    After this reference you can recognise any RunEvent on a project's timeline — stage, severity, reason code, payload — and you know the Coach contract behind the inline Coach notices: which workflow stages it speaks at, where each stage's notices appear in the workspace, what severity each suggestion can carry, and what the five action kinds do when clicked.

    Level: intermediate Read time: ~12 min Type: Reference

    BrewSLM's audit spine has two reference surfaces a developer reads daily: the RunEvent stream (what already happened) and the Coach suggestions (what to do next — the inline "Coach · warning" notices on each destination). Both are contracts the platform commits to. This catalogue documents them as they exist in the codebase — schema, taxonomy, action kinds — so the labels you see in the UI map straight to fields you can grep for. Where the taxonomy declares more than the code emits today, the catalogue says so. (Backend names keep the old Coach Mode label; the UI just says Coach.)

    The RunEvent row

    One canonical row per "interesting thing happened" across every stage. The schema is append-only — corrections are new rows, never updates. Every row carries:

    id              int    primary key (autoincrement)
project_id      int    FK projects.id
run_id          str    "<stage>-<id>" by convention (exp-42, deploy-7, autopilot-{hex})
parent_run_id   str?   parent op when nested (training under autopilot)
stage           str    one of nine canonical values (below)
severity        str    info | warning | error | critical
reason_code     str?   stable code from the taxonomy (required when error/critical)
actor           str    "system" by default; user-id when an operator triggered the event
summary         str?   one-line human readable; UI uses as the row label
payload         json   structured details, free-form per emitter
ts              datetime  wall-clock time of the event
created_at      datetime  insert time (differs from ts for back-dated replays)

    The nine canonical stages

    Every emitter MUST tag its event with one of nine string constants. emit_event checks this at runtime and rejects any other string (invalid_stage:<value>); new stages are added by extending the KNOWN_STAGES set. Only five stages have emitters today: ingestion, training, eval (one info event per completed evaluation), export and deployment (info events only). cleaning, adapter, autopilot and system are declared, not emitted today.

    ingestion     data import / annotation / teacher capture
cleaning      cleaning rules / PII scanning / outlier removal
adapter       Adapter Studio (data-transformation contracts)
training      training runs (SFT, KD)
eval          evaluation runs against eval packs
export        artifact bundling + quantization
deployment    deploy / promote / rollback / drift
autopilot     newbie / strict-mode autopilot orchestration
system        DB / config / extension load (catch-all)

    The four severities

    • info — normal lifecycle ("training completed", "rows imported"). The vast majority of RunEvents.
    • warning — soft issue worth surfacing but not blocking. The one emitted today: training_time_limit_projected ("training on pace to hit its time limit").
    • error — operation failed; must carry a reason code from the taxonomy.
    • critical — pager-worthy. Reserved; nothing emits it today. Must carry a reason code.

    The reason-code taxonomy, by stage

    Every error or critical RunEvent must set a reason_code from the canonical taxonomy. This is a runtime validation inside emit_event, not a lint step: a missing code raises reason_code_required, an unknown one raises invalid_reason_code:<value>. Every call site catches the exception, so in practice the event is dropped and logged, and the operation itself carries on. (info and warning codes are not checked, which is how the off-taxonomy training_time_limit_projected warning gets through.)

    The taxonomy declares 35 codes, but only some have an emitter today. Each code below is marked [emitted] or [declared, not emitted today]. Treat the second group as reserved names: grepping the timeline for them returns nothing. The taxonomy is grouped by stage:

    ingestion

    ingest_unsupported_format         [declared, not emitted today] file extension not in the supported set
ingest_io_error                   [declared, not emitted today] disk write/read failure during ingest
ingest_validation_failed          [declared, not emitted today] row failed schema or content validation
dataset_import_run                [emitted] INFO — generic import pipeline wrote rows
                                  (payload: source, locator, mapper,
                                  accepted/rejected counts, written_path, config_id)
dataset_import_failed             [emitted] import pipeline raised before any rows written
annotation_job_created            [emitted] INFO — label job created (payload: job_id, name, label_type, target_rows)
annotation_label_submitted        [emitted] INFO — reviewer submitted a single label
annotation_rows_promoted          [emitted] INFO — labeled rows materialized to a downstream dataset
distillation_teacher_capture      [emitted] INFO — Track 4 slice 1 — teacher top-k logprobs captured

    cleaning

    cleaning_outlier_threshold_exceeded   [declared, not emitted today] outlier removal removed more rows than the configured cap
cleaning_pii_block                    [declared, not emitted today] PII / safety scan blocked the dataset from advancing

    adapter

    adapter_schema_mismatch         [declared, not emitted today] declared input/output schema could not be matched to the data
adapter_field_resolution_failed [declared, not emitted today] adapter could not resolve a field mapping (missing column, wrong type)

    training

    training_dispatch_error    [emitted] failure dispatching the run to the runtime backend
training_runtime_error     [emitted] generic runtime failure (today only from the simulate runtime)
training_oom               [declared, not emitted today] GPU out-of-memory during training
training_timeout           [emitted] run exceeded its wallclock budget
training_cancelled         [declared, not emitted today] operator (or upstream signal) cancelled the run

    A real (external) training failure is recorded on the run itself, and its RunEvent is named training_<failure code>. Only training_timeout of those names is in the taxonomy, so the other failure events (process exit, signal, monitor error, including most out-of-memory kills) are rejected by the check above and never reach the timeline. Read the run's own failure message on Train for those.

    eval

    eval_runtime_error      [declared, not emitted today] generic failure inside the evaluation runner
eval_dataset_missing    [declared, not emitted today] eval pack referenced a dataset that no longer exists
eval_judge_unavailable  [declared, not emitted today] LLM-as-judge call failed (provider down / quota / config)

    export

    export_run_failed             [emitted] any export failure (artifact build, manifest write, smoke check, quantization)
export_artifact_missing       [declared, not emitted today] required model / tokenizer artifact missing at export time
export_quantization_failed    [declared, not emitted today] quantization step exited non-zero or produced an invalid artifact

    deployment

    deployment_smoke_failed              [declared, not emitted today] post-deploy smoke check failed against the live endpoint
deployment_promote_blocked           [declared, not emitted today] promote refused (status not promotable / readiness gate failed)
deployment_rollback_no_predecessor   [declared, not emitted today] rollback refused because no superseded predecessor exists
deployment_drift_detected            [declared, not emitted today] drift check found pass-rate delta beyond tolerance vs baseline

    Deployment emits info lifecycle events only (create / promote / rollback), with no reason code.

    autopilot

    autopilot_repair_blocked        [declared, not emitted today] autopilot refused a repair (strict mode or unsafe action)
autopilot_strict_mode_refused   [declared, not emitted today] strict mode rejected an auto-repair that would otherwise have applied
autopilot_no_safe_plan          [declared, not emitted today] autopilot could not construct a safe plan from the current intent

    system

    system_db_error              [declared, not emitted today] unexpected database error from a service-internal write path
system_config_invalid        [declared, not emitted today] required configuration value missing or malformed at runtime
extension_load_failed        [declared, not emitted today] plugin module import / register hook raised
extension_contract_invalid   [declared, not emitted today] plugin module failed one or more contract checks

    Stable vs evolving

    The nine stages and four severities are stable — they change only with a major contract bump. The reason-code list grows as new failure modes are surfaced (each addition is a one-line change to the taxonomy file plus an emitter). KNOWN_REASON_CODES in the codebase is the source of truth for what may be emitted; whether a code is emitted depends on an emitter existing, which is why the marks above matter.

    Coach — the contract

    The Coach is a per-stage suggestion service. Each workspace destination mounts CoachNotices for the stage it shows; that component calls GET /api/projects/{id}/coach/{stage} and renders every suggestion as an inline notice — the "Coach · info / warning / critical" tag, the title and body, one click-to-execute action button, a "why?" trace, and an × that dismisses that rule for the project (remembered in the browser). Two notices show at first; "Show N more" expands the rest. The Overview lists up to three under Worth a look. There is no Coach bar, strip or toggle any more; Settings → Show inline tips hides the notices for a project.

    The eight workflow stages Coach speaks at — and where each one renders

    data         dataset import / Adapter Studio / synthetic playbook activity   → Data → Sources
cleaning     cleaning rules and review queue                                → Data → Prepare
gold_set     answer-key (gold-set) status and top-up suggestions            → Data → Labels
synthetic    synthetic mix + pending review                                 → Data → Generate
dataprep     split missing / stale / test too small / leakage               → Data → Split
training     training config + preflight + active runs                     → Train
eval         pass/fail rules + failure clusters + remediation               → Results
export       export-vs-base verdict                                         → Ship

    A stage the API accepts but no generator handles answers with an empty list and handler_available=false; an unknown stage is a 400 naming the valid ones.

    The three severity levels

    Each suggestion carries a severity the UI uses to colour the notice consistently (and to order them: critical first):

    • info — informational ("here's a good next step").
    • warning — soft ("forecast says this run is borderline; consider topping up the answer key").
    • critical — urgent ("Your answer key has 12 rows" — most useful first models need at least 100 rows of labeled examples; the backend still calls the answer key the gold set, e.g. in rule ids).

    The canonical suggestion shape

    {
  "id":       "data:gold-row-count",
  "rule_id":  "gold-row-count.below-comfortable",   /* the decision rule the "why?" trace names;
                                                      dismissing a notice remembers this */
  "severity": "warning",
  "title":    "Your answer key has 150 rows — could be stronger",
  "body":     "You're past the 100-row floor, but 300+ rows is the comfortable zone for narrow tasks ...",
  "action":   { /* one of the five action kinds */ }
}

    The same rule at 99 rows or fewer fires as gold-row-count.thin with severity critical and the title "Your answer key has N rows"; 100–299 rows gives the below-comfortable warning above. Generators are read-only — they never mutate project state. Side effects happen only when the user clicks the action button.

    The five action kinds

    Every action carries a kind, a label, and a params dict. The frontend routes the click on kind alone.

    {
  "kind":   "navigate",
  "label":  "Pick a recipe first",
  "params": { "target": "recipe-picker" }
}
    • navigate — route the user to a destination or section. params.target is a stable name the frontend maps to a workspace URL (e.g. recipe-picker → Train → More options → Task type, training-config → Train → More options, pipeline-tab + params.tab → the matching Data step / Train / Results / Ship, dataprep-split → Data → Split). Used when the next step is "go look at this."
    • run_playbook — trigger a recipe-aware synthetic-data playbook in the background. params carries the playbook mode (e.g. positives_paraphrase) and a target_count. Used for "I'll generate the rows for you" actions.
    • augment_from_cluster — open a failure cluster as a generation source. params is {eval_result_id, cluster_id, target_count}: the cluster is an eval-miss cluster from that evaluation (Results → Failures), not a RunEvent cluster, and the generated rows land pending review. Used after an eval reveals a cluster of similar failures (Lesson 3.13).
    • start_flow — start a background flow, today the documents → Q&A flow (training:documents-to-qa): passages → training pairs + an answer key → split → train. params is {flow: "documents-to-qa", max_passages, pairs_per_passage}; it is offered only to document-only projects with no task type or the qa-sft one.
    • reroute_to_rag — clone the project into a retrieval-first sibling (base model + retrieval, no LoRA) when the eval says passages beat the fine-tune (eval:passages-beat-finetune, Lesson 3.9).

    Concrete thresholds you'll see in suggestions

    Some Coach generators use named numeric thresholds. The current values for the answer-key (gold-set) generator, for example:

    GOLD_ROW_THIN_MAX             99    # <= thin (severity bumps to "critical")
GOLD_ROW_COMFORTABLE_MIN      300   # target the suggested top-up tries to reach
SUGGESTED_TOPUP_FLOOR         20    # don't suggest below this
SUGGESTED_TOPUP_CEILING       500   # don't suggest above this

    Treat these as representative, not part of the public contract — they tune over time as the platform learns better defaults. The stable surface is the severity transitions and the action kinds.

    Key idea

    Two surfaces, one audit spine. RunEvent records what happened with a stable (stage, severity, reason_code) tuple and a JSON payload. The Coach tells you what to do next with a (stage, severity, action) shape and five action kinds — navigate, run_playbook, augment_from_cluster, start_flow, reroute_to_rag — rendered as inline notices where you are working. Both are contracts: stages and severities are stable, the reason-code list and threshold values grow with the platform.

    The last reference catalogues the consumer that closes the loop on these events: the eval pack's gate schema and the two failure-cluster surfaces, including the eval-miss clusters that augment_from_cluster targets.

    Key terms

    RunEvent
    The canonical audit-row schema. Append-only; one row per "interesting thing happened" across all nine stages.
    RunEvent stage
    One of nine canonical strings (ingestion, cleaning, adapter, training, eval, export, deployment, autopilot, system).
    RunEvent severity
    info / warning / error / critical. Errors and criticals must carry a reason code.
    Reason code
    String from the canonical taxonomy that names a failure mode (e.g. training_dispatch_error, export_run_failed). Required and validated at runtime for error / critical events; many declared codes are not emitted today.
    Coach stage
    One of eight workflow surfaces Coach speaks at: data, cleaning, gold_set, synthetic, dataprep (the five Data steps), training (Train), eval (Results), export (Ship).
    Coach notice
    How one suggestion renders: an inline card with the "Coach · severity" tag, one action button, a "why?" trace and a dismiss ×. Settings → Show inline tips turns them off.
    Coach action kind
    One of five: navigate (route), run_playbook (trigger generation), augment_from_cluster (generate rows targeted at an eval-miss cluster), start_flow (start the documents → Q&A flow), reroute_to_rag (clone into a retrieval-first sibling).
