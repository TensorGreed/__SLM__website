    Eval pack & failure cluster schema reference

    After this reference you can read an eval pack's gate list, identify which gates are required vs informational and where they are enforced, and recognise a RunEvent failure-cluster row by its (project_id, stage, reason_code, signature) key — and tell it apart from the eval-miss clusters that augment_from_cluster remediates.

    Level: intermediate Read time: ~11 min Type: Reference Updated: 13 Nov 2026

    This last reference catalogues the two surfaces the evaluation lifecycle exposes: the eval pack (gates that score whether a trained model meets its bar) and the failure cluster (the grouping of similar errors that drives the data-iteration loop). Lesson 3.8 explained what they do and where they live in the workspace; this reference documents the schema. One naming note before the JSON: the workspace calls an eval pack a rule set and a gate a pass/fail rule (Results → Verdict's Pass/fail rules card; the rule-set card on Results → Failures). The field names, pack ids and keys below are the API's and are unchanged.

    This is a verified-contract page: every row was checked against public BrewSLM main at commit 580e616 (13 Nov 2026). Tables say what is enforced or applied today in their own column and name the file that does it; most of the gate logic lives in services/evaluation_pack_service.py.

    Eval pack — the envelope

    An eval pack is identified by id (e.g. evalpack.general.default, evalpack.domain-profile) and conforms to the Evaluation Contract v2 (slm.evaluation-pack/v2). The pack carries per-task specs and a backward-compatible top-level gate list.

    {
  "pack_id":             "evalpack.general.default",
  "contract_version":    "slm.evaluation-pack/v2",
  "description":         "...",
  "gates":               [ /* default task profile's gates */ ],
  "task_specs":          [ /* per-task-profile specs (preferred) */ ],
  "default_task_profile": "instruction_sft"
}

    The legacy top-level gates field still works for single-task projects; modern packs put their gates inside task_specs so different task profiles in one project can each carry their own promotion criteria.

    The gate schema (Evaluation Contract v2)

    Every gate is a small dict. Only metric_id is required: a gate without it is dropped. When a pack is loaded, each gate is normalised to the keys below; anything else on the dict is discarded.

    KeyRequired?DefaultMeaning
    metric_idyes—The metric to compare, lower-cased (hyphens and spaces become _). Matched against the eval's metrics, including metric_schema aliases.
    gate_idnomin_<metric_id>The name the report and the Verdict card use ("Failed required rules: min_f1").
    operatornogtegte (actual ≥ threshold) or lte (actual ≤ threshold). Any other value becomes gte. No eq, no in, no string match.
    thresholdnonullA number. null makes the gate not_enforced: reported, always passes.
    requirednotrueA required gate fails the report when it fails or its metric is missing; an optional one is shown but never fails the report.
    weightnoabsentKept only if you set it to a number.
    sourceset for youevaluation_pack_v2 or the pack builder's tagWhere the gate came from, for the audit. Not read from your dict.
     
    { "metric_id": "macro_f1", "threshold": 0.5 }
// is stored as
{ "gate_id": "min_macro_f1", "metric_id": "macro_f1", "operator": "gte",
  "threshold": 0.5, "required": true, "source": "evaluation_pack_v2" }

    The gate checker also understands per-gate variance_policy, slice_name, min_slice_support and the operators worst_slice_gte / worst_slice_lte (the rule-set editor offers the worst-slice operators). Pack loading drops those keys and turns a worst-slice operator into plain gte on the overall metric, so in a project's gate report they are carried, not applied today. A gate on one slice still works if you write the slice into the metric id: "metric_id": "per_slice.long_input.f1".

    Per-task specs (the canonical v2 form)

    The example below is an illustrative custom pack, not a built-in default: its thresholds are ones you might set for a release candidate. The built-in evalpack.general.default asks much less of instruction_sft (exact match ≥ 0.4 and F1 ≥ 0.5, both required), because it is calibrated for the 135M default model.

    {
  "task_specs": [
    {
      "task_profile":         "instruction_sft",
      "display_name":         "Instruction SFT",
      "description":          "...",
      "required_metric_ids":  ["macro_f1", "exact_match"],
      "metric_schema":        { "macro_f1": { /* aliases, description, expected_range */ } },
      "gates": [
        { "gate_id": "min_macro_f1",    "metric_id": "macro_f1",    "operator": "gte", "threshold": 0.90, "required": true },
        { "gate_id": "min_exact_match", "metric_id": "exact_match", "operator": "gte", "threshold": 0.85, "required": true }
      ]
    }
  ]
}

    A pack with multiple task profiles supports projects whose blueprint says "we're training a classifier and a span extractor"; each profile gets its own gates and metric schema. required_metric_ids is auto-extended to include every metric referenced by a required gate, so a typo in a metric name there surfaces as a missing_metric_required gate result rather than a silently un-evaluated gate.

    How gates are checked: the reason vocabulary

    After evaluation (Lesson 3.8) the run's latest result of each eval type is flattened into one metrics dict. Each gate is then checked mechanically and gets passed: true|false plus a reason:

    reasonPassed?When
    okyesThe value clears the threshold.
    below_thresholdnoA gte gate's value is under the threshold.
    above_thresholdnoAn lte gate's value is over the threshold.
    missing_metric_requirednoA required gate's metric is not in the results.
    missing_metric_optionalyesAn optional gate's metric is not in the results.
    not_enforcedyesThe gate's threshold is null.
    variance_below_thresholdnoMulti-seed run: the mean clears a gte gate but mean − std does not.
    variance_above_thresholdnoMulti-seed run: the mean clears an lte gate but mean + std does not.

    Variance gates. When the metric comes from a multi-seed aggregate (Lesson 3.7), the gate is checked against the lower bound: mean − std for gte, mean + std for lte. The check then also reports actual_std, actual_min, actual_max, actual_n, gate_value, per_seed and variance_policy: "lower_bound". A single-seed run is checked on its value as-is. (The checker has a mean policy too, but since pack loading drops a gate's variance_policy, every pack gate uses the lower bound.) The worst-slice check has its own reasons (worst_slice_below_threshold, no_eligible_slices_required…), which a project report does not produce today, for the reason above.

    The gate report says passed when no required gate failed and no required metric is missing; a failed optional gate is shown but does not fail the report. Two gates can be added on top of the pack: the built-in checks' probe gate, when the project switches it on, and a required probe_critical_failures ≤ 0 gate whenever the project has a custom check marked critical.

    Where gates are enforced

    PlaceEnforced today?What happens
    Results → Verdict, Pass/fail rules cardno, informationalA PASS / FAIL badge (NO REPORT when nothing has been checked), the run, the rule set, when it was checked and the failed required rules by gate_id. Nothing is blocked.
    Promote (Ship → Deploy)noPromote checks only the deployment version's status; it never reads gates. (deployment_promote_blocked is declared, not emitted.)
    Exportyes, when gate_policy is onservices/export_service.py reads project.gate_policy: must_pass blocks if the report did not pass, blocked_if_missing if required metrics are missing, min_score below an aggregate gate score (the share of scored gates that passed). The export is marked FAILED: "Export blocked by deployment gates: …".
    GET /api/projects/{id}/gate-checkno, a reportApplies the same policy and returns is_blocked plus reasons, without blocking anything.

    gate_policy is off by default: a new project gets must_pass: false, blocked_if_missing: false, min_score: 0.0, so out of the box a failing gate blocks nothing. Two ways switch it on: the four built-in starter packs offered in the New Project dialog (legal, customer support, healthcare, finance) each set must_pass: true and a min_score, and the manifest's workflow.gate_policy sets it on apply. There is no UI toggle for it.

    The built-in rule sets

    Pack idWhat it gates
    evalpack.general.defaultThe fallback. Per-profile specs; e.g. instruction SFT exact match ≥ 0.4 and F1 ≥ 0.5 (required), classification accuracy and macro-F1 ≥ 0.5 (required).
    evalpack.classification.defaultLabel prediction: the general default's specs with the task profile defaulting to classification, so accuracy and macro-F1 ≥ 0.5 (required), safety pass rate ≥ 0.9 (optional).
    evalpack.quality.strictHigher bars for release candidates; every gate required.
    evalpack.fast.iterationLow bars for quick loops.
    evalpack.domain.legal, .support, .healthcare, .financeSmall domain-flavoured gate sets (e.g. support: accuracy ≥ 0.8 and hallucination rate ≤ 0.05).
    evalpack.rag_protocol.disciplineRAG answers: F1, citation rate, hallucination rate, appropriate refusals.
    evalpack.domain-profileBuilt on the fly from the project's domain profile thresholds.
    evalpack.project.scaffoldedA project's own draft, saved from the rule-set card.

    Which of these scores your project depends on the project's preference, its domain profile and the default, in that order.

    Which rule set am I scored against?

    Each project's pass/fail rules come from one rule set (an eval pack). BrewSLM takes the first of these that applies:

    1. The rule set chosen for the project. Clicking Use scaffold saves the drafted rules and makes them the choice (evalpack.project.scaffolded). Picking a built-in pack, such as evalpack.quality.strict, evalpack.classification.default or evalpack.domain.legal, or applying a pipeline recipe also sets it. A project made from the Ticket Router SLM or Log Triage Assistant template starts with evalpack.classification.default chosen.
    2. The domain profile's thresholds (evalpack.domain-profile). Every project resolves a profile, at least the platform default generic-domain-v1, so with nothing chosen this is the rule set: F1 ≥ 0.65, LLM-judge pass rate ≥ 0.75 and safety pass rate ≥ 0.90 are required; exact match ≥ 0.55 is reported but not required.
    3. evalpack.general.default, only for a profile with no thresholds: accuracy and macro-F1 ≥ 0.5 for classification; exact match ≥ 0.4 and F1 ≥ 0.5 for instruction tasks.

    A scaffold is a draft until you click Use scaffold. The task type (recipe) only shapes that draft; for classification it proposes macro-F1 ≥ 0.65, accuracy ≥ 0.70 and per-class F1 ≥ 0.50.

    Two neighbours are easy to mix up with a rule set:

    • A domain preset picked at project creation (Legal, Customer Support, Healthcare, Finance) sets the base model, adapter defaults and an export gate, which decides whether export must pass the rule set. It does not choose the rule set.
    • A domain pack (the only built-in one is general-pack-v1) carries defaults such as the split ratios and a default profile. Packs apply live: editing one changes every project that uses it, so duplicate a pack before you edit it.

    To see which one is active, look at the Pass/fail rules card in evaluation: it names the Active Pack and its Source, for example "domain profile default". The Readiness overview's pass/fail rule breakdown names the same rule set ("Rules from …"), and says so when your task type suggests a task-specific rule set the project isn't using.

    Classification projects

    The classification recipe suggests evalpack.classification.default, and the Ticket Router SLM and Log Triage Assistant templates and the sentiment demo choose it, so those projects are gated on accuracy and macro-F1. Picking the classification task type on a project does not choose it: with nothing chosen, the project is still scored by its domain profile's rule set, which is written for free-text answers (a classification eval reports no LLM-judge pass rate, so that required rule cannot pass). Pick it, or a scaffold, in the rule-set picker; the Readiness overview's rule breakdown points this out.

    Honest reporting: required vs informational

    The pack's report carries passed and a reason on every gate, regardless of required. A model that clears its required gates but fails an informational one still passes the report, and even a failed report blocks nothing unless the project's gate policy is on, so the gate report carries every failing gate explicitly. This is the "show the gate that failed" rule the Academy keeps coming back to: don't hide informational failures inside a headline "passed: true."

    The metric_schema field

    Each task spec carries a metric_schema dict mapping metric_id to a small descriptor. The descriptor's role is to make metrics self-describing in the audit:

    {
  "macro_f1": {
    "description":    "Metric 'macro_f1' from evaluation outputs.",
    "expected_range": [0.0, 1.0],
    "aliases":        ["macro_f1", "f1_macro"]     // accepted variants in handler output
  }
}

    Those three keys (description, expected_range, aliases) are the whole descriptor; there is no display name or direction field (direction lives on the gate's operator).

    If a handler emits the metric under one of the listed aliases, the eval pack normalises it to the canonical metric_id before checking gates. That's how a third-party score function whose code says "f1_macro" still passes a gate written against "macro_f1".

    FailureCluster — the row schema

    Clustering reads error / critical RunEvents (Lesson 3.12) and groups them. It was specified as a nightly job, but the app has no scheduler: the recompute button on Ship → Monitor (which also lists the clusters with links to their exemplar events) drives it, via POST /api/projects/{id}/failure-clusters/recompute. Clusters of eval misses for a run are a separate view on Results → Failures. The result of a recompute is a failure_clusters table with one row per distinct failure shape per project. The unique key is (project_id, stage, reason_code, signature):

    id                  int                primary key
project_id          int                FK projects.id
stage               str(32)            from KNOWN_STAGES
reason_code         str(128)           from the taxonomy
signature           str(64)            hash of the canonical failure shape
failure_count       int                running count of events in this cluster
first_seen_at       datetime           when this signature first appeared
last_seen_at        datetime           updated on every new occurrence
exemplar_event_ids  json (list[int])   capped list of representative RunEvent ids
exemplar_summaries  json (list[str])   first-line summaries of those events
exemplar_run_ids    json (list[str])   the run_ids that emitted those exemplars
created_at          datetime
last_computed_at    datetime           refresh marker for clustering runs
    • signature is the first 12 hex characters of sha1(stage|reason_code|normalised summary). Normalising lowercases the summary and strips timestamps, long hex tokens and standalone numbers, so two failures that differ only by a step, batch size or line number land in the same cluster. It does not read the payload.
    • failure_count grows over time; the cluster is the unit of "this keeps happening" not "this happened once."
    • Exemplar lists are capped at 5 — the cluster carries enough rows to investigate without each cluster ballooning.

    Because only a few error codes are emitted today (Lesson 3.12), these clusters can only hold failed imports (dataset_import_failed), failed dispatches (training_dispatch_error), real training runs that stopped without finishing (training_timeout, training_signal, training_exit, training_error), simulate-runtime training errors and failed exports (export_run_failed). The service is services/run_event_clustering_service.py; the eval-miss clusters are services/failure_cluster_service.py.

    Remediation: the augment_from_cluster path

    The remediation contract is: a cluster of eval misses becomes a generation source. This uses the eval-miss clusters on Results → Failures, not the RunEvent failure_clusters rows above. The Coach notice's augment_from_cluster action (Lesson 3.12) carries {eval_result_id, cluster_id, target_count}. The flow:

    1. User clicks Augment N rows for this cluster on the Coach notice at the top of Results, or Augment from this cluster on a cluster card under Results → Failures.
    2. The backend re-clusters that eval result's misses and finds the cluster by cluster_id.
    3. It runs the cluster-targeted synthetic playbook (SynthMode.CLUSTER_TARGETED), whose prompt embeds the cluster's reason, output pattern and exemplar rows. It never reads the failure_clusters table.
    4. The generated rows land in the synthetic dataset with review_status="pending" (Lesson 3.3) — the review queue is under Data → Labels → Details → Review queue.
    5. The user reviews; approved rows roll into the next training round.

    That whole loop is the Track-3 version of "read the failures, add more data, retrain" — gated and audited rather than ad-hoc.

    Key idea

    Two halves of one decision loop. The eval pack declares the quality bar — every gate is a scalar comparison that reports passed and a reason; it blocks only at export, and only when the project's gate_policy is on. Clusters close the loop — eval-miss clusters are routed through augment_from_cluster back into the data layer, while RunEvent clusters on Ship → Monitor group repeated pipeline failures. Both are schemas you can grep for: gate dicts in the pack, (project_id, stage, reason_code, signature)-keyed rows in failure_clusters.

    Key terms

    Evaluation Contract v2
    slm.evaluation-pack/v2 — the eval-pack schema with per-task specs (each carrying its own gates and metric schema).
    Gate
    A scalar comparison: {gate_id, metric_id, operator: gte|lte, threshold, required, source?, weight?}; only metric_id is required. Its result carries passed and a reason (ok, below_threshold, variance_below_threshold…). In the UI: a pass/fail rule; the pack is the rule set.
    Required gate
    A gate with required: true (the default): a missing metric fails it. Failed gates block only at export, and only when the project's gate_policy is switched on; promotion never checks gates.
    Task spec
    Per-task-profile section of an eval pack carrying required_metric_ids, metric_schema, and the gate list.
    FailureCluster
    Row in failure_clusters, uniquely keyed on (project_id, stage, reason_code, signature); carries counts, timestamps, and exemplar lists capped at 5. Built from error / critical RunEvents, not eval misses.
    augment_from_cluster
    Coach-notice action (also a button on each cluster card on Results → Failures) that runs the cluster-targeted synthetic playbook on an eval-miss cluster; the rows land pending review.
