    Capstone B: export, deploy & Coach end-to-end

    After this capstone you can export a model to a deployment format from Ship → Package (smoke tests run there), deploy a versioned endpoint and run its drift check, and describe how the inline Coach notices guide the full lifecycle — then compare a platform run to your by-hand Track 2 run.

    Level: intermediate Read time: ~11 min Prerequisites: When fine-tuning isn't the answer: auto-RAG & reroute-to-RAG Updated: 13 Nov 2026

    You merged and saved a model by hand in lesson 2.8 and noted that BrewSLM automates export to GGUF / ONNX / Hugging Face. Here's that stage — it lives under Ship in the workspace, four stages deep: Package, Publish, Deploy, Monitor — plus the Coach notices that have been implied behind every recommendation in this track.

    10 Export — the merged artifact, productized

    Export takes the trained model and a target format and produces an artifact bundle with weights, tokenizer, manifest, and a smoke-check trace. This is your merge_and_unload + save_pretrained from Track 2, with more targets and quantization tracked. In the workspace it is the New export form on Ship → Package (/project/<id>/ship?stage=package): pick the run, the format and the quantization; finished exports appear in the Releases table below the form.

    formats:        GGUF (CPU) | ONNX | HuggingFace | TensorRT-LLM | Docker
quantization:   None | 4-bit | 8-bit          # the New export form's choices
# a GGUF quant such as Q4_K_M is made first, under Options → Compress first
#   (output GGUF, 4-bit = Q4_K_M via llama.cpp); the GGUF export packages that file
smoke tests:    run by the export (on by default)
RunEvent: export (info)   payload: { format, output_path, file_size_bytes }
  on failure → export_run_failed              # the only export failure code emitted today

    The format you pick follows Track 2's logic: a HuggingFace or Docker export for a GPU server, GGUF for CPU/edge. The order matters for GGUF: compress to a quant like Q4_K_M first under Ship → Package → Options → Compress first, then New export → GGUF (CPU) packages the compressed file. A completed HuggingFace export can go to the Hub from Ship → Publish. A LoRA run is merged into its base model inside the HuggingFace / Docker export (and before conversion in Compress); the separate merge under Compress is model merging (TIES / DEX), not the LoRA merge.

    11 Deploy (optional) — a versioned, watched endpoint

    Deploy (Ship → Deploy) takes an export and a deployment target — a runner (vLLM, TGI or Ollama) or a managed inference endpoint — and records a DeploymentVersion (pending until you promote it) with promote / reject / rollback / drift-check actions; each served version's drift history sits with it on Ship → Deploy, and Ship → Monitor shows the run events and failure clusters. Two safety mechanisms matter:

    • Smoke tests at export time — the export runs a quick sanity pass on the artifact before you ever deploy it. Promote itself checks only that the version is still pending; it runs no smoke test and no gate.
    • Drift check, on demand — it scores your answer key (the gold set, kept under Data → Labels) against the deployed model by exact match (you paste its predictions on Ship → Deploy, or the API calls an endpoint URL) and compares the pass rate with the baseline: the latest evaluation of the run behind the export. A move larger than the tolerance (default 0.05) is reported as drift. Nothing runs on a schedule — re-run it yourself after any infra change or on your own calendar, so serving regressions are caught, not discovered by users. Your Track 1 gold set keeps working long after training.

    Deployment actions emit info RunEvents only. The declared failure codes deployment_smoke_failed, deployment_drift_detected and deployment_promote_blocked are not emitted today; read a drift verdict on Ship → Deploy.

    Coach notices — the through-line

    Throughout this track, each "what next?" had an answer: review these pending rows, your gate isn't met, augment from this cluster, consider RAG. The backend's Coach service emits those stage suggestions (data / cleaning / gold_set / synthetic / dataprep / training / eval / export) and offers actions — navigate, run_playbook, augment_from_cluster, start_flow, reroute_to_rag — so you're never staring at a project wondering what to do. There is no separate Coach bar or toggle any more: each suggestion renders inline as a "Coach · info / warning / critical" notice on the destination it belongs to (Data per step, Train, Results, Ship), with its action button, a "why?" trace and an × that dismisses it; the Overview shows up to three under Worth a look. Settings → Show inline tips switches them off for a project. It's the eleven-stage lifecycle, narrated where you are standing.

    Capstone B — run it through the platform

    Take the same sentiment task you fine-tuned by hand and run it through BrewSLM end-to-end:

    1. + New Project: a name and the problem statement (base model SmolLM2-135M-Instruct under
   Advanced options, or pick it later on the Train form); it lands on the Overview.
2. Data → Sources: Import dataset (your file, or hf:imdb) → Source → Task type → Map → Preview & Confirm.
3. Data → Generate: top up with a synthetic playbook; clear the review queue
   (Data → Generate → Details → Review queue).
4. Data → Labels: confirm the task shape = classification; Data → Split: build the splits.
5. Train → More options → LoRA and advanced training (r=16, lr=2e-4, 3 epochs, bf16).
   Typing an epoch count turns auto-epochs off; leave it untouched and epochs scale to your row count.
6. Train: the readiness line must read "Ready to train" — clear any blocking issues (More options → Checks).
7. Train → press Train → Launch; follow the run in the bell and the runs list below the form.
8. Results → Verdict: evaluate on the test examples (with no rule set chosen it is
   evalpack.domain-profile: F1 >= 0.65, LLM-judge >= 0.75, safety >= 0.90 required;
   for classification, click Use scaffold on Results → Failures for the class-aware rules);
   Results → Failures: read the clusters.
9. If the reroute panel says try_rag → measure it on Results → Compare (auto-RAG) before switching.
10. Ship → Package → Options → Compress first: GGUF, 4-bit (Q4_K_M); then New export → GGUF (CPU)
    (its smoke tests run here) → Ship → Deploy: record a version, promote it, run a drift check.

    Step 8 scores against whichever rule set the project uses, which is not necessarily the one your recipe suggests:

    Which rule set am I scored against?

    Each project's pass/fail rules come from one rule set (an eval pack). BrewSLM takes the first of these that applies:

    1. The rule set chosen for the project. Clicking Use scaffold saves the drafted rules and makes them the choice (evalpack.project.scaffolded). Picking a built-in pack, such as evalpack.quality.strict, evalpack.classification.default or evalpack.domain.legal, or applying a pipeline recipe also sets it. A project made from the Ticket Router SLM or Log Triage Assistant template starts with evalpack.classification.default chosen.
    2. The domain profile's thresholds (evalpack.domain-profile). Every project resolves a profile, at least the platform default generic-domain-v1, so with nothing chosen this is the rule set: F1 ≥ 0.65, LLM-judge pass rate ≥ 0.75 and safety pass rate ≥ 0.90 are required; exact match ≥ 0.55 is reported but not required.
    3. evalpack.general.default, only for a profile with no thresholds: accuracy and macro-F1 ≥ 0.5 for classification; exact match ≥ 0.4 and F1 ≥ 0.5 for instruction tasks.

    A scaffold is a draft until you click Use scaffold. The task type (recipe) only shapes that draft; for classification it proposes macro-F1 ≥ 0.65, accuracy ≥ 0.70 and per-class F1 ≥ 0.50.

    Two neighbours are easy to mix up with a rule set:

    • A domain preset picked at project creation (Legal, Customer Support, Healthcare, Finance) sets the base model, adapter defaults and an export gate, which decides whether export must pass the rule set. It does not choose the rule set.
    • A domain pack (the only built-in one is general-pack-v1) carries defaults such as the split ratios and a default profile. Packs apply live: editing one changes every project that uses it, so duplicate a pack before you edit it.

    To see which one is active, look at the Pass/fail rules card in evaluation: it names the Active Pack and its Source, for example "domain profile default". The Readiness overview's pass/fail rule breakdown names the same rule set ("Rules from …"), and says so when your task type suggests a task-specific rule set the project isn't using.

    What the platform bought you

    Same pipeline, same model, same data as your by-hand run — but now with per-row import accountability, a reviewed synthetic top-up, a reproducible manifest, preflight checks, a watched training Job, pass/fail rules you can enforce at export, clustered failures with remediation, a retrieval escape hatch, and a versioned endpoint with on-demand drift checks. You did it once by hand to understand it; the platform does it repeatably, auditably, and at scale.

    That completes the BrewSLM lifecycle, end to end. You can now do this work by hand and drive the platform with full understanding of what each surface is doing underneath. Three reference lessons close this track: the training config reference, the RunEvent taxonomy & Coach catalogue, and the eval pack & failure cluster schema reference. After them, Track 4 goes deeper — the advanced topics (distillation, preference tuning, quantization, multi-task) that build on this foundation.

    Key terms

    Export formats
    GGUF (CPU) / ONNX / HuggingFace / TensorRT-LLM / Docker — the target the artifact bundle is built for; chosen in the New export form on Ship → Package.
    quantization variants
    Compressed files such as a GGUF Q4_K_M, made first under Ship → Package → Options → Compress first; a GGUF export then packages the compressed file. (The New export form itself offers only None / 4-bit / 8-bit.)
    DeploymentVersion
    A versioned deployment with promote / reject / rollback / drift-check actions.
    drift check
    An on-demand, exact-match scoring of the answer key (gold set) against the deployed model, compared with the latest evaluation of the run behind the export (tolerance 0.05), to catch serving regressions; run and read on Ship → Deploy. It never runs on a schedule.
    Coach notices
    The stage suggestions and actions (navigate, run_playbook, augment_from_cluster, start_flow, reroute_to_rag) the Coach service emits, rendered inline on each destination and under the Overview's "Worth a look".
