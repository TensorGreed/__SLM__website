    Preflight and the trainability forecast

    After this lesson you can explain what preflight checks, why its errors block the launch and its warnings don't, where the result shows up on the Train page, and how preflight and the separate trainability forecast catch dependency, config and data problems before training starts instead of after it crashes.

    Level: intermediate Read time: ~9 min Prerequisites: Recipes and task handlers: the training config without the code Verified: 13 Nov 2026

    In Track 2, two whole lessons existed because of things that bite at runtime: getting the environment right (2.1) and surviving OOM (Track 1.16, and the memory math of 1.15). You found those problems by hitting them. BrewSLM's preflight stage finds them before the run starts.

    What preflight checks

    Preflight takes the resolved training config, the base model, the selected runtime, and the project's prepared split, and checks:

    • Base model and capability — does this base model support the task type and trainer backend you picked?
    • Config consistency — do the settings agree with each other? (fp16 and bf16 both on is an error, for example.)
    • Dependencies and runtime — are the libraries this config needs installed, and is CUDA / bf16 available? DPO and ORPO need trl and LoRA needs peft; a missing one is an error, not a mid-run crash. A missing bitsandbytes is only a warning: the 8-bit optimizer falls back to adamw_torch.
    • Prepared data — does prepared/train.jsonl exist and meet the data contract for the task? A missing validation split is a warning.

    One thing it does not check is whether the training queue is up. With the default TRAINING_BACKEND=external, a run is handed to a Celery worker through Redis, so both must be running; preflight checks the runtime's settings (for example that TRAINING_EXTERNAL_CMD is set), not the services.

    Its output is {ok, errors, warnings, hints, capability_summary}: ok is true when there are no errors. There is no gate check here — pass/fail rules are applied after evaluation (Lesson 3.8).

    # POST /api/projects/1/training/experiments/preflight  (trimmed; the strings are real)
"preflight": {
  "ok": false,
  "errors": [
    "training_mode=dpo requires dependency 'trl' for native pairwise objective trainers."
  ],
  "warnings": [
    "bitsandbytes is not installed; optimizer will fall back to adamw_torch."
  ],
  "hints": [
    "Install trl in the backend/worker environment before DPO/ORPO runs."
  ],
  "capability_summary": { "model": {...}, "dependencies": {...}, "runtime_environment": {...}, "dataset": {...} }
}

    Memory is a separate call. POST …/training/experiments/preflight/plan builds three suggested configs — safe, balanced, max_quality — runs preflight on each, attaches a VRAM-risk level (low / medium / high, scored from batch size, sequence length, LoRA vs full fine-tune, gradient checkpointing and accumulation; cpu when no CUDA device is detected, since VRAM pressure doesn't apply), and names a recommended_profile. The risk is a heuristic: it does not compare gigabytes against your GPU, and it never blocks a launch.

    Where you see it, and the trainability forecast

    Surfaced in the UI, preflight is the readiness line on the Train form. These are the real strings (trainFormText.ts, TrainForm.tsx):

    Checking the data, the model and the runtime…
Ready to train.                 # no errors, no warnings
Ready to train, 1 warning.      # warnings never block
2 blocking issues.  [Fix]  [Check again]
  - training_mode=dpo requires dependency 'trl' for native pairwise objective trainers.
  - …

    When the line is blocked, the form lists the first four blocking issues under it, and Fix opens Train → More options → Checks, where the full preflight result and its plan live. Check again re-runs preflight on demand. Instead of "start training, wait, watch it crash at step 1, fix, repeat," you get the list in seconds — and the confirm dialog the Train button opens shows the resolved config one last time before Launch.

    The trainability forecast, under Train → More options → Plan and gaps (next to the config-gap scan and the archetype comparison), is a different check. It does not ask "will this run start?" but "is this run likely to pass the default gates?". Each signal is ok, warn or block. Row count is a block below the recipe's minimum and a warn below 1.5 times it; answer-key diversity warns when the mean pairwise token overlap (Jaccard) between rows is above 0.40, i.e. the rows look alike; per-task signals add class imbalance for classification (normalised class entropy: warn below 0.75, block below 0.5), format and entity coverage for span extraction, and summary length ratio for summarization. A hand-tuned formula turns row count, task difficulty, base-model size, diversity and class balance into a confidence between 5% and 95%. Any block signal, or a confidence under 40%, gives likely fail; 65% or more with no warn signals gives likely pass; anything else is borderline. It is advice: the panel's button reads "Train anyway" on a likely fail, and it doesn't block. (Source: backend/app/services/trainability_forecast_service.py.)

    The archetype comparison beside it asks a different question: does your data look like the data of projects that worked? It builds a per-recipe profile from your own projects of the same task type whose latest eval pass rate is at least 0.6, mixed with seeded stats from the shipped project templates while fewer than three of your projects qualify. Only distribution stats are kept, never rows. For each feature that applies to the task type (row count, class balance, hard-negative ratio, input and output lengths, answer-key diversity) it marks your value below the cohort's 25th percentile, above its 75th, or ok, and suggests a fix where it can, such as generating more rows with a paraphrase playbook when you are below on row count. (Source: backend/app/services/archetype_service.py.)

    The hardware auto-tuner (the Hardware auto-tuner button under More options → Training presets) works from the other end: pick the hardware you will deploy on (a short list from a Raspberry Pi to an 80 GB datacenter GPU) and it suggests a base model, quantization bits, LoRA rank and batch size from fixed VRAM tiers. Apply sets the base model, turns LoRA on with that rank (alpha twice the rank) and sets the batch size. It is a lookup table, not a measurement, so preflight and the plan still have the last word. (Source: backend/app/services/hardware_service.py.)

    From Track 2

    Remember manually estimating whether a run would fit, then adding gradient accumulation or checkpointing when it didn't? The preflight plan gives each suggested config a rough VRAM-risk level so you can pick the safer one up front. It is a heuristic, not the Track 1.15 arithmetic, so the memory math is still yours to do for a tight fit — but a missing dependency caught here is far cheaper than a crash an hour into training.

    Errors block, warnings don't

    There is one rule, no modes. Errors block: the launch raises "Training preflight failed: …" and nothing is dispatched until they are cleared. Warnings never block: they are shown, and the run proceeds. A preflight failure stops before dispatch and emits no RunEvent; the training / training_dispatch_error RunEvent is for a different case — preflight passed, and handing the run to the runtime then threw.

    Key idea

    Preflight is the check you never ran by hand: base-model, config, dependency, runtime and data checks that return errors and warnings before spending compute — the readiness line on Train, the full result and its plan under More options → Checks. Errors block; warnings don't. The trainability forecast under Plan and gaps is separate advice about whether the run will pass its gates. Catch the problem on paper, not at step one.

    Key terms

    Preflight
    Stage 07: pre-run checks returning ok, errors, warnings and hints; shown as the readiness line on the Train form.
    trainability forecast
    A separate, advisory check under Train → More options → Plan and gaps: from data signals, is the run likely to pass the default gates (likely pass / borderline / likely fail)?
    VRAM risk
    A low / medium / high heuristic (cpu when no CUDA device is detected) the preflight plan attaches to each suggested config. It does not compare GB with VRAM and never blocks.
    errors vs warnings
    Preflight errors block the launch; warnings never do. There are no strict / fail-open modes.
    archetype comparison
    Your data's features against the 25th–75th percentile range of your successful projects of the same task type (template stats while you have fewer than three).
    hardware auto-tuner
    A lookup from target hardware to a suggested base model, quantization, LoRA rank and batch size (More options → Training presets).
    preflight plan
    A separate call that returns safe / balanced / max_quality suggested configs, each with its own preflight and VRAM risk, plus a recommended_profile.
