    Build a SQL injection classifier with a small language model

    By the end of this tutorial you'll have a binary classifier that flags SQL-injection-shaped queries in milliseconds, deployable inline before your database layer. It runs on a single small GPU (or CPU), costs nothing per query at inference, and — unlike a regex stack — generalises to injection patterns it has never seen because it's a language model, not a string matcher.

    Level: intermediate Time: ~2.5 hours total (most of it answer-key curation, which is the work that matters) Prerequisites: Tutorial 1 (Support FAQ) for the workflow shape, Task shapes for the classification framing Verified: 13 Nov 2026

    Before you start

    This tutorial assumes BrewSLM is running locally at http://localhost:5173 with an admin user signed in. If you haven't done that yet, complete Tutorial 0 — Set up BrewSLM and your first project first. It takes ~20 minutes and is the prerequisite for every tutorial in this track.

    You'll also want, before you start: ~100 injection samples (the OWASP / payloadbox payload list is fine) and ~200+ benign queries mined from your own application logs. The benign queries are the harder part to get right — that's the work this tutorial focuses on.

    Terms you'll see in this tutorial (click to expand)
    Recipe
    The training-plan template behind a project. For this tutorial: classification (shown in the app as the task type Text Classifier / Classification). Defines the base model + adapter + pass/fail-rule defaults for binary/multi-class text classification.
    Answer key
    BrewSLM's name for the gold set — the trusted, human-checked rows every run is scored against. It lives under Data → Labels (the Answer key card). This tutorial says "answer key" for the thing in the app and "gold" for the idea.
    Classification head
    A small dense layer the platform adds on top of the base model's hidden state to predict a label from a fixed vocabulary. For SQLi: two output classes (injection, benign).
    Hard negative
    An input that LOOKS like the target class but is labeled as the OTHER class. For SQLi: a benign query that contains injection-flavoured tokens (quote marks, OR, comments, SELECT). The single most important data type for a security classifier.
    Hard negatives playbook
    BrewSLM's synth generator for confusable rows (mode id hard_negatives). Asks a data-writer model to generate inputs that look like the target class but should be labeled as the other class. The target is the answer key's largest class; the Playbooks panel has no picker. How often the classifier wrongly blocks legitimate input depends heavily on rows like these.
    Macro-F1 / per-class floor
    Eval gates that catch class-starving failure modes. Macro-F1 averages per-class F1 equally (no majority-class bias). A per-class floor requires one class to hit a precision, recall or F1 threshold on its own. For SQLi you'll add a benign recall floor: 1 − benign recall is the share of legitimate queries the model would block.
    Adversarial test set
    A small (~50 row) held-out test dataset the model never sees during training, filled with intentionally-hard inputs (obfuscated injections, unicode tricks, WAF-bypass patterns). Tests generalisation, not memorisation.
    Stratified split
    Train/val/test split that preserves the per-class ratio across all three sets. Essential when classes are imbalanced — random split can produce val sets with no minority-class examples.
    Shadow mode
    Deployment pattern where the classifier runs in production but its verdict is logged-only, not acted-on. Used to measure real-world false-positive rate before wiring the classifier to block.

    This is BrewSLM's canonical workflow for a binary classifier deployed inline as a security control. The use case is SQL injection but the recipe shape generalises: command injection, XSS payloads, prompt-injection on LLM inputs, suspicious file uploads, abuse-language flagging — anything where you need a fast yes/no on a piece of text before letting it through. The bones are the same; only your gold set changes.

    The end state is the model you'd actually run in production at a B2B SaaS: small enough to deploy in front of every database call without adding network hops, accurate enough to catch novel injection variants, and honest enough about false-positive cost that legitimate dynamic SQL doesn't get blocked.

    What you'll build

    A binary text classifier with two output labels:

    • injection — the input looks like an attempt to manipulate the SQL query (union-based, boolean-blind, time-blind, stacked queries, comment-leak, …).
    • benign — the input is normal user-supplied data, even if it contains SQL-flavoured tokens. "O'Brien" in a last-name field is benign. "' OR 1=1 --" is not.

    The model is a fine-tuned LoRA adapter on top of SmolLM2-135M-Instruct running in milliseconds per query on a single GPU and tens of milliseconds on CPU (a rough guide; measure on your hardware). Inline-deployment-friendly: you can wire it as middleware between your application layer and your database calls without users noticing the latency.

    Key idea

    A SQLi classifier lives or dies on its false-positive rate — blocking a legitimate query is more visible than missing a malicious one (you have a WAF and a parameterised-query culture for the second). The training drill that matters most is the hard-negatives playbook: queries that look injection-shaped but are legitimate. Get this right and the rest is easy.

    Why a small model (not regex, not a frontier model)

    Three options exist for inline SQLi detection. Use this comparison:

    ApproachDetection qualityLatencyCostPrivacy
    Regex stack (ModSecurity, libinjection)Misses novel obfuscation; high FP on creative legitimate inputSub-millisecondFreeSelf-hosted
    Frontier LLM via APIExcellent on novel patternsSeconds, plus queueingA fee on every query: at an illustrative $0.003-0.02 per query, a steady 100 qps is about $0.8M-5.2M/month (10k qps would be about $78M-518M)Every query leaves your network
    Small fine-tuned classifier (this tutorial)Good on novel patterns + low FP if you curate hard negativesMilliseconds (GPU) to tens of milliseconds (CPU)No per-query fee; you pay for your own GPU or CPU time (high qps needs batching or several replicas)Self-hosted

    The latency entries are rough orders of magnitude, not measurements; yours will differ. Regex catches the textbook attacks but misses obfuscation; a security team that's been bitten by a creative payload knows this already. Frontier-LLM is good at detection but the latency makes it impossible to deploy inline — and shipping every user query to a third-party API is a non-starter for most enterprise deployments. Small fine-tuned models occupy the gap.

    Choose your dataset

    You need two things: injection samples (the positive class) and benign queries (the negative class — the harder part to get right). The positive class is well-served by public data; the negative class needs YOUR application's traffic to be useful.

    Injection samples (positive class)
    The OWASP / payloadbox payload list ships ~3000 SQLi variants — union-based, error-based, blind, stacked. The Kaggle sql-injection-dataset adds another ~30k labeled rows. Together they cover the textbook attack space and most of the published obfuscations.
    Benign queries (negative class — the work)
    Mine your own application logs. Real user-supplied strings from your form fields, search boxes, comment threads, and URL parameters. The model needs to learn that "O'Brien", "3 OR 4 cars", "WHERE can I find …", "please select * from menu" are all benign even though they contain SQL-flavoured tokens. Public benign-query corpora exist but they're sanitised; your own users produce weirder strings.
    Adversarial held-out set
    Build a small (~50 row) red-team set the model NEVER sees during training. Mix obfuscated injections (hex encoding, comment-splitting, char-by-char), unicode tricks, and known WAF-bypass patterns. Score against this separately at eval time so you know how the model generalises.

    Class ratio realism

    In production, your traffic is >99.9% benign. Training on a 50/50 split is fine for learning the boundary, but precision measured on a balanced test set does not transfer: precision depends on how common each class is. Worked example: at 0.1% injection prevalence, a model with injection recall 0.95 and a 1% false-positive rate has injection precision 0.00095 / (0.00095 + 0.00999) ≈ 8.7%, so most of its blocks are false alarms, while the same model on a 50/50 test set shows ≈ 99%. Gate on the prevalence-free numbers (benign recall, which is 1 − the false-positive rate, and injection recall), then re-estimate precision at your production base rate. Probabilities learned on balanced data are also too high for a 99.9/0.1 prior, so pick the blocking threshold in shadow mode, not from the test set.

    Ingest and map

    In BrewSLM, create a new project: Projects → + New Project, give it a name and describe the job in What problem do you want this model to solve? ("flag SQL-injection-shaped input as injection or benign before it reaches the database"). The project opens on its Overview. The task shape is confirmed on Data → Labels → What kind of task is this? — a text,label file is usually detected as Classification; if not, Change and pick it (Train → More options → Task type → Text Classifier → Use this task type is the same switch). Confirming sets the adapter (classification-label) and task profile (classification). The recipe's pass/fail rule set is only a draft at this point: until you click Use scaffold (see Evaluation), runs are scored against the general default rule set (accuracy ≥ 0.5, macro-F1 ≥ 0.5).

    Open Data → Sources → Import dataset (auto-mapping) → Import dataset →. The wizard walks Source → Task type → Map → Preview & Confirm. Your CSV should look like:

    text,label
"' OR 1=1 --",injection
"O'Brien",benign
"admin' UNION SELECT user, pass FROM users --",injection
"3 OR 4 cars",benign
"1 AND SLEEP(5) --",injection
"WHERE can I find the export menu?",benign

    Two columns: text (the input to classify) and label (one of injection / benign). The wizard's Map step proposes the columns and Preview & Confirm shows the accepted sample rows; click Import N row(s) to project once the labels look right.

    ✓ Checkpoint: Data → Sources lists the import (Details → Sources summary shows the row count). The per-class picture lives on Data → Labels: Answer key diagnostics under the Answer key card shows the share per label and the entropy of the key in nats (a perfectly balanced binary key reads ln 2 ≈ 0.69; the dashed 15% line is the floor Coach uses to flag an under-represented class), and Data → Split → Details → Data health and leakage flags imbalance in the training rows. If a class sits under the line, the Balance class distribution playbook becomes the priority before any training. (The Readiness overview ledger under Data → Sources → Details does not check balance: its data_ready row only needs 50 training rows in total.)

    Label normalisation

    Make sure your label vocabulary is exactly injection and benign — not SQLi / Benign / positive / 0 / 1. Every distinct label string becomes its own class of the head; mixing capitalisation or synonyms during training splits one class into near-identical ones, shows up as model "uncertainty" between them and tanks macro-F1.

    Cleanup and class-balance check

    Open Data → Prepare (its Details → Quality and safety section runs the PII, toxicity and leakage scans) and, once you have generated rows, Data → Generate → Details → Synthetic quality. Key checks:

    • Class balance. Answer key diagnostics (Data → Labels) shows the per-class share + entropy of the key; Data health and leakage (Data → Split → Details) flags imbalance in the training rows. Aim for both classes near 50% — the 15% line is where Coach starts warning. The Readiness overview ledger won't catch this for you; its data_ready row counts rows, not classes.
    • Duplicate detection. Many public SQLi corpora ship near-duplicates ("OR 1=1" and "OR 1=1 --" are functionally identical). Drop one. The near-duplicate signal in Data health and leakage catches these, and Data → Prepare's one-click autofixes (dedupe, near-duplicate dedup) apply the fix — review one cluster at a time.
    • PII in benign queries. Your application logs may contain user-submitted emails, names, phone numbers. Decide your policy: redact (preserve shape: name@domain.tld → X@X.X) or drop. Data → Prepare's Redact PII & Secrets checkbox redacts per field when you run Clean All Documents; whether a redacted query is still a useful benign example is your call per row.
    • Encoding hygiene. Strip BOMs, normalise quotes (smart quotes vs straight quotes are a real source of false-positives), normalise whitespace. The classifier doesn't need to learn that " and " are the same character.

    Domain packs (the security gap)

    BrewSLM doesn't ship a security-domain pack. It ships one generic domain pack (general-pack-v1, under Settings → Tools → Domain Packs); the domain-specific pieces are the Domain preset choices in the create dialog's Advanced options (Legal, Customer Support, Healthcare, Finance) and the matching domain eval packs. All of them are content domains, not threat domains. For SQLi you're operating on platform defaults, which is fine.

    Building a custom security pack is a worthwhile follow-up project that this tutorial intentionally doesn't cover. It would bundle: stricter per-class floors (benign recall 0.99+), curated obfuscation patterns for the hard-negatives playbook, a glossary that links the eval-pack gates to the relevant OWASP top-10 entry, and an Academy tag pointing at this tutorial. If you're shipping this to a security team that uses the platform across multiple projects (XSS classifier, prompt-injection classifier, etc.), packaging the conventions as a domain pack pays back fast.

    Build the answer key (gold set) — hard negatives are the work

    The answer key — BrewSLM's name for the gold set, under Data → Labels → the Answer key card — is where this tutorial diverges most from tutorial 1. The same curation applies to the training rows you import. For a SQLi classifier:

    Positive class (~150 rows)

    Start with the OWASP / payloadbox payload list. Manually pick rows that span every category:

    • Classic union: ' UNION SELECT user, pass FROM users --
    • Boolean-blind: 1' AND (SELECT SUBSTRING(@@version,1,1))='5' --
    • Time-blind: 1; WAITFOR DELAY '0:0:5' --
    • Stacked: 1; DROP TABLE users --
    • Error-based: 1' AND extractvalue(1,concat(0x7e,version())) --
    • Obfuscated / encoded: 1' OR 1=1/**/--   1%20OR%201%3D1--
    • Second-order / out-of-band: 1; load_file('/etc/passwd') --

    Pick ~25 rows from each category. Diversity beats volume; 150 well-chosen positives is enough for the model to generalise.

    Negative class — focused on hard negatives (~250 rows)

    This is where the classifier is born or buried. Easy negatives ("hello", "thank you", "my email is foo@bar.com") teach the model nothing useful — the regex stack already gets these right. The interesting work is in hard negatives: legitimate inputs that look like injection attempts. Mine your own logs for:

    • Names with apostrophes: "O'Brien", "D'Arcy", "Iro's", "L'Oreal"
    • Quoted strings in free-text: "He said 'never trust user input' -- the comment marker IS the attack signature; the classifier needs to learn context
    • Numbers with OR/AND inside text: "3 OR 4 cars are available", "1 AND 2 makes 3", "8 AND counting"
    • Legitimate dynamic SQL strings: ORM-generated query fragments your devs paste into bug reports — these look exactly like injection attempts because they ARE SQL, just authored by your devs not by an attacker
    • Semicolons in user content: "Send the report; copy the boss" — semicolons are normal punctuation
    • SELECT / FROM as English words: "Please SELECT from the menu", "I want a refund FROM your store"
    • SQL keywords in product names: "WHERE You At?" (an app name), "JOIN our discord"

    Aim for ~250 hard negatives. How much legitimate traffic the model blocks (its benign recall) hinges on these.

    LLM-assisted gold expansion

    For larger imports, use the same "promote from raw" flow from tutorial 1:

    1. Bulk-import a few thousand candidate rows (mixed positive + negative, unlabeled).
    2. Run a teacher model (a local model, or a cloud one behind an API) on the candidates outside the app with a prompt like: "label each row as 'injection' or 'benign'. Return JSONL."
    3. Review the labels before you import them (in a spreadsheet, or a second person re-labels a sample). Imported rows do not go through the Review queue: Data → Sources → Import dataset writes them as accepted, and they train on the next split. The wizard's preview is the only check in the app.

    A teacher run plus a review pass can produce 200 labeled rows in well under the time it takes to hand-label them (a rough guide; yours will differ). Faster than hand-labeling 200 from scratch, slower but more reliable than blind-trusting the teacher's labels.

    Adversarial inputs need human review

    Teacher models will mis-label adversarial inputs — they'll call obfuscated injections benign because the obfuscation hides the attack from the LLM too. Do not skip the review step. Rows from the app's Data → Generate playbooks land pending in the review queue and only train once accepted; the Answer key card's model generation shows you a preview, and the rows you pick are saved straight to the answer key (review them there afterwards). Rows you import skip the queue, so for teacher-labelled imports your own pre-import review is the gate. For security workloads it is the most important piece of process you have.

    Splitting train, validation, test

    Data → Split (the Train / Val / Test Split form) cuts the split when you click Run Split. For classification, two things to get right:

    • Stratified split. Put label in Stratify By Field (optional) so train/val/test all carry the same injection:benign ratio. (With the field left blank the split auto-stratifies by a categorical label anyway and records stratify_auto in the manifest — set it explicitly so you can see it.) On every later re-split tick Keep the current N test examples so new data never moves the test examples into training.
    • Reserve adversarial-only test rows. The 50-row red-team set you curated (see Choose your dataset above) stays OUT of the main split: import it as an external benchmark (Results → Compare → External benchmarks; a text,label file under the project's imports, mapped onto your two labels, leakage-filtered against train + val, scored against any run you pick).

    For 400 rows in total, 80/10/10 produces 320 train / 40 val / 40 test. That's enough — the adversarial benchmark is what catches generalisation failures, not the random-split test examples.

    Generate hard-negative drills

    This is THE most important synth step in this tutorial. Three playbooks matter for a classifier (Data → Generate → Details → Playbooks); for SQLi the headline one is Hard negatives:

    Hard negatives — confusable rows
    Generates rows that LOOK like a target class but are labeled as the OTHER class; the validator drops any row labeled as the target class. The Playbooks panel has no class picker: the target is the answer key's largest class. With this tutorial's key (~150 injection, ~250 benign) that is benign, so a run writes benign-looking queries labeled injection (stealthy attacks). That helps injection recall, but it is not the false-positive drill. For the rows that matter most here — queries that look injection-shaped (quote marks, OR, comments, semicolons) but are legitimate — either make injection the larger class in the answer key before you run the playbook, or write those rows by hand (the gold-set section above shows the shapes). Generate ~60 rows.
    Paraphrase positives — coverage extender
    Vary the wording of injection patterns: alternative obfuscations, different keywords, different injection vectors against the same logical attack. Generate ~40 rows seeded from your manually-curated positive set.
    Balance class distribution — for the imbalance case
    If your answer key is imbalanced (say 100 injections / 30 benigns), this playbook fills the under-represented class. There is no class picker: each run fills the rarest class in the answer key (a Coach notice's one-click action can target a specific class). Optional — only run if Coach or Answer key diagnostics shows class imbalance.

    Open Data → Generate. Pick a Provider (a local model server is the free default; a cloud provider with a key, or any OpenAI-compatible endpoint, also works) and Model Name, then open Details → Playbooks: run Hard negatives first with Target rows 60. Generation runs as a background Job; the notification bell tracks progress.

    Run Hard negatives BEFORE Paraphrase positives

    Hard negatives (generated, or written by hand for the benign side — see above) are where your accuracy lives; do them first, review them, fix any prompt drift. Paraphrase positives is a coverage extender — useful but secondary. Balance class distribution is a corrective, used only if the class shares are off. Doing them in the wrong order means you'll be reviewing easy positives while the hard negatives that actually matter haven't been generated yet.

    Review the synth queue

    Every generated row lands pending in the Review queue (Data → Generate → Details → Review queue: tick rows, then Accept selected / Reject selected; the Review queue under Data → Labels → Details groups them by the playbook that produced them, with Accept all / Reject all per group). The classification hard-negatives playbook is the highest-stakes review pass you'll do — each accepted row teaches the model what NOT to flag, so accidentally accepting a mis-labeled row gets baked into a false-positive regression you'll see only when production traffic hits.

    Per-row actions:

    • Accept — the row joins training. For hard negatives: only accept if you can articulate why this string would fool a regex but is legitimate. "Looks confusing" is not a reason; "ORM-generated SELECT in an error message" is.
    • Reject (soft) — the row is marked rejected and stays on disk for audit. The queue has no field for your own reason tags: Reject selected records no reason, and the only reasons are the review assistant's assist:<code> codes, set when you reject a whole group under Group by → Verdict + reason. Keep your own notes (e.g. "actually an injection") outside the app if you need them.
    • Purge this reason — periodically clear the rejected pile, one reason bucket at a time (the no-reason bucket or an assist: code). For SQLi specifically, don't purge rejected hard negatives that were really injections without a second person reviewing — those rows are evidence of a teacher-model failure mode worth keeping.

    Expect to reject a large share of generated hard negatives on first pass (a rough guide, not a measured number). The playbook prompt can't be edited in the app; the acceptance rate climbs as you improve the answer-key rows it is seeded from, or switch to a stronger data-writer model.

    Training configuration

    Open Train. It is one form — Base model (+ Browse), Task, Seeds (One run / Three seeds), Run name, a readiness line and the Train button (a confirm dialog shows the resolved config, then Launch). The knobs below live under More options → Model and hyperparameters (epochs, batch size, learning rate, Task Type) and LoRA and advanced training. The defaults are sensible, and the confirm dialog shows the values it resolved for your data:

    Base model
    HuggingFaceTB/SmolLM2-135M-Instruct. The classification head sits on top of the base model's hidden state; LoRA's target_modules default is auto, which on a model this small adapts all linear layers. Alternative: distilbert-base-uncased for marginally better accuracy at higher latency (encoder-only models are good at classification; the app trains their heads in fp32 and scores them with a head-only eval).
    Task Type
    More options → Model and hyperparameters → Task Type = Classification. Two output classes (injection, benign) are inferred from your rows' label vocabulary. The head is a single dense layer initialised from scratch and trained alongside the LoRA.
    Learning rate
    2e-4 (the default). There is one learning rate for the whole run; the app has no separate learning rate for the classification head.
    Epochs
    Auto. With auto epochs on (the default) the app aims for about 200 optimiser steps and sets epochs and gradient accumulation from your row count: 320 training rows at batch 4 gives accumulation 1 and 3 epochs. Turn auto off under More options if you want to set epochs yourself.
    Batch size
    4 (the default), with gradient accumulation 4 that auto epochs shrinks to 1 on a dataset this small, so the effective batch is 4. Classification inputs are short (queries, not paragraphs), so memory isn't the constraint; a larger batch is a reasonable override.
    Class weighting
    auto (the default): when the largest class has at least 3× the rows of the smallest, the loss is weighted by inverse class frequency. On a roughly balanced injection/benign set it does nothing.

    Training runs on the Celery worker, so Redis and a worker must be running (see Tutorial 0); without the worker the run reads RUNNING but never makes progress, and without Redis it is marked Failed at hand-off. Expected runtime: minutes on a single GPU, longer on CPU (rough guides, not measured numbers). Watch the training loss + validation metrics in the run's live dashboard in the runs list under the form; if F1 plateaus below 0.80 by epoch 3, Cancel the run and check the labels — it's almost always a labeling consistency problem, not a model problem.

    ✓ Checkpoint: on Train, your run's row shows the live loss sparkline trending down and the validation macro-F1 trending up. By the last epoch you would hope to see val macro-F1 well above the rule set's 0.65 bar (a rough guide, not a measured number). When training completes the bell pings, the automatic lift check scores the run, and Results → Verdict shows the summary card ("Accuracy x on the test examples" for an encoder classifier, the lift against the base model otherwise) with the per-class numbers in the scorecard below it.

    Read the trainability forecast

    Before training, the trainability forecast (Train → More options → Plan and gaps, "Predicted gate-pass: ~N%"; the same number is the predicted_pass row of the goal ledger on Data → Sources → Details → Readiness overview) gives you a forecast based on row count, class balance, and base model size. For SQLi specifically:

    • Predicted pass probability ≥ 70%. Lower means your answer key is too thin OR your hard negatives are too similar to each other (low diversity).
    • Data ready = met. The ledger's rule is only 50 training rows in total, with no per-class check, so also look at the forecast's class-balance signal and Answer key diagnostics yourself; a class with far fewer rows than the other tends to under-fit.
    • Goal ledger's gold_set row at ≥ 100%. The target is 100 answer-key rows, and any count below 100 adds a blocker; for classification you can go higher (300-400).

    If the forecast is below 50%, expect the per-class rules to fail, on the test examples or later on real-world traffic. Spend the extra hour curating hard negatives instead of training. The single biggest predictor of a successful SQLi classifier is the quality of the hard-negative pile, not the training config.

    Evaluation with per-class floors

    After training, the automatic lift check scores the run and Results → Verdict shows the Pass/fail rules card (rule set, PASS/FAIL, the required rules that failed).

    Which rule set am I scored against?

    Each project's pass/fail rules come from one rule set (an eval pack). BrewSLM takes the first of these that applies:

    1. The rule set chosen for the project. Clicking Use scaffold saves the drafted rules and makes them the choice (evalpack.project.scaffolded). Picking a built-in pack, such as evalpack.quality.strict or evalpack.domain.legal, or applying a pipeline recipe also sets it.
    2. The domain profile's thresholds (evalpack.domain-profile). Every project resolves a profile, at least the platform default generic-domain-v1, so with nothing chosen this is the rule set: F1 ≥ 0.65, LLM-judge pass rate ≥ 0.75 and safety pass rate ≥ 0.90 are required; exact match ≥ 0.55 is reported but not required.
    3. evalpack.general.default, only for a profile with no thresholds: accuracy and macro-F1 ≥ 0.5 for classification; exact match ≥ 0.4 and F1 ≥ 0.5 for instruction tasks.

    A scaffold is a draft until you click Use scaffold. The task type (recipe) only shapes that draft; for classification it proposes macro-F1 ≥ 0.65, accuracy ≥ 0.70 and per-class F1 ≥ 0.50.

    Two neighbours are easy to mix up with a rule set:

    • A domain preset picked at project creation (Legal, Customer Support, Healthcare, Finance) sets the base model, adapter defaults and an export gate, which decides whether export must pass the rule set. It does not choose the rule set.
    • A domain pack (the only built-in one is general-pack-v1) carries defaults such as the split ratios and a default profile. Packs apply live: editing one changes every project that uses it, so duplicate a pack before you edit it.

    To see which one is active, look at the Pass/fail rules card in evaluation: it names the Active Pack and its Source, for example "domain profile default".

    For this project: until you click Use scaffold, the run is scored against the domain profile's rule set (evalpack.domain-profile: F1 ≥ 0.65, LLM-judge pass rate ≥ 0.75 and safety ≥ 0.90 required, written for free-text answers), not the classification rules below. Review the scaffold's thresholds on Results → Failures, add the SQLi rule below, then click Use scaffold; the next eval uses it.

    The classification scaffold has four rules; three are required:

    Macro-F1 ≥ 0.65 (required)
    Average of per-class F1s. Catches the failure mode where the model is great at the majority class and bad at the minority class — flat accuracy alone won't surface this on a 99/1 split.
    Accuracy ≥ 0.70 (required)
    The overall share of correct labels. On its own it hides a starving class; that is what the other rules are for.
    Per-class F1 floor ≥ 0.50 (required)
    Every class must hit at least 0.50 F1 individually. For SQLi: injection F1 ≥ 0.50 AND benign F1 ≥ 0.50 — neither class is allowed to starve. For a security control you will likely raise these thresholds; that is your override, not the default.
    Safety pass rate ≥ 0.93 (optional)
    Catches refusal / off-topic / adversarial inputs that should be flagged through a different path. Optional gate but useful when you wire the model behind a SOC dashboard.

    Add one SQLi rule: benign recall. Blocking a legitimate query means a benign input was predicted injection, so the share of legitimate traffic you block is 1 − benign recall (the false-positive rate). Benign precision measures something else: the share of the traffic the model let through that really was benign, so 1 − benign precision is the share of passed traffic that was a missed attack. In the scaffold panel click + Add rule, pick Per-class · benign → Recall in the Metric dropdown (the per-class groups populate from your latest classification eval; if they're empty, run an eval first to discover classes), set operator ≥, threshold 0.99 (block at most 1% of legitimate queries), tick Required, then Use scaffold. A model with benign recall 0.92 blocks 8% of legitimate traffic — usually unacceptable. Per-class · injection → Precision is in the same dropdown and tells you how many blocks are false, but remember it depends on the base rate (see Class ratio realism).

    The scorecard under the Pass/fail rules card on Results → Verdict lists every rule with its value and threshold so you see exactly which class is starving and which rule is failing.

    Run the adversarial eval

    The 50-row red-team set you curated lives as an external benchmark (Results → Compare → External benchmarks). Score each run on it — Score this run (later Re-score) on its row; the result also shows as a benchmark line on the Verdict card — alongside the test examples, so you read two numbers with different bars:

    • Test examples: your saved rule set (macro-F1 ≥ 0.65 in the scaffold, or the higher bar you set; random split — checks the model isn't overfit to its training rows)
    • Adversarial benchmark: macro-F1 ≥ 0.65 (a bar you hold it to by eye — these are intentionally hard; you want to know whether the model generalises, not whether it solves them all)

    The two scores in concert tell you different things. High main + low adversarial = the model memorised its training rows. High both = the model generalises. Low main = something is broken in the training pipeline, not the data.

    Update the adversarial set quarterly

    SQLi tactics evolve. WAF-bypass research publishes new obfuscations every few months. Plan to refresh your adversarial test set 4x a year by adding ~10 rows from recent attack-research write-ups. The training set can stay stable; the adversarial set is your tripwire on novel patterns.

    When the eval fails

    Common SQLi-specific failure patterns and the fix for each:

    SymptomRoot causeFix
    Macro-F1 strong (0.90+), benign recall 0.85Hard negatives too easy or too few — model defaults to flagging anything quote-shaped, so it blocks legitimate inputAdd 100+ harder negatives. Mine new ones from your most active form-field columns and write them by hand (or make injection the larger class in the answer key before re-running Hard negatives, as above: with benign the larger class it writes benign-looking injections instead).
    Injection precision 0.95+, injection recall 0.70Model is too conservative — misses novel injection variantsAdd obfuscated injection examples to the gold set (hex-encoded, comment-spliced, second-order). Run Paraphrase positives for variant coverage.
    Both classes < 0.75 F1Answer key is too small OR has labeling inconsistencySample 50 random answer-key rows; have a second reviewer re-label without seeing the original. Disagreement > 10% = labeling problem. Reconcile and re-train.
    Adversarial benchmark F1 below 0.50 despite main > 0.85Model memorised its training rows; doesn't generaliseAdd more diverse data first (obfuscation variants, second-order patterns) — more training on the same rows deepens the fit. A larger base model is a later lever.
    Per-class rules pass but model flags 5% of production trafficTrain-test distribution mismatch — your test set's benign queries don't reflect production trafficCapture 1000+ real production queries, label them (10% sample by hand, rest via teacher), re-run eval against this realistic test set BEFORE shipping.

    Ship inline

    Three deployment patterns for SQLi classifiers, from least to most risky:

    Shadow mode (recommended first)
    Deploy the classifier; log its verdict on every incoming query; do not act on the verdict. Run for two weeks. Compare flagged queries to what your existing controls (regex / WAF / manual review) caught. Set the threshold from the false-positive rate and precision you actually see on YOUR traffic, not your test set.
    Tee-mode (analyst tooling)
    Surface the classifier's verdict in your SOC dashboard alongside the existing detection chain. Analysts see the small-model opinion as a "second eye"; queries flagged by the model but not by regex go to a review queue. This is high-value with zero false-positive risk.
    Inline blocking (after shadow-mode tuning)
    Wire the classifier as middleware between your application and database. Queries flagged with confidence > 0.85 get blocked; the user sees a generic "input rejected" page. Only do this AFTER shadow mode has proven the false-positive rate on YOUR traffic.

    Export on Ship → Package → New export: pick the run, Format HuggingFace (the weights; a LoRA run is merged into its base at export, keeping the classification head), quantization and deployment targets, then Run Export. (ONNX and GGUF (CPU) package only a compressed model, so they need Ship → Package → Options → Compress first on this run before the export; Docker adds a Dockerfile and a serve.py, but that serve.py is a generic text-generation template and does not serve a classification head.) The export appears in the Exports table and on disk under DATA_DIR/exports/<project id>/<export id>/run-<timestamp>/; Ship → Deploy holds the serve / deploy plans for the targets you ticked, and Ship → Publish pushes a HuggingFace export to the Hub. Smoke-test first on Results → Try it (Provider = Trained run (this project); a classifier run replies with the predicted label).

    For inline deployment, wrap the exported classifier in a thin HTTP service that fronts your DB layer — POST /classify with the text, back comes the label and its probability. The core of it loads the export's model/ folder as a sequence classifier:

    import torch
from transformers import AutoTokenizer, AutoModelForSequenceClassification

tok = AutoTokenizer.from_pretrained("./model")
model = AutoModelForSequenceClassification.from_pretrained("./model", dtype=torch.float32).eval()

def classify(text: str) -> tuple[str, float]:
    with torch.no_grad():
        logits = model(**tok(text, return_tensors="pt", truncation=True)).logits
    probs = logits.softmax(-1)[0]
    i = int(probs.argmax())
    return model.config.id2label[i], float(probs[i])

print(classify("' OR 1=1 --"))

    Latency is milliseconds per query on a GPU and tens of milliseconds on CPU for a model this size (a rough guide; measure on your hardware). The classifier itself does the heavy lifting; your service handles auth, threshold tuning, and the block-or-allow decision.

    Defense in depth, not replacement

    This classifier is one layer. Keep your parameterised queries, your prepared statements, your principle of least privilege. The classifier catches what gets past the rest; it is not a substitute for the rest. Any deployment plan that turns off existing controls because "the model handles it now" is the deployment plan that ends up on a post-mortem.

    What's next

    You have a deployed SQLi classifier with thresholds tuned on your own traffic. Three next moves:

    Active-learning loop from production
    Every shadow-mode disagreement (classifier flags but WAF doesn't, or vice versa) is a high-signal training example. Capture them; have analysts review the disagreements; add the confident-correct ones to the training rows and the answer key. Retrain when the key grows by ~100 rows. Over a quarter, the classifier gets noticeably sharper on your traffic specifically.
    Generalise to adjacent threat classes
    The same recipe + workflow works for: XSS payload detection (binary classifier on user-supplied HTML/JS), command injection (on inputs to shell wrappers), prompt-injection on LLM inputs, abuse-language flagging. New gold set; same training pipeline. The classification recipe is more general-purpose than its name suggests.
    Build a security domain pack
    Package the conventions you've established here — per-class floors and rule-set overrides — into a custom security domain pack (Settings → Tools → Domain Packs). Future security classifier projects inherit the conventions instead of re-establishing them each time.

    The next tutorial picks a different recipe: invoice field extraction with the span-extraction recipe — structured output, JSON-schema gold sets, and the structured-extraction eval handler's validity diagnostics. Same end-to-end workflow shape; another platform path.

    Key terms

    Hard negative
    An input that LOOKS like the target class but is labeled as the OTHER class. For SQLi: a benign query that contains injection-flavoured tokens (quote marks, OR, comments). The single most important data type for a security classifier.
    Per-class floor
    A gate that requires one class's precision, recall or F1 to meet a minimum threshold on its own. Catches the failure mode where the model is great on the common class and silently bad on the rare class. For a blocker, benign recall is the rule that caps how much legitimate traffic you block.
    Adversarial held-out set
    A small test dataset of intentionally-hard inputs the model NEVER sees during training. Score against this separately to know whether the model generalises beyond its training distribution.
    Shadow mode
    Deployment pattern where the classifier runs in production but its verdict is logged-only, not acted-on. Used to calibrate the threshold and measure real-world false-positive rate before wiring the classifier to block.
    Stratified split
    Train/val/test split that preserves the per-class ratio across all three sets. Essential for imbalanced classification — random split can produce val sets with no minority-class examples.
    Macro-F1
    Average of per-class F1 scores, weighted equally regardless of class size. The headline metric for classification eval; catches class-imbalance bugs that flat accuracy misses.
