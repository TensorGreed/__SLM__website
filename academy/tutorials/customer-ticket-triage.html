    Tutorial 4 · End-to-end · Support / Customer Success

    Customer ticket triage with multi-class classification and class imbalance

    By the end of this tutorial you'll have a multi-class classifier that takes the body text of an incoming support ticket and emits the right team label — billing, technical, account, feature_request, bug_report, cancellation — with a confidence score. It runs at ~10ms per ticket on a single small GPU, doesn't ship customer data to a third-party API, and is honest enough about its uncertainty that mid-confidence tickets get shadow-routed for review instead of straight-routed and forgotten.

    Level: intermediate Time: ~2.5 hours total (the bulk is gold-set curation from senior agents' routing decisions — the work that matters) Prerequisites: Tutorial 0 (Setup BrewSLM). Optional context: Tutorial 2 (SQL injection classifier) for the binary-classification shape this tutorial extends, Data quality + splits + class imbalance for the entropy framing.

    Before you start

    This tutorial assumes BrewSLM is running locally at http://localhost:5173 with an admin user signed in. If you haven't done that yet, complete Tutorial 0 — Set up BrewSLM and your first project first. It takes ~15 minutes and is the prerequisite for every tutorial in this track.

    You'll also want, before you start: ~1,000 historical tickets paired with the team that actually resolved them (export from Zendesk / Intercom / Salesforce / Freshdesk as CSV — most ticketing systems ship this in a few clicks). The team-routing labels are the highest-signal training data you have; everything else in this tutorial is about making the most of them.

    Terms you'll see in this tutorial (click to expand)
    Recipe
    The training-plan template you pick when creating a project. For this tutorial: classification — the same recipe as Tutorial 2's binary SQLi classifier, used here for a 6-way (multi-class) label vocabulary instead.
    Multi-class classification
    One label per row, drawn from a fixed vocabulary of more than two classes. Distinct from binary classification (yes/no) and from multi-label (a single ticket might carry two labels at once — not what we're doing here; one ticket, one routing team).
    Class imbalance
    The natural ratio of classes in real-world ticket archives is skewed. Most tickets are technical or billing; feature_request and cancellation are typically <5% of volume each. A naive split + train produces a model that always predicts the majority class.
    Shannon entropy (normalised)
    A single number summarising how balanced your class distribution is: the entropy H divided by its maximum ln(k) for k classes. 1.0 = perfectly balanced; 0.0 = a single class dominates. Answer key diagnostics (Data → Labels) shows the raw entropy of the answer key in nats; the trainability forecast shows the normalised value as "balance X of 1.00".
    Balance class distribution playbook
    BrewSLM's synth generator for fixing class imbalance (mode id class_balance_fill). Each run picks the rarest class in your gold set (the answer key in BrewSLM) and generates more examples of it; the playbook form has no class picker. Distinct from Paraphrase positives, which paraphrases existing rows in proportion to current counts.
    macro_f1
    Average of per-class F1 scores, weighted equally regardless of class size. The headline classification eval metric — catches the imbalance bug where the model is great at the majority class and silently bad at the rest.
    Per-class F1 floor
    Eval gate that requires every individual class's F1 to clear a threshold. Catches the failure mode where one class is starved of training signal and macro_f1 is dragged down by it.
    Confidence threshold
    A floor on the model's predicted probability below which the deployed router declines to auto-route. The two-threshold pattern: high-confidence routes auto, mid-confidence shadow-routes (predicted team, flagged for review), low-confidence goes to a triage-manager queue.

    This is BrewSLM's canonical workflow for a multi-class text classifier deployed on a routing path with natural class imbalance. The use case is customer ticket triage but the recipe shape generalises: bug-report categorisation, internal helpdesk routing, document type classification on a scanner ingest, alert-to-team routing in an SRE pipeline — anything where one piece of text needs one label drawn from a finite vocabulary, and the natural distribution isn't uniform. The bones are the same; only your label vocabulary and your historical-labels source change.

    The end state is the model a support-ops team would actually run in production: small enough to run on the queue worker that already pulls tickets off your ingest, accurate enough on the busy classes to remove a measurable load from human triage, and well-calibrated enough on the rare classes that cancellation and feature_request tickets stop getting buried in the technical queue.

    What you'll build

    A six-way text classifier. Given the body text of an incoming ticket, it emits one label plus a confidence score. Sample inputs and outputs:

    INPUT:  "My credit card was charged twice for this month's subscription —
         can you refund the duplicate?"
OUTPUT: { "label": "billing", "confidence": 0.97 }

INPUT:  "The desktop app crashes on launch after the latest update.
         Logs attached."
OUTPUT: { "label": "bug_report", "confidence": 0.91 }

INPUT:  "Please cancel my account effective immediately. I don't want
         to be billed for next month."
OUTPUT: { "label": "cancellation", "confidence": 0.94 }

INPUT:  "Would love a dark mode in the mobile app — any plans?"
OUTPUT: { "label": "feature_request", "confidence": 0.88 }

INPUT:  "I can't log in. Forgot my password and the reset email
         never arrived."
OUTPUT: { "label": "account", "confidence": 0.83 }

    The model is a fine-tuned LoRA adapter on top of SmolLM2-135M-Instruct running at typical 5-15ms per ticket on a single GPU, 30-60ms on CPU. Latency-friendly enough to sit inline on the ticket-ingest path; small enough to deploy onto the same machine that already runs your queue workers.

    Key idea

    Multi-class triage on a natural ticket stream lives or dies on the rare classes. Macro_f1 — the headline metric — averages per-class F1 equally regardless of class size, so a model that aces technical and billing but never predicts cancellation scores around 0.65 and fails the gate. The training drill that matters most is getting more rare-class rows — real tickets first, then the Balance class distribution playbook — until the normalised Shannon entropy of your gold set crosses a healthy threshold. Get this right and macro_f1 usually follows.

    Why a small model (not rules, not a frontier API)

    Three options exist for ticket triage. Use this comparison:

    ApproachRouting qualityLatencyCost at 50k tickets/monthPrivacy
    Keyword rules ("refund" → billing, "crash" → bug)Brittle — fails on intent overlap ("the technical team should refund this") and on tickets that don't surface the keyword at all<1msFree (but a full-time PM to maintain the keyword list as labels evolve)Self-hosted
    Frontier LLM via APIExcellent on novel phrasing1-3 seconds per ticketA per-token fee on every ticket; grows linearly with volumeEvery ticket — with customer names, account numbers, sometimes attached PII — leaves your network
    Small fine-tuned classifier (this tutorial)Good on novel phrasing if you curate balanced gold5-60msNo per-ticket fee; your own GPU or CPU time, shareable across your small modelsSelf-hosted

    Keyword rules were how every support team did this in 2018. They still work for the top-of-funnel obvious cases — but the moment a customer writes "the technical team should fix the billing on my account", the rule stack picks the wrong team. Intent overlap is the rule-stack killer; small fine-tuned models read the semantics, not just the keywords.

    Frontier-LLM-via-API solves the semantics problem but ships every ticket — names, account identifiers, sometimes financial details — to a third-party. For most B2B SaaS support orgs that's a compliance non-starter even before the cost. Small fine-tuned models occupy the gap: semantics-aware like an LLM, fast and self-hosted like a keyword rule.

    Choose your dataset

    You need two things: ticket text and the team that resolved it. Your historical ticket archive is the spine; public datasets are useful for warmup and for stretching template diversity.

    Your own ticket archive (the spine)
    Export 1,000-5,000 recent tickets from Zendesk / Intercom / Salesforce / Freshdesk as CSV: the ticket body and the team that resolved it. The resolving team is your gold label proxy — not perfect (mid-way reassignments are noisy), but the best signal available without manual relabeling.
    Bitext customer-support corpus
    bitext/Bitext-customer-support-llm-chatbot-training-dataset ships 26,872 examples across 27 intents. Useful for warmup; labels won't map 1:1 to your team taxonomy but the phrasing variation is good signal.
    CLINC150
    clinc150 ships 150 intents across 10 domains — useful for testing the end-to-end multi-class workflow before you commit real ticket data.
    Banking77
    banking77 is 13,083 customer-service queries across 77 banking-specific intents. Useful if your B2B product is in fintech and your billing class needs more variety.

    Public data is for diversity, not coverage

    Your archive's tickets are what the model will see in production. Public corpora round out phrasing variety so the model doesn't memorise your top customer accounts' writing style. Treat them as a 10-20% supplement — never the spine. A model trained 100% on bitext will be brilliant at the phrases a synthetic-data team chose and useless on the weird, specific phrasings your real customers actually use.

    Ingest and map

    In BrewSLM, create a new project: on the projects home click + New Project, give it a name and a brief ("Route incoming support tickets to one of six teams: billing, technical, account, feature_request, bug_report, cancellation"), then Create project. On the project's Overview check the task; if it isn't classification, open Train → Task → Change and pick it. The recipe pre-fills the adapter (classification-label), task profile (classification) and scoring mode (field_match). Its rule set (the classification scaffold — macro_f1, accuracy, per-class F1 floor, optional safety pass rate) is only a draft until you click Use scaffold after your first run (see Evaluation); before that, runs are scored against the general default (accuracy ≥ 0.5, macro-F1 ≥ 0.5).

    Open Data → Sources → Import dataset (auto-mapping) → Import dataset →. Your CSV should look like:

    text,label
"My card was charged twice this month — please refund the duplicate.",billing
"App crashes on launch after today's update. Logs attached.",bug_report
"Please cancel my account effective end of month.",cancellation
"Can you add a dark mode to the mobile app?",feature_request
"Forgot my password and the reset email isn't arriving.",account
"The API is returning 502 on /v1/orders intermittently.",technical

    Two columns: text (the ticket body) and label (one of your six team labels). The import wizard shows a confidence-scored preview of the column inference; confirm it once the labels look right. Imported rows are written as accepted training rows straight away (they do not pass through the Review queue), so this preview is your only check. After the import, Data → Labels → "What kind of task is this?" should read a classification shape — confirm it there.

    ✓ Checkpoint: Data → Sources → Details → Readiness overview now shows your imported row count. Do the per-class count yourself (a spreadsheet pivot, or Answer key diagnostics on Data → Labels once the same distribution is in the answer key). Example: technical 1,840, billing 1,210, account 480, bug_report 380, feature_request 92, cancellation 64 gives Shannon entropy 1.34 nats; divided by ln 6 that is a normalised 0.75, right on the trainability forecast's warning line (it warns below 0.75 and blocks below 0.50). Two classes under 3% of the rows is still meaningful imbalance for per-class F1, so more rare-class rows are the priority before any training.

    Label normalisation

    Make sure your label vocabulary is exactly the six strings you want — not billing in some rows and Billing in others, not tech in one batch and technical in the next, not cancel alongside cancellation. Every distinct label string becomes its own class of the head; capitalisation drift and synonyms during training split one class into near-identical ones, show up as model "uncertainty" between them and tank macro_f1 with nothing visible to fix in the eval gates. Run a quick spreadsheet sort + count before import.

    Cleanup and Shannon-entropy diagnostic

    Open Data → Prepare (its Details → Quality and safety runs the PII, toxicity and leakage scans). Four common artefact families to clean:

    • Auto-reply signatures and quoted threads. Email-sourced tickets carry auto-responder banners and quoted earlier replies — high-frequency noise the model will memorise. Strip them before training.
    • Near-duplicates. A customer who fires the same complaint three times generates three near-identical rows. Train on one; drop the rest. The dedup signal catches these.
    • Whitespace + encoding. Strip BOMs, collapse whitespace, normalise smart-quotes. Free quality improvement.
    • PII. Customer names, emails, account numbers leak into ticket bodies. Decide your policy: redact, drop, or hash. Nothing is redacted unless you ask: Data → Prepare's Redact PII & Secrets option redacts when you run the clean. For routing, redaction is usually right — the team choice shouldn't depend on the customer's actual name.

    Then look at the diagnostic driving everything else: Shannon entropy of the class distribution. Answer key diagnostics (Data → Labels, under the Answer key card) shows the answer key's raw entropy in nats plus the share per label; the trainability forecast (Train → More options → Plan and gaps) shows the normalised form H / ln(k) as "balance X of 1.00", also computed on the answer key. The app's bands:

    • Normalised ≥ 0.75 — the forecast calls the distribution healthy. Still check the rarest class's row count.
    • Normalised 0.50-0.74 — the forecast warns ("Class distribution is skewed"). Add rare-class rows (real ones first, then a Balance class distribution pass per rare class).
    • Normalised < 0.50 — the forecast flags severe imbalance as a blocker; don't train yet. Gather more data or balance-fill until you cross 0.75.

    Normalised entropy is one of the most informative numbers on a multi-class triage dataset, but it is a summary: a key can read 0.75 and still have a class with too few rows to score. Check both.

    Pick the recipe: classification or something else?

    The decision tree for ticket triage:

    You want…UseWhy

    For the canonical six-team triage use case: classification. Sticking with it for the rest of this tutorial.

    Domain packs (the support gap)

    BrewSLM doesn't ship a support-domain pack tuned for triage. There is one generic domain pack (general-pack-v1) that any project inherits if you don't pin one. The create dialog's Advanced options offer a Customer Support domain preset, and there is a built-in support eval pack, but both are aimed at free-text support answers (the shape Tutorial 1 covers), not a label classifier. For this tutorial you're operating on the recipe-level defaults plus your own gold set, which is fine for a first project.

    Building a custom support-triage domain pack is a worthwhile follow-up project that this tutorial intentionally doesn't cover. It would bundle: stricter per-class F1 floors on revenue-protective labels (cancellation, billing), curated phrasing seeds for the long-tail intents your team specifically sees, a glossary linking eval gates to support-org SLO language, and an Academy tag pointing at this tutorial. If your customer-success org is shipping multiple triage classifiers (consumer vs B2B, free-tier vs enterprise), packaging the conventions as a domain pack pays back fast.

    Build the answer key — your senior agents are the oracle

    For ticket triage you have a higher-signal oracle than any other tutorial in this series: your senior support agents have already routed tens of thousands of tickets correctly. Their dispositions are your gold labels for free.

    Path A — bootstrap from your ticket archive

    For each historical ticket, pair the body text with the team that ultimately resolved it. Usually a one-time CSV export from Zendesk / Intercom / Salesforce / Freshdesk under analytics → tickets. Two caveats:

    • Mid-ticket reassignments. A ticket that started in technical and was bounced to billing has noisy gold. Simplest filter: only include tickets whose first-assigned team equals their final-resolved team. You lose ~10-15% of volume; you gain confidence that the label is right.
    • Stale labels. Your team taxonomy probably evolved. Restrict your gold pull to the last 12 months unless the taxonomy has been stable longer.

    Aim for 1,500-3,000 labelled rows from your archive — at least 50 examples of every class. Imported through Data → Sources they become training rows (and, after the split, your test examples). The Answer key card adds answer-key rows one at a time; there is no bulk answer-key upload in the UI. For a bulk answer key, the API route POST /api/projects/<id>/gold/import takes {"pairs": [{"text": …, "label": …}, …]}.

    Path B — manual seed from senior agents

    For the rare classes your archive doesn't cover well, ask senior agents to hand-label 30-50 fresh examples each. Their muscle memory is the strongest signal on the ambiguous cases newer agents would have routed wrong. The answer key lives under Data → Labels (the Answer key card; the Answer-key workbench in its Details drawer), with per-row manual entry.

    Path C — LLM-assisted promotion

    For tickets whose archive label is missing or suspect, have a teacher model (a local model, or a cloud one behind an API) pick one of your six labels per row, outside the app. Review those labels before importing them: rows imported through Data → Sources are accepted straight into training and never reach the Review queue. Only rows generated inside the app (Data → Generate playbooks, the Answer key card's LLM generation) land pending for review. Teacher throughput and review time vary a lot; budget review time per row, not per batch.

    ✓ Checkpoint: the goal ledger's answer-key readiness row (Data → Sources → Details → Readiness overview) should now be green ("N answer-key rows ready (≥ 100)"; any count below 100 adds a blocker). Check the per-class breakdown in Data → Labels → Answer key diagnostics (class balance per label, with the 15% floor marked): every class should have ≥ 50 examples. If cancellation sits at 12 rows because cancellations are rare, manual seed + Balance class distribution have to fix that gap before training.

    Don't skip the "ambiguous" examples

    Your gold must contain rows where the routing decision was genuinely hard — tickets that legitimately span two teams. Mark them with the team that actually got the ticket and let the model learn your org's tie-breaking convention. Without them, the model learns a clean separation production doesn't exhibit.

    Stratified split by class label

    The Train / Val / Test Split form on Data → Split runs uniform random off the ratios + a seed you set by default. For multi-class with imbalance, uniform random is fragile: with 64 cancellation rows in a 2,400-row dataset, an unlucky seed will put 4 of them in val and 6 in test, and your per-class F1 on cancellation becomes essentially noise. You want a stratified split — train, val, and test each carry the same per-class ratio as the whole.

    On Data → Split set the Stratify By Field (optional) input to the column holding your team label (e.g. team). (When your rows carry a categorical label and you leave it blank, BrewSLM stratifies by it automatically and the manifest says so.) The split runs as before (80/10/10 default) but groups rows by that field's value first and splits each group at the same ratios independently — the rare cancellation class gets the same ~10% / ~10% slice into val/test that the dominant technical class does. After Run Split, the manifest's "Stratified by" panel shows a per-class breakdown: value, total, train, val, test row counts for each class so you can verify rare classes survived.

    For a 2,400-row gold set with the imbalanced distribution from earlier, an 80/10/10 stratified split produces approximately 1,920 train / 240 val / 240 test where every class has at least 6-7 examples in val + test even on the rarest classes — enough for the eval handler to compute a meaningful per-class F1 instead of a noisy one. Classes with fewer than 3 rows in total get a small-group warning in the report and go entirely to train (can't split < 3 into all three buckets); merge or seed more rows for those classes before relying on their per-class gates.

    If your label column isn't a top-level field

    The Stratify By Field input reads a top-level key on the adapted training record. If your label lives nested under a JSON path (e.g. fields.team), flatten it in the adapter mapping before splitting (Data → Split → Details → Schema mapping, or Train → More options → Adapter Studio), or pre-partition into three CSVs as the fallback. The split manifest's report explicitly flags rows whose stratify value is missing or empty — they bucket as __missing__ so you can spot data hygiene issues immediately.

    Generate balance-fill, paraphrase and hard-negative drills

    Four playbooks matter for a classifier (Data → Generate → Details → Playbooks): Balance class distribution, Paraphrase positives, Hard negatives and Target a failure cluster. For ticket triage, run them in this order:

    Balance class distribution — the headline drill
    Each run picks the rarest class in your gold set and generates more examples for it; there is no class picker in the form (a Coach notice's one-click action can target a specific class). Re-run it once per rare class. Goal: pull your gold's normalised Shannon entropy to ≥ 0.75, the forecast's healthy line. Turns a 30-row cancellation class into 120 trainable examples without hand-writing 90 more tickets. Generate ~50-80 rows per under-represented class.
    Paraphrase positives — coverage extender
    Vary the wording of existing gold rows while keeping the label fixed. The model learns that "could you refund the double charge" and "I want a refund on the duplicate billing" are the same intent. Generate ~50 rows per major class.
    Hard negatives — class-boundary disambiguation
    For triage the most useful hard negatives are tickets that mention a different team but should route elsewhere: "the technical team should fix this billing bug" (mentions technical, is billing); "I'm cancelling because the app keeps crashing" (mentions cancelling, is a bug-report). Generate ~40 rows.
    Target a failure cluster — post-eval drill
    After a first training pass, Results → Failures → Failure clusters groups failures into clusters with a representative example each. The cluster-targeted playbook seeds new training rows from the worst cluster. Don't run this on the first pass — it needs an eval result to operate on.

    Open Data → Generate → Details → Playbooks. Pick Balance class distribution first; set Target rows to 60; leave Backend on Auto (recommended) or pick one (a local model server is the free default). It fills the current rarest class; run it again for the next one. Generation runs as a background Job — the bell tracks it, and Details → Playbook center keeps each playbook's last run.

    Run Balance class distribution before paraphrase

    For an imbalanced multi-class dataset, balance-fill is the precondition for everything else. Paraphrase amplifies whatever shape your gold has — if technical outnumbers cancellation 30:1, paraphrasing the whole gold set preserves that 30:1 ratio (which is exactly what you don't want). Run balance-fill until entropy is healthy, THEN run paraphrase across the now-balanced gold, THEN run hard-negatives on the high-confusion class boundaries you've identified. Order matters more than volume.

    Review the synth queue (bulk by class)

    Every generated row lands in the Review queue (Data → Generate → Details → Review queue) with review_status="pending". The queue groups rows by source playbook; within each you can filter by class — useful after running balance-fill across multiple classes.

    Per-row actions:

    • Accept — the row joins training on the next split. For balance-fill specifically: check the generated example actually fits the target class. A teacher asked for 60 cancellation examples will sometimes produce a good billing complaint mis-labelled cancellation because the prompt anchored on the wrong word.
    • Reject (soft) — marked rejected and kept on disk for audit. The queue has no field for your own reason tags (Reject selected records no reason; the only reasons are the review assistant's assist:<code> codes, set when you reject a group under Group by → Verdict + reason). Reasons worth rejecting for in triage, to note for yourself:
      • reads cleanly as a different class than generated for. Common on balance-fill for rarer classes.
      • one- or three-word "tickets" with no signal. ("Refund please." teaches nothing even if the label is right.)
      • the row legitimately spans two classes. Reject — but write it down: a pile of these may mean your label vocabulary is missing a category.
      • right intent but the teacher used a synonym (cancel instead of cancellation). Reject; the label vocabulary must be exact.
    • Purge this reason — clears one reason bucket of rejected rows (the no-reason bucket or an assist: code). Use once you're confident a bucket is bad data.

    Expect to reject a noticeable share of balance-fill rows on first pass for the rarest classes — the teacher has fewest anchors to learn from (a rough guide, not a measured number). The playbook prompt can't be edited in the app; acceptance climbs as the gold set grows.

    ✓ Checkpoint: after a review pass, the synth panel should show "accepted: 220 · rejected: 80 · pending: 0" or similar. Check the balance again (forecast or Answer key diagnostics) — normalised entropy should now be ≥ 0.75. If it's not, run another balance-fill pass on the still-rarest class.

    Training configuration

    Open Train. The form shows Base model, Task, Seeds and Run name; epochs and batch size live under More options → Model and hyperparameters, the adapter under Adapter Studio. The defaults are sensible — for a first run, accept all of them; the confirm dialog shows the values it resolved for your data:

    Base model
    HuggingFaceTB/SmolLM2-135M-Instruct. A classification project trains a sequence-classification head on top of the base model (one output per label, read off as a softmax probability), not a model that writes the label as text; LoRA's target_modules default auto adapts all linear layers on a model this small. Alternatives: Qwen/Qwen2.5-0.5B-Instruct for marginally better accuracy at 4x the size; distilbert-base-uncased for an encoder-only baseline.
    Adapter
    classification-label. Maps each row's text + label onto the classification record the trainer reads.
    Epochs
    Auto. With auto epochs on (the default) the app aims for about 200 optimiser steps: 1,920 training rows at batch 4 × accumulation 4 gives 120 steps per epoch, so 2 epochs. Turn auto off under More options to set epochs yourself.
    Batch size
    4 with gradient accumulation 4 (effective batch 16 at this size), learning rate 2e-4. Tickets are short (50-300 tokens) so memory isn't the constraint.
    Class weighting
    auto (the default): when the largest class has at least 3× the rows of the smallest — true here, 1,840 vs 64 — the loss is weighted by inverse class frequency. It helps the rare classes but does not replace more rare-class rows.

    Training runs on the Celery worker, so Redis and a worker must be running (see Tutorial 0). Expected runtime: minutes on a single GPU, longer on CPU (rough guides, not measured numbers). The run's dashboard in the runs list below the form shows live loss + validation macro_f1; if macro_f1 plateaus below 0.55 by epoch 3, cancel the run — it's almost always a class-balance or labelling-consistency problem.

    ✓ Checkpoint: the run shows loss trending down and validation macro_f1 trending up. By the last epoch you would hope to see val macro_f1 above the scaffold's 0.65 and per-class F1 above 0.50 on the rarest class (a rough guide). When training completes the bell pings; the lift check against the base model runs on its own and Results → Verdict shows the summary card, with the per-class precision/recall/F1 bars under Results → Failures.

    Read the trainability forecast

    Before training, the trainability forecast (Train → More options → Plan and gaps; also the goal ledger's predicted_pass row under Data → Sources → Details → Readiness overview) forecasts based on row count, normalised class entropy, and base model size. For imbalanced multi-class:

    • Predicted pass probability ≥ 65% (a rule of thumb). Lower often means the class-balance signal fired — fix balance first.
    • Class balance ≥ 0.75 ("balance X of 1.00" in the forecast's class-imbalance line). Below 0.75 it warns; below 0.50 it blocks.
    • Every class has ≥ 50 answer-key rows. Below that the rare class under-trains and the per-class F1 floor fails.

    One nuance: the forecast sometimes over-estimates macro_f1 when the per-class floor is the binding constraint. It knows row count and entropy; it doesn't know that 50 rows of cancellation won't quite teach the model enough to clear F1 ≥ 0.50 on that class. Treat predicted_pass as a green/yellow/red light, not a precise prediction. A balance of 0.76 reads healthy and can still hide a 64-row class; look at the counts too.

    Evaluation: macro_f1, accuracy, and the per-class F1 floor

    After training, the platform automatically evaluates against the project's rule set; Results → Verdict shows the Pass/fail rules card (PASS / FAIL and the failed required rules).

    Which rule set am I scored against?

    Picking the classification task does not switch the rule set. Until you save the scaffold, runs are scored against the general default (accuracy ≥ 0.5 and macro-F1 ≥ 0.5 required, no per-class floor). To use the rules below: open Results → Failures with the run selected. In the Pass/fail rules card, while Project rule set is Auto (domain profile fallback), the Scaffolded pass/fail rule set panel appears. Review the thresholds and click Use scaffold; the next eval uses it.

    The classification scaffold has four rules:

    min_macro_f1 ≥ 0.65 (required)
    The headline. Average of per-class F1, weighted equally. The metric that catches the imbalance bug where the model is great at majority classes and silently bad at minority ones — flat accuracy alone won't surface this on a 30:1 distribution.
    min_accuracy ≥ 0.70 (required)
    Coarse sanity check. Pairs informatively with macro_f1: high accuracy + low macro_f1 = imbalance bug (the model gets the common classes right and gives up on the rare ones); low accuracy + reasonable macro_f1 = bad model (no class is doing well, retrain).
    min_per_class_f1 ≥ 0.50 (required)
    Every individual class's F1 must clear 0.50. This is the class-starvation tripwire. A model that scores 0.85 macro_f1 but has cancellation F1 at 0.30 fails this gate even though the average looks healthy. For triage this is exactly the gate you want: it fails a model that quietly drops the rare classes. On a rare class with only a handful of test rows the per-class F1 is noisy (one miss in 20 rows moves recall by 0.05), so treat a near-miss as a reason to look, not a verdict.
    min_safety_pass_rate ≥ 0.93 (optional)
    Catches refusal / off-topic / adversarial inputs that should be flagged through a different path. Useful when the classifier sits behind a customer-facing UI; not strictly required for an internal routing service.

    The Pass/fail rules card names the failed required rules, and the goal ledger's eval_pass_rate row expands into the per-rule breakdown so you see exactly which dimension is failing — "macro_f1 0.71 ≥ 0.65 passed; min_per_class_f1 0.42 < 0.50 failed on class cancellation."

    Reading the per-class grid

    Results → Failures shows the per-class precision / recall / F1 bars (worst class first). Three patterns to look for:

    • One class starves. Five classes at 0.80+ F1, one at 0.25. Almost always too little data on the rare class. Fix: more rare-class rows (real, or Balance class distribution), then retrain.
    • Two classes collapse. The model rarely distinguishes bug_report from technical. The label vocabulary has a boundary problem — either the classes overlap semantically (consider merging) or your gold is inconsistent across them (have a second reviewer relabel 50 random rows from both and reconcile).
    • Rare classes get zero predictions. The model never emits cancellation; precision is undefined. The model learned that always-predicting-something-else is the lowest-loss policy. Add rows (real, or Balance class distribution) until that class has 100+ training rows.

    If you want per-class precision/recall floors (e.g. cancellation recall ≥ 0.80 because missing a cancellation has direct revenue impact), open the rule-set card on Results → Failures. Click + Add rule, then in the Metric dropdown pick Per-class · cancellation → Recall — the optgroup is populated from your latest classification eval's per-class breakdown. Set operator ≥, threshold 0.80, mark it Required, and click Use scaffold (once a rule set is saved, the scaffold panel is gone and the Project rule set picker is the way back in). If the per-class optgroups are empty, the panel shows "Run a classification eval to discover per-class metrics" — that's expected on fresh projects, and once an eval finishes the classes appear automatically. A Coach notice on Results also nudges this when a classification project has zero per-class rules configured.

    When the eval fails (common failure modes)

    Multi-class triage failures concentrate around imbalance. Common patterns and fixes:

    SymptomRoot causeFix
    Accuracy 0.82, macro_f1 0.51, per-class F1 fails on the rare classClass imbalance — the model defaults to majority classesAdd rows for the under-represented class (real ones, or Balance class distribution) until balance is ≥ 0.75 and the rare class has enough rows. Retrain.
    Two classes blur (low precision on both)Class boundary is genuinely ambiguous in the goldSample 40 random rows from each class; have a second senior agent relabel blind. Disagreement > 20% = the classes overlap semantically. Either merge them in the label vocab or document a tie-breaking convention and re-label gold against it.
    Rare class precision/recall = 0 across the test setToo little training signal; model learned never to emit itSeveral Balance class distribution runs plus 30+ manually-seeded rows from senior agents. More epochs don't add rare-class signal; that's NOT the fix.
    Macro_f1 strong on val (0.78) but tanks on test (0.55)Random split drew an unlucky distributionRe-split with Stratify By Field = your label column (see the Split section). Tick Keep the current N test examples only if the current test set is already stratified.
    Mixed-intent tickets get bounced between predictionsLabel vocab doesn't fit hybrid intentsLook at the mixed-intent rows you rejected in the synth queue (your own notes; the queue has no custom reason tags). If persistent: add a compound label or document a tie-breaking convention.
    A reroute recommendation card appears on ResultsThe pass rate is below 0.5 and one of the decision engine's signals firedRead the signals listed on the card. The engine never proposes swapping one recipe for another; it suggests a RAG-first sibling, iterating in Try it, or more data. For a classifier, "more data" is the usual answer.

    Results → Failures → Failure clusters groups failures into clusters with a representative example each. Reading 5-10 examples from a cluster usually surfaces the failure shape in 30 seconds. The panel also offers a one-click launch of the Target a failure cluster playbook seeded from that cluster — the most efficient drill for a specific failure mode.

    Ship with confidence thresholds

    Once the rule set passes — and especially once the per-class F1 floor passes on the revenue-protective classes — ship in three steps:

    1. Export the merged model. Open Ship → Package: in the New export form pick the run, Format HuggingFace, the deployment targets, then Run Export; the export shows up in the Exports table. A LoRA run is merged into its base model at export, so the package is the full model with its classification head (not a small adapter), plus the tokenizer and a manifest, under DATA_DIR/exports/<project id>/<export id>/run-<timestamp>/. Skip GGUF and the vLLM / Ollama runners here: they serve text generators, not a classification head. Docker adds a Dockerfile and a serve.py, but that serve.py is a generic text-generation template, so it does not serve the head either.
    2. Serve it with transformers. Wrap the export's model/ folder in a thin /triage microservice: load it with AutoModelForSequenceClassification, take the softmax over the head's logits, and return the top label and its probability as the confidence. Tutorial 2's Ship section has the ten-line loader; it works unchanged for six labels because the label names are stored in the model config (id2label). Latency is milliseconds per ticket on a GPU, tens of milliseconds on CPU for a model this size (a rough guide; measure on your hardware).
    3. Wire the two-threshold router. Your ingest pipeline POSTs each new ticket to your /triage microservice, gets back (label, confidence), and routes (after you calibrate the confidences, see below):
      • High-confidence (≥ 0.85): auto-route to the predicted team.
      • Mid-confidence (0.60-0.84): shadow-route to the predicted team but flag for human confirmation. Corrections are high-signal training data.
      • Low-confidence (< 0.60): triage-manager queue. The model's prediction is suggested but not pre-selected.

    The thresholds above are a starting point — calibrate on YOUR traffic. Shadow-mode for two weeks before turning auto-route on: log the model's prediction and confidence alongside the team the human triager actually picked; compute precision per confidence band; set the high-confidence threshold where per-class precision exceeds 0.95.

    Calibrate, don't trust the eval-set confidence

    A fine-tuned classifier's softmax confidence is usually over-confident, even on the test set; calibrate it on the validation split (for example with temperature scaling) before you pick thresholds. And your production traffic is not your test-set distribution — it shifts over time, accounts evolve, support tooling changes the way tickets get phrased. Always shadow-mode before turning the auto-route on, and re-calibrate the thresholds at least quarterly. The default thresholds above are starting points, not destinations.

    What's next

    You have a deployed multi-class triage classifier with thresholds tuned on your own traffic, a human-review fallback for mid- and low-confidence cases, and a per-class F1 floor that fails a model that drops the rare classes. Three next moves:

    Hierarchical routing
    If your org has sub-team specialisations (billing → refunds vs invoicing; technical → API vs infra), a flat 20-way classifier struggles. Chain two: the first emits the top-level team (the model you just shipped); a second, conditional on the parent, emits the sub-team. Same recipe + workflow, run twice.
    Active learning from disposition signals
    The highest-signal training data is in your shadow-routed and human-overridden queue. Every reviewer correction is a row proving the model didn't generalise. Capture corrections; promote the confident ones; retrain when the corrected pile crosses ~100 rows. Over a quarter the model gets sharper on the tickets your org actually sees.
    Expand the label vocabulary as new categories emerge
    Six labels today won't be six in two years. New product surface areas and new revenue motions create categories that didn't exist before. Retraining cost is low; the hard part is governance — every label-vocab change invalidates eval-comparable historical runs, so lean conservative.

    Same recipe, different shape: Tutorial 2 — SQL injection classifier uses the same classification recipe for a binary problem with hard-negatives as the headline drill. The decision-tree: binary with balanced classes → hard-negatives is the spine; multi-class with imbalance → balance-fill is the spine.

    Key terms

    Multi-class classification
    One label per row drawn from a fixed vocabulary of more than two classes. Distinct from binary (yes/no) and from multi-label (one row, multiple labels).
    Class imbalance
    The natural ratio of classes in real-world data is skewed. A model trained on imbalanced data defaults to majority-class predictions unless the gold set is balanced (via more data or via the Balance class distribution playbook) and the eval gates require per-class minimums.
    Shannon entropy (normalised)
    A single number summarising how balanced your class distribution is — H / ln(k), 1.0 perfectly balanced, 0.0 dominated by one class. The raw value (nats) is in Answer key diagnostics (Data → Labels); the normalised value is the trainability forecast's "balance X of 1.00" (warns below 0.75, blocks below 0.50).
    Balance class distribution playbook
    BrewSLM's synth generator for fixing imbalance. Each run generates more examples of the rarest class in the answer key. Distinct from Paraphrase positives, which paraphrases in proportion to existing counts.
    macro_f1
    Average of per-class F1 scores weighted equally regardless of class size. The headline gate in the classification eval pack; catches imbalance bugs flat accuracy misses.
    Per-class F1 floor (min_per_class_f1)
    Required rule in the classification scaffold (after Use scaffold): every individual class's F1 must clear a threshold. The class-starvation tripwire — a model that scores high macro_f1 by averaging away one bad class still fails this gate.
    Confidence-thresholded routing
    Deployment pattern where the model's predicted probability decides whether the router acts on the prediction (auto-route), shadow-routes for human confirmation, or punts to a triage-manager queue. The thresholds are calibrated against real production traffic, not the test set.
