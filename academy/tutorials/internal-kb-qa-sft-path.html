    Tutorial 5 · End-to-end · Internal KB

    Internal knowledge-base QA via the qa-sft recipe — the simpler path

    By the end of this tutorial you'll have a small language model that answers questions from your internal knowledge base — "how do I get VPN access?", "what's the office WiFi password?" — directly from its weights, with no retrieval index alongside. Inference takes well under a second on a small GPU. The pipeline is intentionally lighter than the rag-protocol path: no citation discipline, no refusal phrase, no BM25 index to maintain. When facts are stable and the corpus is small, this is the right tool. When they're not, this tutorial covers the honest signal that says "this wants retrieval" and the one-click reroute that clones a retrieval-first sibling for you to compare.

    Level: intermediate Time: ~1.5 hours total (less ceremony than the rag-protocol tutorial) Prerequisites: Tutorial 0 (Setup BrewSLM). Optional companion: Tutorial 1 (Support FAQ with rag-protocol) — this tutorial is the explicit counterpart, picking memorisation where T1 picked retrieval. Updated: 13 Nov 2026

    Before you start

    This tutorial assumes BrewSLM is running locally at http://localhost:5173 with an admin user signed in. If you haven't done that yet, complete Tutorial 0 — Set up BrewSLM and your first project first. It takes ~20 minutes and is the prerequisite for every tutorial in this track. Training needs Redis and a running Celery worker; Tutorial 0 starts both.

    You'll also want, before you start: 40-80 canonical Q&A pairs from your internal knowledge base. Easiest sources: resolved internal-IT tickets, employee-handbook FAQ pages, Slack-canonical-answer threads (the ones with a thumbs-up emoji on the reply that gets reposted twice a month). If you don't have your own data yet, the public SQuAD dataset or Natural Questions works for validating the workflow before you point at your own corpus.

    Terms you'll see in this tutorial (click to expand)
    Recipe
    The training-plan template. BrewSLM proposes one from your brief and your data. For this tutorial: qa-sft. Set under Train → Task → Change. Defines the base model + adapter + pass/fail rule defaults for direct-answer QA — no retrieval index, no citation marker, just (question, answer) supervised fine-tuning.
    Adapter
    The mapping layer that converts your CSV/JSONL rows into training-ready fields. For qa-sft the adapter is qa-pair — for training it reads a question column and an answer column. Answer-key rows use question and expected, with an optional rationale.
    Task profile
    The shape category the platform uses to pick eval handlers and synth playbooks. qa-sft's task profile is instruction_sft — same family as a generic SFT task, with QA-specific defaults layered on top.
    Scoring mode
    How the eval handler compares prediction to gold. qa-sft uses field_match — the prediction is scored against the single expected field via exact_match + F1, with an LLM-judge gate on top to catch semantic equivalence the string metrics miss.
    Memorisation
    The model encodes each (question, answer) pair into its weights during training. At inference, the same (or paraphrased) question retrieves the answer from those weights. No index, no retrieval step. The trade: when a fact changes, you retrain.
    Canonical answer
    The single "official" version of an answer to a question. qa-sft trains on one canonical answer per question — paraphrasing the question is encouraged, paraphrasing the answer is noise.
    LLM-judge pass rate
    A semantic-equivalence gate. A judge model reads (gold answer, predicted answer) and scores whether they say the same thing. Catches the case where "Visit Settings → Security" and "Go to Settings, then Security" should both pass even though exact_match says they don't.
    Reroute-to-RAG
    The platform's one-click escape hatch when the post-eval decision engine detects you're using qa-sft for a workload that wants retrieval. Clones your project as a sibling with runtime_config.rag_first=True (the base model plus retrieval, not the rag-protocol recipe), carries your answer key (gold set) forward, builds the BM25 index. You compare both side-by-side.

    This is BrewSLM's canonical workflow for direct-answer QA over a small, stable knowledge base — the kind of corpus an internal-IT team at a 50-engineer company actually maintains. The classic shapes: "how do I get VPN access?", "where do I file expense reports?", "what's the office WiFi password?". These don't change weekly. The answers fit in the model's weights cheaply. You don't need a retrieval index to look them up — you need the model to remember them.

    The end state is the model you'd actually deploy at a B2B engineering team: small enough to host on the same box as your Slack-bot worker, accurate enough that the helpdesk channel goes quiet, simple enough that one engineer can own the whole pipeline.

    What you'll build

    A direct-answer QA assistant. Concretely:

    • "How do I get VPN access?" → "File a ticket in #it-help with the project you need access to, then run the VPN installer that IT sends back."
    • "How do I file expenses?" → "Use the expense app. Photograph the receipt, tag the project code, and submit. Manager approval is automatic under $200."
    • "How do I get on the office WiFi?" → "The network is brewslm-corp, password is in the team password manager under Office WiFi. Mobile devices use the brewslm-guest network with a daily PSK posted in #office."

    The model is a fine-tuned LoRA adapter on top of SmolLM2-135M-Instruct. Inference takes a fraction of a second on a single GPU and somewhat longer on CPU, still fine for a Slack-bot (a rough guide; measure on your hardware). No citations in the output (the part rag-protocol does and qa-sft doesn't); when a fact changes, you update the gold set and retrain.

    Key idea

    qa-sft is the simpler tool. Less ceremony than rag-protocol — no citation discipline, no refusal training, no index to maintain. It memorises facts. When facts change, you retrain. That's the trade. If your corpus is small (under ~100 facts) and stable (changes less often than once a month), this is the right pick. If it isn't, the post-eval decision engine in BrewSLM may suggest a retrieval-first approach, and we'll walk through how to test that suggestion.

    Why a small model (not regex, not a frontier API, not always RAG)

    Three options people reach for when building an internal helpdesk bot. Use this comparison:

    ApproachHandles paraphrased questions?LatencyCostPrivacy / offline
    Regex / keyword Slack-botNo — fails on "how do I VPN" vs "VPN access"MillisecondsFreeSelf-hosted
    Frontier LLM via APIYesSeconds, plus queueingA fee on every query (an illustrative $0.003-0.02 each)Every employee question leaves your network
    Small qa-sft model (this tutorial)Yes (paraphrase playbook drills exactly this)A fraction of a secondNo per-query fee; the running cost of your own GPU or CPUSelf-hosted; runs offline

    The latency and cost entries are rough orders of magnitude, not measurements; yours will differ. Regex dies the first time someone types "how the heck do I VPN" — the register your engineers actually use diverges hard from the canonical FAQ wording. Frontier-LLM works but you're paying per question and sending every employee's "what's our parental leave policy" out to a third-party API. The small fine-tuned model is the middle path: handles paraphrase, stays on your hardware, costs nothing per query at runtime.

    The remaining decision is qa-sft vs rag-protocol — both are BrewSLM recipes for QA, and they look almost identical from the outside. The recipe-choice section below is the real load-bearing piece of this tutorial: the answer changes based on properties of your corpus, not preferences. Read it carefully before you start building.

    Choose your dataset

    You need (question, answer) pairs. The answer is the canonical thing the model should say when asked the question. Three common starting points:

    Your own knowledge base
    Most internal-IT teams already have the data, scattered across three places. Confluence / Notion pages where an H2 is the question and the paragraph below is the answer. Slack threads where someone asked, IT replied, and the reply got a thumbs-up. Resolved tickets in Jira / Linear with the "answer" field populated. Extract Q→A pairs from all three; you'll find 40-80 high-signal ones in any half-mature engineering org.
    Public starting points (for warmup)
    SQuAD ships 100k QA pairs over Wikipedia paragraphs — the canonical QA benchmark. Natural Questions is Google's dataset of real user questions answered from Wikipedia. Either gets you to a working pipeline in 30 minutes; swap in your real corpus once you've verified the platform end-to-end.
    Resolved helpdesk archives
    A year of resolved internal-IT tickets already contains canonical Q&A pairs — the question is the ticket title, the answer is the first reply that closed the ticket. Filter for tickets that resolved without follow-up and you've got pre-validated gold candidates.

    How many rows do you need?

    40-80 canonical Q&A pairs is a good seed. qa-sft is a memorisation task — every gold row is a fact the model commits to weights. The paraphrase synth playbook then multiplies your seed 3-5x by generating variant phrasings of the same questions, so 60 seed rows becomes 200-300 trainable rows.

    Ingest and map

    In BrewSLM, create a new project: on the projects home click + New Project, give it a name and a brief ("Answer internal IT helpdesk questions from our knowledge base, directly, no citations"), then Create project. On the project's Overview check the task; if it isn't qa-sft, open Train → Task → Change and pick it. The recipe pre-fills the adapter (qa-pair), the task profile (instruction_sft) and the scoring mode (field_match). It also offers a draft pass/fail rule set (exact_match + F1 + LLM-judge), but that draft only applies once you click Use scaffold after your first run — see Evaluation.

    Open Data → Sources → Import dataset (auto-mapping) → Import dataset →. Your CSV or JSONL should look like:

    question,answer
"How do I get VPN access?","File a ticket in #it-help with the project you need access to, then run the VPN installer that IT sends back."
"What's the office WiFi password?","The network is brewslm-corp, password is in the team password manager under Office WiFi. Mobile devices use brewslm-guest with a daily PSK posted in #office."
"How do I expense a $30 dinner?","Use the expense app. Photograph the receipt, tag the project code, submit. Under $200 manager approval is automatic."

    Two required columns, question and answer; the recipe's shape matcher recognises answer (or response, output, reply) as the output column. Don't call it expected here: that is the field name for answer-key rows, not training rows. The import wizard scans your columns and proposes a binding; check it in the preview and fix the output column if needed. Imported rows land as accepted training rows (they skip the review queue), so the preview is your review.

    ✓ Checkpoint: Data → Sources → Details → Readiness overview now shows your imported row count (e.g. "62 trainable rows"), and Sources summary in the same drawer lists your imported CSV/JSONL. If the mapping is wrong, the preview will show empty or mis-shaped rows — check Data → Split → Details → Schema mapping and re-run the import with the correct column for each field.

    One canonical answer per question

    If your data contains the same question with multiple slightly-different answers ("Use the VPN client" / "We use the VPN client, install the desktop app" / "VPN client, ping #it-help if it doesn't work"), pick one canonical phrasing and drop the rest. Training on three different answers to the same question teaches the model that the question has a distribution of valid responses — which is noise, not signal, when what you actually want is "say this one thing".

    Cleanup

    Open Data → Prepare → Details → Quality and safety. Three deterministic scans worth running:

    • Strip Slack / Confluence markup. Slack data carries <@U02ABC> user mentions, channel refs like <#C03XYZ|it-help>, and emoji shortcodes (:tada:). Confluence exports carry <p>, <strong>, and the occasional rogue <ac:structured-macro>. Strip them; the model doesn't need to learn that <@U02ABC> means "IT manager".
    • Dedup near-identical questions. People ask "what's the WiFi password?" five different ways. The platform's dedup signal in the same panel clusters them. The right move is NOT to drop them all. Keep ONE in the answer key with the canonical answer, and let the paraphrase synth playbook regenerate the other phrasings later as training rows — question variation in training, one canonical answer per question.
    • PII signals. Internal helpdesk archives often have employee email addresses and Slack handles in the answer text. Decide per row — "open a ticket at helpdesk@brewslm.com" stays; "ping jane@brewslm.com directly" probably drops (Jane will leave the company and the model will keep recommending a dead address).

    You don't have to clean everything before training; you do have to clean the rows you promote to the answer key.

    Pick the recipe: qa-sft or rag-protocol?

    This is the load-bearing decision in the whole tutorial. BrewSLM ships two recipes for question-answering and they look surprisingly similar from the outside. The difference is which property of your data they exploit:

    • qa-sft memorises the facts into the model's weights. You ask, it remembers, it answers. When facts change, you retrain.
    • rag-protocol trains the model to use a retrieval index — given a chunk of context, cite the source, refuse if context is insufficient. The facts live in the index (BM25 over your corpus), not the weights. When facts change, you re-index; no retraining needed.

    Use this decision matrix:

    Question about your corpusPick qa-sftPick rag-protocol
    How often do your facts change?Rarely (less than once a month)Frequently (weekly or more)
    How big is your corpus?Small — under ~100 facts (a rough guide)Large — over ~500 facts (a rough guide; past some size the model can't memorise them all)
    Do you need a citation in the output?No — direct answer is fineYes — auditability / source-of-truth requirements
    Do you need clean refusal when the answer isn't known?No — best-effort is acceptableYes — guessing is unacceptable
    Will you run offline / air-gapped?Yes — qa-sft works without a retrieval index loadedIf you can load the BM25 index alongside, fine
    Do you need a compliance audit trail (which doc produced which answer)?NoYes — citations are the audit trail
    How much pipeline complexity are you willing to maintain?Less is better — fewer moving partsOK with index maintenance + protocol-shaped gold

    The internal-IT helpdesk inside a 50-engineer company is the canonical qa-sft case. Facts are stable across quarters. The corpus is small — a few dozen canonical Q&As often cover most of the helpdesk volume (a rough guide; count your own tickets). Citations aren't required because the answer is itself the source-of-truth from the team that maintains the policy.

    An ecommerce FAQ that updates monthly, a legal QA system that touches new statutes, or a customer-support bot covering 600 product SKUs — those are rag-protocol territory. Tutorial 1 walks through that path.

    Sticking with qa-sft for this tutorial

    If two or more rows in the matrix point at rag-protocol, stop here and switch to Tutorial 1 instead. If they all point at qa-sft (the canonical internal-IT helpdesk case), keep going. The remaining tutorial assumes you've made the qa-sft call deliberately.

    Domain packs (optional)

    Three domain layers exist. Domain presets are starting defaults picked at creation (+ New Project → Advanced options → Domain preset: Legal, Customer Support, Healthcare and Finance starters). Domain packs are overlays assigned under Settings → Tools → Domain Packs; the only built-in one is general-pack-v1, and you can build your own (see Tutorial 8). Built-in domain eval packs such as evalpack.domain.support show up in the Project rule set picker.

    For most internal-KB use cases all of these are optional. The platform defaults work fine; a custom pack is a refinement you can add later if you find yourself doing the same cleanup on every project. The recipe defaults plus the cleanup step above cover everything important.

    Build the answer key

    The answer key — the gold set — is the trusted reference your model is evaluated against, under Data → Labels. For qa-sft this is the most important data work you'll do — every answer-key row is a fact the model commits to memory. Aim for 40-80 rows; quality matters more than quantity.

    Path A — manual seeding from your canonical answers

    Open Data → Labels. Confirm "What kind of task is this?" if it asks, then work in the Answer key card (the Answer-key workbench with coverage and suggested rows is in the step's Details drawer). For each row you add:

    1. Write the question the way a real teammate would ask it. If you have Slack logs, copy the actual wording — "how do I get on VPN" beats the textbook "How do I request VPN access?".
    2. Write the expected answer. Make it short, factual, and complete in a single response. If the canonical answer is currently a 12-sentence Confluence page, distill it to the 2-3 sentence version that would fit in a Slack reply.
    3. Optionally fill rationale — a one-line note on why this answer is right. Helps your future self when you're auditing the answer key six months later.

    Spend an hour here. The model will inherit the tone, format, and granularity of these rows — casual and short stays casual and short; formal and exhaustive stays formal and exhaustive.

    Path B — LLM-assisted drafting from raw exports

    If you have a few hundred raw Confluence pages or resolved tickets, let a model draft candidates:

    1. Bring the raw pages / tickets in on Data → Sources and clean them.
    2. Run a data-writer model (a local model through Ollama is the free default; a cloud provider key or any OpenAI-compatible endpoint also works) against them from Data → Generate — Provider, Model Name, Load from Cleaned Data — with the generation mode set to Single-turn Q&A, so it drafts (question, answer) pairs.
    3. Every drafted pair lands in the review queue (Data → Generate → Details → Review queue) with review_status="pending". Accepting a row makes it training data, not an answer-key row.
    4. For the answer key, copy the best drafts by hand into the Answer key card on Data → Labels, as in Path A. The answer key is held out of training, so keep a row in one or the other, not both.

    This turns hours of writing from scratch into review and light editing. The platform will not auto-accept LLM-generated rows — every accept is an explicit click.

    ✓ Checkpoint: the recipe recommends at least 50 answer-key rows; the goal ledger's answer-key row (Data → Sources → Details → Readiness overview) counts toward 100, so at 60 rows it shows partial progress. That is fine for now. The paraphrase playbook in the next section adds training rows, not answer-key rows. If it says nothing has been promoted, open Data → Labels and confirm rows landed in the Answer key card.

    Splitting train, validation, test

    BrewSLM splits when you click Run Split on Data → Split (the Train / Val / Test Split form; the split adapter reads qa-pair). The default ratios are 80/10/10 with a deterministic seed. For qa-sft, uniform random off the canonical config is fine.

    This is genuinely different from the other tutorials. Span-extraction cares about template-leakage; code-review cares about author-leakage. qa-sft doesn't have an equivalent split leakage trap — questions are independent, answers paraphrase-stable. Random split is honest here. The leak to watch in qa-sft comes from the paraphrase playbook, not the split (see the warning in the next section).

    Override the default ratios in the same form only when your answer key is small (under 50 rows): use 70/15/15 so val/test have at least 7-10 rows each. Below that the eval metrics get too noisy to read.

    Generate synthetic drills (just paraphrase)

    The qa-sft recipe ships two synth playbooks, and the headline one for a fresh project is the paraphrase playbook. This is intentional — qa-sft is the smaller, simpler recipe and it deliberately doesn't ship the modes that classification or span-extraction do. If you've read Tutorial 2 (SQL injection) or Tutorial 3 (invoice extraction), you'll have seen hard-negative and class-balance-fill playbooks; those are not available for qa-sft, and that's by design. There are no "negative classes" in direct-answer QA the way there are in classification — every question has a correct answer; there's nothing to be a "negative" against.

    qa_sft_paraphrase — the workhorse (POSITIVES_PARAPHRASE mode)
    For each gold row, generate N paraphrases of the QUESTION while keeping the ANSWER verbatim. Goal: the model learns that "how do I get VPN?", "I need VPN access, where do I go?", "VPN setup steps?" all map to the same canonical answer. Generate ~3-5 paraphrases per gold row; a 60-row seed expands to 240-360 trainable rows.
    qa_sft_cluster_targeted — for iteration 2 (CLUSTER_TARGETED mode)
    After your first training pass + eval, the platform's failure-cluster surface will identify question-types the model is weak on. The cluster-targeted playbook generates new examples specifically aimed at those clusters. Don't run this on iteration 1 — there's no failure cluster yet. It's the right tool for round 2.

    Known leak: the paraphrase playbook also reads your final answer key

    Today qa_sft_paraphrase picks its seed rows from both halves of the answer key, the Practice answer key (gold_dev) and the Final answer key (gold_test), and every row it writes keeps the seed's answer word for word. Accepted rows train, so reworded final-answer-key questions go into training with their answers, and a later score on that final set is inflated. Until a product fix ships, seed from practice rows only: run the playbook while the Final answer key is still empty and add the final rows afterwards, or skip the playbook. Rows you add by hand go to the Practice answer key unless you pick Final in the card's selector.

    Open Data → Generate → Details → Playbooks. The qa-sft recipe surfaces the paraphrase card; click it, set target count to 3-5× your answer-key size, pick a backend (a local model, a cloud provider key or any OpenAI-compatible endpoint). Generation runs as a background Job — the notification bell tracks progress, and Details → Playbook center keeps the run history.

    Paraphrase the question, not the answer

    The whole point of the paraphrase playbook is to teach the model question-invariance — "the same fact answers many phrasings". If the data-writer model paraphrases the ANSWER too, you'll be training the model that the same question can have N slightly-different acceptable answers, which is the noise mode this tutorial keeps warning against. The review queue (next section) is where you catch this.

    Review the synth queue

    Every paraphrase row lands in the Review queue (Data → Generate → Details → Review queue) with review_status="pending". By default the queue groups rows by source (the playbook that made them); Group by also offers Job, Backend and the Pre-screen verdicts. Per-row actions:

    • Accept — the row joins the training corpus on the next split.
    • Reject (soft) — the row stays on disk for audit. You can't type a reason tag; the only reasons are the ones a Pre-screen (review assist) run attaches.
    • Purge — a section-level action that physically deletes all rejected rows (optionally only those with one pre-screen reason).

    The key check for qa-sft paraphrase rows is "does the answer match the seed verbatim?". If yes (most rows), accept. If the data writer paraphrased the answer too — even slightly — reject it. You want question variation, not answer variation. For a large batch, run Pre-screen with that check as the rubric, then group by Verdict + reason and reject the failing group in one go.

    If you're rejecting more than half, the playbook prompt itself can't be edited — try a different backend or model, or tidy the seed rows it paraphrases.

    Training configuration

    Open Train. The form shows Base model, Task, Seeds and Run name; the values below live under More options → Model and hyperparameters and LoRA and advanced training. The defaults are sensible — for a first run, accept all of them. Several are auto: they resolve from your model and data size, and the confirm dialog shows the resolved values before you launch.

    Base model
    HuggingFaceTB/SmolLM2-135M-Instruct. Small, instruction-tuned, runs on consumer hardware. Alternatives the recipe surfaces: Qwen/Qwen2.5-0.5B-Instruct (slightly better quality at ~4x the size), Qwen/Qwen2.5-3B-Instruct (noticeably better, needs more VRAM).
    Adapter
    LoRA, rank 16, alpha 32, target modules auto — on models of 2B parameters or fewer that means every linear layer (all-linear). No separate classification head, no custom output projection — qa-sft uses the base model's standard LM head.
    Learning rate
    2e-4. Higher than full fine-tuning because LoRA has fewer trainable parameters.
    Epochs
    Auto. The trainer aims for about 200 optimiser steps and caps epochs by dataset size (up to 8 for 100–999 rows); a 250-row training set resolves to 4 epochs. Memorisation is the goal here, so several passes are expected; watch for the model echoing training rows verbatim on questions it shouldn't. Typing an epoch count turns auto off.
    Batch size + gradient accumulation
    Batch 4, accumulation 4 configured, but with auto epochs the trainer shrinks accumulation first on small datasets, so a few hundred rows train at accumulation 1 (effective batch 4). Lower the batch on GPUs under 8 GB.

    Training runs on the Celery worker, so Redis and the worker from Tutorial 0 must be up; without the worker the run reads RUNNING but never makes progress, and without Redis it is marked Failed at hand-off. Expected runtime (a rough guide, not a measured benchmark): minutes on a single GPU, longer on CPU. The runs list below the form shows live loss; if loss isn't dropping after the first 50 steps, cancel the run and check your data — the dataset is probably misshapen.

    ✓ Checkpoint: in the runs list under Train, your run's loss drops steeply over the first steps and then flattens (the exact values depend on your data and model). The bell shows a "training" notification with a percentage. When complete, BrewSLM runs the lift check against the base model on its own; Results → Verdict shows the summary card (or an Evaluate this run button if the check didn't run).

    Read the trainability forecast

    Before kicking off the training run, the platform pre-computes a trainability forecast: given your current data + answer key + base model, what's the predicted pass probability? It lives under Train → More options → Plan and gaps; the goal ledger (Data → Sources → Details → Readiness overview) shows the same number as the predicted_pass row.

    qa-sft's pass probability tends to be higher than rag-protocol's for the same-size data set. That's because there's no citation discipline to learn, no canonical refusal phrase to imprint, no protocol-shaped gates — just (question → answer). Healthy targets for a fresh internal-KB project:

    • Predicted pass probability ≥ 70%. qa-sft on 60+ answer-key rows + paraphrase synth typically clears this. Below 50% usually means your answer key is genuinely too thin or has inconsistent canonical answers (one question with multiple slightly-different golds — see the cleanup section).
    • Answer key at or above the recipe's recommended 50 rows (the ledger row itself counts toward 100). Below that the forecast becomes noisy.
    • Data ready = met (training rows + mapping + splits all green).

    If the forecast is below 50%, add data before you train. The goal ledger's blockers panel tells you which component is weakest.

    Evaluation: exact_match + F1 + LLM-judge

    After training, the platform automatically evaluates against the project's rule set; Results → Verdict shows the Pass/fail rules card (PASS / FAIL and the failed required rules) below the summary card, both naming the run they describe.

    Which rule set am I scored against?

    Each project's pass/fail rules come from one rule set (an eval pack). BrewSLM takes the first of these that applies:

    1. The rule set chosen for the project. Clicking Use scaffold saves the drafted rules and makes them the choice (evalpack.project.scaffolded). Picking a built-in pack, such as evalpack.quality.strict or evalpack.domain.legal, or applying a pipeline recipe also sets it.
    2. The domain profile's thresholds (evalpack.domain-profile). Every project resolves a profile, at least the platform default generic-domain-v1, so with nothing chosen this is the rule set: F1 ≥ 0.65, LLM-judge pass rate ≥ 0.75 and safety pass rate ≥ 0.90 are required; exact match ≥ 0.55 is reported but not required.
    3. evalpack.general.default, only for a profile with no thresholds: accuracy and macro-F1 ≥ 0.5 for classification; exact match ≥ 0.4 and F1 ≥ 0.5 for instruction tasks.

    A scaffold is a draft until you click Use scaffold. The task type (recipe) only shapes that draft; for classification it proposes macro-F1 ≥ 0.65, accuracy ≥ 0.70 and per-class F1 ≥ 0.50.

    Two neighbours are easy to mix up with a rule set:

    • A domain preset picked at project creation (Legal, Customer Support, Healthcare, Finance) sets the base model, adapter defaults and an export gate, which decides whether export must pass the rule set. It does not choose the rule set.
    • A domain pack (the only built-in one is general-pack-v1) carries defaults such as the split ratios and a default profile. Packs apply live: editing one changes every project that uses it, so duplicate a pack before you edit it.

    To see which one is active, look at the Pass/fail rules card in evaluation: it names the Active Pack and its Source, for example "domain profile default".

    Picking the qa-sft task does not pick its rules. Until you act, you're scored against the domain profile's thresholds (evalpack.domain-profile, from the platform default profile generic-domain-v1): F1 ≥ 0.65, LLM-judge ≥ 0.75 and safety ≥ 0.90 required, exact match ≥ 0.55 optional (see the box above). To use the qa-sft rules:

    1. Open Results → Failures with your run selected and find the Pass/fail rules card.
    2. Leave Project rule set on Auto (domain profile fallback); the Scaffolded pass/fail rule set panel appears below it, auto-generated from the qa-sft task type.
    3. Adjust any threshold, then click Use scaffold. It is saved as the project's rule set and later evaluations score against it.

    The scaffolded qa-sft rule set carries four rules:

    Exact match ≥ 0.45 (required)
    Share of predictions where the model emitted the gold answer verbatim. 0.45 is intentionally not strict — exact_match is a coarse signal for natural-language answers because "Visit Settings → Security" and "Go to Settings, then Security" both say the same thing but differ on every token. exact_match catches gross paraphrase drift; the LLM-judge gate below catches the semantic case.
    F1 ≥ 0.60 (required)
    Token-overlap F1 between prediction and gold. A middle ground — partial credit for predictions that contain the right content words but reorder them. Standard SQuAD-style F1.
    LLM-judge pass rate ≥ 0.75 (required)
    A judge model reads (gold, prediction) and scores whether they say the same thing semantically. This is the gate that actually matters for natural-language QA. It catches the "Visit Settings → Security" / "Go to Settings, then Security" case as a pass even though exact_match fails. It also catches the failure mode where exact_match passes (model memorised the gold verbatim) but the answer is wrong in context.
    Safety pass rate ≥ 0.93 (not required)
    Refusal / off-topic / adversarial input handling. Marked non-required for qa-sft because the recipe doesn't train refusal behaviour — if you need this gate active, it's a signal you're in rag-protocol territory.

    The Pass/fail rules card names the failed required rules, and the goal ledger's eval_pass_rate row expands into the per-rule breakdown so you see exactly which rule failed — "exact_match 0.41 / ≥ 0.45 failed, f1 0.63 / ≥ 0.60 passed, llm_judge 0.78 / ≥ 0.75 passed". The exact_match-vs-LLM-judge split is the signal you'll learn to read.

    When the eval fails — and the reroute escape hatch

    Common qa-sft failure patterns and the fix for each:

    SymptomRoot causeFix
    LLM-judge passes (≥ 0.80) but exact_match low (≤ 0.30)Model paraphrases answers — semantically right but emits its own wording rather than your canonical versionUsually acceptable for a helpdesk bot. If you need verbatim, add the canonical wording as a system-prompt prefix at deploy time and retrain with the prefix in the gold question.
    exact_match high but LLM-judge lowModel memorised the gold rows verbatim but the answer is wrong in context — overfitting on the training distributionSet a lower epoch count than the auto value (this turns auto off); add more paraphrase rows; check for stale gold answers that are no longer correct.
    Both metrics mediocre AND post-eval engine recommends reroute-to-RAGYour workload is retrieval-shaped — too many distinct facts to memorise, or facts that need citationWalk the reroute trace below and, if it holds up, try the retrieval-first sibling.
    Model invents facts on questions outside the KBqa-sft doesn't train refusal behaviour — when asked something it doesn't know, the model generates a plausible-looking but fabricated answerThis is a known qa-sft limitation. If clean refusals matter, move to rag-protocol (Tutorial 1), which DOES train refusal. Don't try to hand-train refusal into qa-sft — that's working against the recipe.

    The reroute-to-RAG flow (when memorisation stops being enough)

    BrewSLM's post-eval decision engine looks at your eval result and the shape of your gold set. When the pass rate is below 0.5 and a retrieval-shaped signal fires — the brief mentions retrieval, or the answers in your answer key are very diverse — it surfaces a recommendation card on Results → Failures: "This task looks more like a RAG fit".

    Expand the "Why this fired?" disclosure on each signal. You'll see the actual numbers, for example a mean pairwise answer Jaccard below the 0.20 threshold (lower means more diverse answers) next to the pass rate under 0.5. If the trace matches your read of the data, click "Switch to RAG (keeps your answer key)". The platform runs clone_project_for_rag, which does three concrete things:

    1. Creates a sibling project with your project name + " (RAG)" suffix. The new project's parent_project_id points back at the qa-sft project.
    2. Forces runtime_config.rag_first=True and auto_rag.enabled=True on the clone. At inference time Results → Try it uses the BASE model (no LoRA) plus BM25 retrieval — no new training step.
    3. Carries your answer key + prepared splits forward and builds the BM25 index immediately, so the sibling's Results → Try it works the moment the clone completes.

    The original qa-sft project stays put — nothing is destroyed. You now have two projects side-by-side. Open Results → Try it on each, ask the same 10 questions, compare. The sibling is still a qa-sft project answered by the base model with retrieval; it is not the rag-protocol recipe. If you later want a model trained to cite and refuse, that is a separate project built as in Tutorial 1.

    The honest move

    The reroute recommendation is one of BrewSLM's better moments. The platform isn't trying to keep you on qa-sft because that's the project you started with — it'll volunteer that a different recipe might do better, with the trace to back the call. Take the recommendation seriously. If the trace looks right, try it. The qa-sft project doesn't go away; you compare both and ship whichever wins.

    Ship the model

    Once the rule set passes, ship in three steps:

    1. Export the model. Open Ship → Package. In the New export card pick the run under Experiment and a Format: HuggingFace (a LoRA run is merged into its base model) for vLLM, or GGUF (CPU) for Ollama. GGUF needs a compressed file first: open Options → Compress first, pick the training run, set Output Format to GGUF and click Quantize (the LoRA adapter is merged automatically). Then Run Export. The export lands under data/exports/<project>/<export>/run-<UTC timestamp>/ and appears in the Exports table.
    2. Get the launch commands. Expand the export's row and click Serve Plan. The One-Click Serve Plan card shows the Setup Commands and the Launch Command. For a HuggingFace export the vLLM runner is 
      python -m vllm.entrypoints.openai.api_server --model ./model
      which exposes an OpenAI-compatible /v1/chat/completions endpoint. For a GGUF export the setup writes a Modelfile (FROM ./model/<file>.gguf) and runs ollama create; the launch command is ollama serve. There are no deploy scripts in the bundle.
    3. Wrap in your own /ask microservice. BrewSLM doesn't expose a hosted /ask endpoint — you wrap the chat-completions endpoint in a thin HTTP service that handles the request shaping (your system prompt, your auth, your rate limiting). For a Slack-bot use case the wrapper is ~30 lines of Python: receive a Slack event, call /v1/chat/completions with the user's question, post the response back to the channel. Nothing qa-sft-specific.

    Smoke-test in Results → Try it first

    Before wiring the model into Slack, open Results → Try it for the project and pick the run under Training run. Ask 10 real internal-IT questions you'd see in #it-help. Check the answers; spot-check for the failure modes from the previous section (paraphrased answers, invented facts on out-of-KB questions). Try it is your last-mile sanity check before the deployed model starts producing answers that look authoritative because they're in Slack.

    What's next

    You have an exported direct-answer internal-KB assistant. Three obvious next moves:

    Refresh every N weeks when the KB changes
    qa-sft memorises facts. When facts change, you retrain. Set a recurring calendar item — every 4-8 weeks for an internal-IT helpdesk. Update the answer key with new canonical answers, re-run the paraphrase playbook on the new rows (until the leak noted in the synthetic-drills section is fixed, that re-run also seeds from your final answer key; skip it, or treat the next final score as optimistic), retrain. < 30 minutes once you've done it once.
    Grow the corpus thoughtfully (don't just dump everything in)
    The temptation when the model works is to throw every Confluence page at it. Resist. Each added row is a fact the model has to keep memorised; pile on too many and the memorisation pressure costs accuracy on the original rows. Add new answer-key rows when you have a real "we got this question N times and didn't have a good answer" signal.
    Watch the reroute signal — the honest "you've outgrown qa-sft" tripwire
    As your corpus grows past what the model can memorise, the pass rate drops and the post-eval decision engine may fire the reroute-to-RAG recommendation. Take it seriously when it fires: compare the retrieval-first sibling against your fine-tune. qa-sft was the right tool when the corpus was small and stable; retrieval is the right tool when it isn't. If you also need citations and clean refusals, start a rag-protocol project as in Tutorial 1.

    Key terms

    qa-sft recipe
    BrewSLM recipe that trains a small model to directly answer questions from memorised facts. No retrieval index, no citation marker, no canonical refusal phrase. The simpler counterpart to rag-protocol; right tool for small, stable knowledge bases.
    Canonical answer
    The single official version of an answer to a question. qa-sft trains on one canonical answer per question — paraphrasing the question (across many phrasings) is encouraged; paraphrasing the answer is noise.
    field_match scoring
    The eval-handler mode qa-sft uses. Compares prediction to a single expected field via exact_match + F1; the scaffolded rule set adds a required LLM-judge rule for semantic equivalence.
    LLM-judge pass rate
    The gate that actually matters for natural-language QA — a judge model reads (gold, prediction) and scores whether they say the same thing. Catches paraphrase that exact_match misses; required at ≥ 0.75 in the qa-sft scaffolded rule set once you click Use scaffold (also required at ≥ 0.75 in the domain-profile rule set you get before that).
    Reroute-to-RAG
    One-click platform flow that clones the qa-sft project as a RAG-first sibling. The clone has runtime_config.rag_first=True (base model plus retrieval, not the rag-protocol recipe), carries the gold set forward, and builds the BM25 index immediately. Only qa-sft projects can be cloned this way. The original qa-sft project stays put. The honest escape hatch when memorisation stops being the right strategy.
    Memorisation pressure
    The trade-off qa-sft makes. Every gold row is a fact the model commits to weights. A small model handles a modest number of facts cleanly; as the count grows it starts dropping signal on earlier rows to make room for new ones (where that happens depends on the model and the facts; the ~100 / ~500 figures above are rough guides, not measured limits). That ceiling is the natural reroute-to-RAG trigger.
