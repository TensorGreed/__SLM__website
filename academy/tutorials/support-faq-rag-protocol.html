    Tutorial 1 · End-to-end · Support FAQ

    Build a support FAQ assistant with the rag-protocol recipe

    By the end of this tutorial you'll have a small language model that answers questions from your FAQ corpus, cites the source chunk it pulled, refuses cleanly when the context can't answer the question, and is exported in a format you can serve with vLLM or Ollama. The whole thing runs on a single small GPU (or CPU) and costs roughly nothing per query at inference time.

    Level: intermediate Time: ~2 hours total (most of it training + eval) Prerequisites: Pretraining vs fine-tuning vs RAG, Auto-RAG & reroute Verified: 13 Nov 2026

    Before you start

    This tutorial assumes BrewSLM is running locally at http://localhost:5173 with an admin user signed in. If you haven't done that yet, complete Tutorial 0 — Set up BrewSLM and your first project first. It takes ~20 minutes and is the prerequisite for every tutorial in this track. Training needs Redis and a running Celery worker; Tutorial 0 starts both.

    You'll also want, before you start: ~60 rows of (context, question, answer) FAQ data in a CSV or JSONL file. Easiest source: scrape your help-center pages, or grab a row sample from SQuAD if you just want to validate the workflow.

    Terms you'll see in this tutorial (click to expand)
    Recipe
    The training-plan template. BrewSLM proposes one from your brief and your data; set or change it under Train → Task → Change. For this tutorial: rag-protocol. Defines the base model + adapter, plus a suggested pass/fail rule set that applies once you click Use scaffold.
    Adapter
    The mapping layer that converts your CSV/JSONL rows into training-ready fields. For rag-protocol, the adapter is rag-grounded — it reads (context, question, answer) triples.
    Answer key (gold set)
    Your trusted reference rows. What the model is evaluated against. In the BrewSLM UI this is the answer key, under Data → Labels. Aim for 60+ rows; quality beats quantity.
    Synth playbook
    A platform-provided generator that expands your gold set with controlled variations. rag-protocol ships three: paraphrase (citation drill), refusals, and format-robustness.
    Review queue
    Where every synth-generated row lands with pending status (Data → Generate → Details → Review queue). You accept, soft-reject, or purge — explicit review prevents bad data from sneaking into training.
    Eval pack
    The pass/fail rules your trained model is scored against — the UI calls them the rule set (Results → Verdict). For rag-protocol you want evalpack.rag_protocol.discipline — six rules, four of them required (citation rate, hallucination, refusal match, F1). Picking the recipe does not select it; you pick it yourself in the Project rule set picker (see Evaluation).
    Goal ledger
    The "% toward your stated goal" widget in the Readiness overview (Data → Sources → Details → Readiness overview). Expands into per-component progress (data ready, answer key ready, predicted pass probability, eval pass rate with a per-rule breakdown).
    Citation marker
    The [#1] token in an answer that points at the source chunk. The training signal the model learns to emit when its answer is grounded in a retrieved passage.
    Auto-RAG
    BrewSLM's BM25 retrieval index. Built automatically over the project's training rows when a run completes; the playground (Results → Try it) and the Auto-RAG comparison use it to ground answers in retrieved chunks. An exported model does not carry it.

    This is the canonical BrewSLM workflow for any project where the model needs to answer questions grounded in a body of text — customer FAQ, internal knowledge base, support transcripts, legal QA, product docs. The recipe stays the same; only your corpus changes. The platform learns the protocol; the index supplies the facts.

    The end state is the model you'd actually deploy at a B2B SaaS company: small enough to host yourself, accurate enough to answer in production, honest enough to refuse when it shouldn't guess.

    What you'll build

    A protocol-aware support FAQ assistant. Concretely:

    • "How long do I have to return an item?" → "You have 30 days from delivery to return unused items in their original packaging [#1]."
    • "What time does your store close?" (off-topic — context is about refunds) → "I don't have enough context to answer that."
    • "How LONG do I HAVE to RETURN?" (same question, different register) → Same answer, same citation marker, same format. The model is invariant under input register.

    The model is a fine-tuned LoRA adapter on top of SmolLM2-135M-Instruct (or any small instruction-tuned model). Inference takes well under a second on a single GPU (a rough guide; yours will differ with hardware and answer length). Retrieval sits in front of the model: whatever serves it looks up the relevant FAQ passages and puts them in the context, so when your FAQ changes you update the index — no retraining needed when you update content.

    Key idea

    The rag-protocol recipe teaches the model how to use a retrieval index — cite, refuse, format. The FACTS live in the index. That separation is why the same trained model works for ecom FAQ, legal QA, internal IT, and healthcare support without retraining for each.

    Why a small model with RAG (and not a big LLM)

    Three reasons enterprise teams pick a small fine-tuned model over a frontier model for narrow QA:

    Cost per query
    Frontier models charge per token; a 135M LoRA on your own GPU is roughly free at inference. At an illustrative $0.003-0.02 per query (a rough guide; real prices vary with the model and prompt length), a support funnel doing 10,000 questions a day (about 300,000 a month) pays roughly $900-6,000 a month in API fees; the small model has no per-query fee, only the cost of running your GPU.
    Latency
    A network hop plus a frontier-model queue often adds seconds; a small model on local hardware usually answers in a fraction of that (a rough guide; measure your own). For chat surfaces, sub-second answers feel instant.
    Privacy + control
    Your customers' questions stay on your hardware. You control when the model updates. You can audit every weight and every retrieved chunk.

    The trade-off is scope. A small model is not a general assistant. It's good at one bounded task — answering questions from one corpus, in one format. That's exactly the support-FAQ use case.

    Choose your dataset

    You need question / answer / source-paragraph triples. The source paragraph is the chunk of text the answer is grounded in; the citation marker [#1] in the answer points at it. Three common starting points:

    Your own help center
    Most companies already have FAQ pages with implicit (question → answer) linkage. Walk the page, extract the question (the H3/H4), the answer (the paragraph below), and the URL or section name as the citation. 60+ rows is the minimum useful gold set.
    Support transcripts
    Resolved tickets where the agent cited a KB article. The customer's question, the agent's answer, and the KB article's relevant paragraph become your triple. Export from Zendesk / Intercom / Salesforce as CSV.
    Public starting points
    SQuAD for general-domain QA practice; MS MARCO for passage retrieval. Use these to validate the workflow before pointing at your own data.

    How many rows do you need?

    60 high-quality rows beats 600 noisy ones. The synthetic playbooks will multiply your seed 3-5x; the eval pack scores quality, not volume. Aim for 60 gold rows that cover every category of question you expect in production.

    Ingest and map

    In BrewSLM, create a new project: on the projects home click + New Project, give it a name and a one-line brief ("Answer customer questions from our FAQ pages, cite the source passage, refuse when the context can't answer"), then Create project. You land on the project's Overview. Then pin the recipe: Train → Task → Change and pick rag-protocol. The recipe pre-fills the adapter pick (rag-grounded) and the task profile (rag_qa). It does not switch the rule set that Results scores against: until you choose one, that stays the general default (evalpack.general.default). You'll select the discipline rule set after the first run, in Evaluation.

    The screenshots in this tutorial come from Demo · Support FAQ (Tutorial 0), but that demo can't follow this tutorial: its rows are question/answer pairs with no context column and no [#N] markers, so rag-protocol has nothing to ground or cite. Use your own (context, question, answer) data here; the demo fits the qa-sft tutorial instead.

    Then Data → Sources → Import dataset (auto-mapping) → Import dataset →. Point the wizard at your CSV or JSONL. It will scan the columns and propose:

    {
  "context": "Our refund policy allows returns within 30 days of delivery for unused items in original packaging.",
  "question": "How long do I have to return an item?",
  "answer": "You have 30 days from delivery to return unused items in their original packaging [#1]."
}

    The wizard shows you a confidence-scored preview of rows mapped through the adapter. Confirm the mapping when the preview looks right; the rows land in the project as accepted training rows. Imports skip the review queue, so the preview is your only review of imported data.

    ✓ Checkpoint: Data → Sources → Details → Readiness overview now shows your imported row count (e.g. "247 trainable rows"), and Sources summary in the same drawer lists your imported CSV/JSONL. If the mapping is wrong, the preview will show empty or mis-shaped rows — open Data → Split → Details → Schema mapping to check how the columns were bound, and re-run the import with the correct column for each field.

    Citation marker format

    The marker [#N] is what the model trains on. If your data uses a different convention (footnote numbers, document IDs, source URLs), normalize it during the cleanup step before training — the platform's discipline pack scores answers by token overlap with the context, not the marker format, but the model needs one consistent marker shape to learn.

    Cleanup and PII review

    Open Data → Prepare → Details → Quality and safety. It runs a deterministic scan over your imported rows and flags:

    • PII signals — email addresses, phone numbers, credit-card-shaped strings inside the context or answers. Review each one; the platform will not auto-redact (per the project's safety rule).
    • Near-duplicates — questions that paraphrase each other. Decide whether to keep one or both; for FAQ data, keeping near-dupes can hurt eval F1 because they bleed signal between train and test splits.
    • Markdown / HTML artefacts in the context. Strip <p> tags, leftover bullet markers, etc. Clean context = honest faithfulness scores at eval time.

    You don't have to clean everything before training. You do have to clean the rows you're about to promote to the answer key — those are the rows the pass/fail rules score against, and they're the rows the synthetic playbooks seed from.

    Pick the recipe: rag-protocol or qa-sft?

    BrewSLM ships two recipes that look similar on the surface. Use this decision tree:

    Questionrag-protocolqa-sft
    Facts change frequently?✓ (index lives outside weights)✗ (model memorises facts at train time)
    Many domains, same shape?✓ (one model, swap indexes per customer)✗ (one model per domain)
    Need explicit citation in output?✓ (recipe trains [#N] marker)✗ (no citation discipline)
    Need clean refusals?✓ (recipe trains canonical refusal phrase)✗ (model will guess)
    Tiny stable corpus (under 30 facts)?(over-engineering)✓ (memorisation works fine)
    Fast iteration on a one-off?(more pieces to wire)✓ (less ceremony)

    For an ecom FAQ that updates monthly, an internal support KB that grows weekly, or a legal QA system that touches new statutes regularly — rag-protocol wins. For a stable 20-row FAQ that hasn't changed in years, qa-sft is simpler.

    Domain packs (when and why)

    Three different domain layers exist, and they are easy to confuse:

    • Domain presets — starting defaults picked at creation, under + New Project → Advanced options → Domain preset: Legal Starter, Customer Support Starter, Healthcare Starter (Non-Diagnostic) and Finance Starter (Non-Advisory). A preset suggests a base model, adapter defaults, gate defaults and safety reminders. Its adapter defaults are for instruction tuning, so for this tutorial leave it on No domain preset.
    • Domain packs — overlays you assign under Settings → Tools → Domain Packs. The only built-in pack is general-pack-v1; you build your own (see Tutorial 8).
    • Domain eval packs — built-in rule sets such as evalpack.domain.support and evalpack.domain.legal, which you can pick in the Project rule set picker. For this tutorial you want the discipline rule set instead.

    None of these changes the refusal phrase: the refusals playbook and the refusal metric both use a fixed phrase list built around "I don't have enough context to answer that." A domain pack is a refinement, not a prerequisite; the platform defaults work fine for a first run.

    Build the answer key (manual + LLM-assisted)

    The answer key — the gold set — is the trusted reference your model is evaluated against. It lives under Data → Labels. Aim for 60 rows minimum, 100+ ideal. Two complementary paths:

    Path A — manual seeding

    Open Data → Labels. Confirm "What kind of task is this?" if it asks, then work in the Answer key card (the Answer-key workbench with coverage and suggested rows sits in the step's Details drawer). For each row you add:

    1. Paste the source paragraph into context — verbatim from your KB or FAQ page.
    2. Write the question a real customer would ask. Use the actual wording you see in tickets, not a sanitised paraphrase.
    3. Write the answer. Make it short, factual, and end with the citation marker [#1] pointing at the chunk.

    Spend 30 minutes here. The model trains on signals you imprint with these rows — your answer key's tone, format, and refusal style are what the model will inherit.

    Path B — LLM-assisted drafting

    For larger sources (a few hundred FAQ pages), let a model draft candidates and keep the answer key itself hand-checked:

    1. Bring your raw FAQ pages in on Data → Sources and clean them.
    2. Open Data → Generate, set Generation Mode to Single-turn Q&A and use Load from Cleaned Data to feed it the pages. A local or cloud data-writer model drafts (question, answer) pairs.
    3. The drafts land in the review queue (Data → Generate → Details → Review queue) with review_status="pending". Accepting a row makes it training data, not an answer-key row.
    4. For the answer key, copy the best drafts by hand into the Answer key card on Data → Labels, adding the context and the [#1] marker, exactly as in Path A.

    This turns hours of writing from scratch into review and light editing. The answer key is held out of training, so a row should never be in both; the platform will not auto-accept LLM-generated rows, and every answer-key row is an explicit decision.

    ✓ Checkpoint: the goal ledger's answer-key row (Data → Sources → Details → Readiness overview) counts toward 100 rows, so at the recipe's recommended 60 it shows partial progress. That is fine for now. Synthetic drills add training rows, not answer-key rows, so grow the key by hand if you want the row to reach 100. If the row says nothing has been promoted, go back to Data → Labels and confirm rows landed in the Answer key card — the Answer key diagnostics block counts them.

    Don't skip refusal examples

    Your answer key must contain rows where the right answer is the canonical refusal phrase ("I don't have enough context to answer that."). Add 5-10 of these manually — questions that are obviously off-topic for your domain. Without refusal examples in gold, the model never learns to refuse, and the discipline pack's appropriate_refusal_rate gate will fail.

    Splitting train, validation, test

    BrewSLM splits when you click Run Split on Data → Split (the Train / Val / Test Split form; the split adapter should read rag-grounded). The default ratios are 80% train / 10% validation / 10% test, with a deterministic seed so the splits are reproducible.

    Override the ratios in the same form when:

    • Your answer key is small (under 80 rows): use 70/15/15 so the val/test splits have at least 10 rows each.
    • You're working with class imbalance (some question categories rare): set Stratify By Field to the category column.
    • You want a held-out test set you'll only score against at the very end: bump test to 20% and run repeated rounds against val only.

    The prepared splits land as data/projects/<id>/prepared/{train,val,test}.jsonl plus a manifest.json (snapshots under prepared/versions/) and get pinned in the project's manifest with row counts and a content hash. If anything drifts later (you re-imported, you ran another cleanup), the goal ledger flags the version mismatch and Data → Split → Details → Dataset versions lets you make a version active again or re-split.

    Generate synthetic drills

    This is where the rag-protocol recipe earns its name. Three playbooks ship with the recipe, each drilling a different protocol behaviour:

    POSITIVES_PARAPHRASE — citation drill
    Vary the wording of the question; keep the answer and citation marker verbatim. Goal: the model learns that the same fact answers many phrasings. It seeds from your answer-key rows and keeps their context and answer verbatim, so it needs triples to start from. Generate ~50 rows from your 60-row gold seed.
    REFUSALS — context-insufficient drill
    Generate questions that the provided context can't answer, paired with the canonical refusal phrase. Two flavours: off-topic context (real context but unrelated to the question) and no-context (empty context). Goal: the model learns to refuse on structural absence, not just on hard questions. Generate ~30 rows.
    FORMAT_ROBUSTNESS — register-invariance drill
    Same semantic question, different REGISTERS — terse ("Return window?"), verbose ("Could you please tell me how many days I have to return an item?"), formal, polite, imperative. Same answer, same format. Goal: the model holds its output format regardless of how the input is phrased. Generate ~40 rows.

    Open Data → Generate. The step's form is the generic generator — Generation Mode (Single-turn Q&A for this tutorial), Provider, Model Name, Source Text with Load from Cleaned Data. The recipe's playbooks are under Details → Playbooks: the rag-protocol recipe shows three playbook cards (Paraphrase positives, Refusals, Format robustness). Click each, set the target count, pick a backend (a local model through Ollama is the free default; a cloud provider key or any OpenAI-compatible endpoint also works). Generation runs as a background job — the bell surfaces progress, and Details → Playbook center keeps each playbook's last run.

    Don't generate everything before reviewing

    Run the citation playbook first, generate 20 rows, review them. The playbook prompts are fixed, so if the rows are poor, fix your seed rows or try a different backend or model. Then run the refusal playbook with 20 rows. Then format. Generating 200 rows up front and reviewing all of them after the fact is harder than three quick cycles.

    Review the synth queue

    Every generated row lands in the Review queue (Data → Generate → Details → Review queue) with review_status="pending". The queue groups rows by source playbook so you can review one category at a time. For each row you have three actions:

    • Accept — the row joins the training corpus on the next split.
    • Reject — the row is soft-rejected. You can't type a reason; the only reasons are the ones a Pre-screen (review assist) run attaches. The row stays on disk so you can audit later.
    • Purge — a section-level action that physically deletes all rejected rows (optionally only those with one pre-screen reason). Use this once you're confident the rejected pile is genuinely bad data.

    The review queue also shows each row's confidence. Nothing is highlighted, so sort or scan for it: a score under 50% usually means a playbook validator down-scored the row (a lost citation marker multiplies it by 0.45; a missing canonical refusal phrase multiplies it by 0.30). For larger batches, the Pre-screen card asks a model to give each pending row a verdict and reason, so you can group by Verdict + reason, accept the clean group and look at the failures first. It never accepts or rejects by itself.

    Training configuration

    Open Train. The form shows Base model, Task, Seeds and Run name; the hyperparameters below sit under More options → Model and hyperparameters and LoRA and advanced training. The defaults are sensible — for a first run, accept all of them. Several are auto: they resolve from your model and data size, and the confirm dialog shows the resolved values before you launch.

    Base model
    HuggingFaceTB/SmolLM2-135M-Instruct. Small, instruction-tuned, runs on consumer hardware. Alternative: Qwen/Qwen2.5-0.5B-Instruct for slightly better quality at 4x the size.
    Adapter
    LoRA, rank 16, alpha 32, target modules auto — on models of 2B parameters or fewer that means every linear layer (all-linear), since attention-only targets under-fit a model this small.
    Learning rate
    2e-4. Higher than full fine-tuning because LoRA has fewer trainable parameters.
    Epochs
    Auto. The trainer aims for about 200 optimiser steps and caps epochs by dataset size (up to 8 for 100–999 rows). For 200 training rows that resolves to 4 epochs. Typing an epoch count turns auto off; watch validation loss if you do.
    Batch size + gradient accumulation
    Batch 4, accumulation 4 configured, but with auto epochs the trainer shrinks accumulation first on small datasets, so 200 rows train at accumulation 1 (effective batch 4). Lower the batch on GPUs under 8 GB.

    Training runs on the Celery worker, so Redis and the worker from Tutorial 0 must be up; without the worker the run reads RUNNING but never makes progress, and without Redis it is marked Failed at hand-off. Expected runtime (a rough guide, not a measured benchmark): minutes on a single GPU, longer on CPU. The runs list below the form shows live loss; if loss isn't dropping after the first 50 steps, cancel the run and check your data — the dataset is probably misshapen.

    ✓ Checkpoint: in the runs list under Train, your run's loss drops steeply over the first steps and then flattens (the exact values depend on your data and model). The bell shows a "training" notification with a percentage. When complete, BrewSLM runs the lift check against the base model on its own; Results → Verdict shows the summary card (or an Evaluate this run button if the check didn't run).

    Read the trainability forecast

    Before kicking off a real training run, the platform pre-computes a trainability forecast: given your current data + answer key + base model, what's the predicted F1 / pass rate? It lives under Train → More options → Plan and gaps; the goal ledger (Data → Sources → Details → Readiness overview) shows the same number as the predicted_pass row.

    For a healthy support FAQ project you want:

    • Predicted pass probability ≥ 65%. Below that means the data is genuinely too thin or imbalanced — add more gold, run more synth, or pick a stronger base model.
    • Answer-key readiness ≥ 100% (i.e. ≥100 rows). Below that the forecast becomes noisy.
    • Data ready = met (training rows + mapping + splits all green).

    If the forecast is below 50%, training will almost certainly fail the pass/fail rules. Add data before you train — the goal ledger's blockers panel tells you which component is weakest.

    Evaluation: the discipline gates

    After training, the platform automatically evaluates against the project's rule set. Results → Verdict shows the Pass/fail rules card (run, rule set, PASS / FAIL, the failed required rules) below the summary card, both naming the run they describe. Out of the box that rule set is the general default (evalpack.general.default), as in the figure below; picking the rag-protocol recipe does not change it. Switch it once, after your first run:

    Which rule set am I scored against?

    Each project's pass/fail rules come from one rule set (an eval pack). BrewSLM takes the first of these that applies:

    1. The rule set chosen for the project. Clicking Use scaffold saves the drafted rules and makes them the choice (evalpack.project.scaffolded). Picking a built-in pack, such as evalpack.quality.strict or evalpack.domain.legal, or applying a pipeline recipe also sets it.
    2. The domain profile's thresholds (evalpack.domain-profile). Every project resolves a profile, at least the platform default generic-domain-v1, so with nothing chosen this is the rule set: F1 ≥ 0.65, LLM-judge pass rate ≥ 0.75 and safety pass rate ≥ 0.90 are required; exact match ≥ 0.55 is reported but not required.
    3. evalpack.general.default, only for a profile with no thresholds: accuracy and macro-F1 ≥ 0.5 for classification; exact match ≥ 0.4 and F1 ≥ 0.5 for instruction tasks.

    A scaffold is a draft until you click Use scaffold. The task type (recipe) only shapes that draft; for classification it proposes macro-F1 ≥ 0.65, accuracy ≥ 0.70 and per-class F1 ≥ 0.50.

    Two neighbours are easy to mix up with a rule set:

    • A domain preset picked at project creation (Legal, Customer Support, Healthcare, Finance) sets the base model, adapter defaults and an export gate, which decides whether export must pass the rule set. It does not choose the rule set.
    • A domain pack (the only built-in one is general-pack-v1) carries defaults such as the split ratios and a default profile. Packs apply live: editing one changes every project that uses it, so duplicate a pack before you edit it.

    To see which one is active, look at the Pass/fail rules card in evaluation: it names the Active Pack and its Source, for example "domain profile default".

    1. Open Results → Failures with your run selected and find the Pass/fail rules card.
    2. In Project rule set, pick RAG Protocol — Discipline Gates (6 rules). Every later evaluation of the project scores against it.
    3. Don't click Use scaffold on this project. The scaffold panel only appears while the picker is on Auto, and for rag-protocol it offers a generic instruction-tuning draft, not the discipline rules.

    evalpack.rag_protocol.discipline has six rules. Four are required:

    Citation rate ≥ 75%
    Share of answers whose token overlap with the retrieved context meets the faithfulness threshold (0.7). Despite the name it is a grounding rate: it never looks for the [#N] marker, so the citation drills don't move it directly. A low score means the model is answering without grounding in the passages. Check the markers yourself in Results → Try it.
    Hallucination rate ≤ 15%
    Mean fraction of answer tokens NOT supported by the context. High score = the model is filling in facts that aren't in the passages.
    Appropriate refusal rate ≥ 80%
    The share of rows where the model's refuse/answer choice matches the gold's — refuses when gold refuses, answers when gold answers. A refusal counts only if the answer contains one of a fixed set of phrases built around the canonical one. The majority class dominates: with 6 refusals in 60 rows, a model that refuses everything scores 0.10, but one that answers everything scores 0.90 and passes. So also check refusal recall on the refusal rows (per-row rag_pred_is_refusal vs rag_ref_is_refusal).
    F1 ≥ 0.55
    Standard SQuAD F1 over the answer span. The legacy QA-shape gate that lets you compare the rag-protocol score to your old qa-sft baseline.

    Two more are optional: format consistency ≥ 0.75 and safety pass rate ≥ 0.90.

    The Pass/fail rules card names the failed required rules, and the goal ledger's eval_pass_rate row expands into a per-rule breakdown so you see exactly which discipline is failing — "citation 72%/≥75% failed, hallucination 18%/≤15% failed, refusal 85%/≥80% passed."

    When the eval fails (reroute trace)

    Common failure patterns and the fix for each:

    SymptomRoot causeFix
    Citation rate < 60%Answers drift away from the context (a grounding failure, not a missing marker)Run another Paraphrase positives round (50+ grounded rows), check the gold answers quote their context, retrain
    Hallucination rate > 30%Gold set too thin; model has no grounded examples to imitateAdd 30+ gold rows, focus on contexts the current model gets wrong
    Refusal rate < 50%Not enough REFUSALS playbook rows in trainingRun the Refusals playbook for 30+ rows, retrain
    F1 strong but all discipline gates failModel memorised answers without learning the protocolStronger refusal/citation drills; consider switching to a larger base model
    Every gate fails by 20+ pointsTask is knowledge-bound, not behaviour-boundRun the Auto-RAG comparison (Results → Compare) — base model + retrieval may be enough

    When the platform's post-eval decision engine recommends a reroute, the recommendation card sits on Results → Failures. Expand the "Why this fired?" disclosure on each signal. You'll see the actual numbers ("Jaccard 0.18 < 0.20 threshold", "matched_keywords: ['answer questions about']") rather than just the recommendation verb. The card's one-click "Switch to RAG (keeps your answer key)" only works on qa-sft projects; on a rag-protocol project it fails. Here, open Results → Compare and run the Auto-RAG comparison instead, which scores the base model with and without retrieval next to your fine-tune.

    The honest move

    Knowing when NOT to fine-tune is as valuable as knowing how. If the discipline pack flags hallucination at 35% and the reroute trace says your task is knowledge-bound, more training won't help. Run the base-model-plus-retrieval comparison and ship whichever wins. The platform won't stop you training again, but its reroute recommendation tells you when more epochs are unlikely to help; take it seriously.

    Ship the model

    Once the rule set passes, ship in four steps:

    1. Export the model. Open Ship → Package. In the New export card pick the run under Experiment and a Format: HuggingFace (a LoRA run is merged into its base model) for vLLM, or GGUF (CPU) for Ollama. GGUF needs a compressed file first: open Options → Compress first, pick the training run, set Output Format to GGUF and click Quantize (the LoRA adapter is merged automatically). Then Run Export. The export lands under data/exports/<project>/<export>/run-<UTC timestamp>/ and appears in the Exports table.
    2. Get the launch commands. Expand the export's row and click Serve Plan. The One-Click Serve Plan card shows the Setup Commands and the Launch Command. For a HuggingFace export the vLLM runner is 
      python -m vllm.entrypoints.openai.api_server --model ./model
      For a GGUF export the setup writes a Modelfile (FROM ./model/<file>.gguf) and runs ollama create; the launch command is ollama serve. There are no deploy scripts in the bundle.
    3. Put retrieval in front of it. A stock vLLM or Ollama process doesn't load any retrieval index, so the model only cites what you put in its context. Your app (or a small /ask service) retrieves the FAQ passages and sends them with the question. The BrewSLM gateway on Ship → Deploy (card Use from Claude Code) can add one retrieval call per request, but over the project's document passages index, which exists only if you brought in documents.
    4. Smoke-test in the playground. Open Results → Try it, set Provider to "Trained run (this project)" and pick your run under Training run. Ask 10 real customer questions; check that each answer cites a chunk and that off-topic questions get the canonical refusal. Each reply's retrieval chip tells you what was retrieved for it — your sanity check.

    What's next

    You have an exported protocol-aware support assistant. Three obvious next moves:

    Swap the corpus
    The same trained adapter works for legal QA, healthcare support, internal IT, ecommerce returns — anywhere you have a (context, question, answer) shape. Build a new index over the new corpus; no retraining needed. This is the protocol-over-domain payoff.
    Refresh the index monthly
    FAQ content changes. Schedule a periodic re-ingest of your help center into whatever index your serving app retrieves from; a BM25 index rebuilds in seconds. The trained adapter doesn't care which facts are in the index — it cares that they're cited.
    Active learning loop
    Capture real customer questions that produced low-confidence answers. Promote the best ones into the answer key; retrain when it grows by ~50 rows. Over a quarter, the model gets noticeably sharper on the questions your customers actually ask.

    The next tutorial in this series picks a different recipe: SQL injection classifier — same end-to-end shape, classification recipe, hard-negative drills, a benign-recall floor so real traffic isn't blocked. Same workflow, different platform path.

    Key terms

    rag-protocol recipe
    BrewSLM recipe that trains a small model to cite the retrieved chunk, refuse cleanly, and hold output format. Domain-agnostic — facts live in the retrieval index, not the weights.
    Citation marker
    The [#N] token in an answer that points at the source chunk. The training signal the model imprints from the gold + synth data.
    Canonical refusal phrase
    "I don't have enough context to answer that." The single recognisable shape the model emits when the retrieval is insufficient; downstream consumers can detect it.
    Discipline gates
    The rules in evalpack.rag_protocol.discipline: four required (citation rate, hallucination rate, appropriate refusal rate, F1) and two optional (format consistency, safety). Select it in the Project rule set picker; the recipe doesn't.
    Goal ledger
    The single "% toward your stated goal" widget in the Readiness overview (Data → Sources → Details), expanding into per-component readiness (data, answer key, predicted pass, eval pass rate with per-rule breakdown).
    Reroute-to-RAG
    One-click clone that creates a RAG-first sibling project (base model + retrieval, no LoRA). The "task is knowledge-bound, not behaviour-bound" escape hatch. It only clones qa-sft projects; on rag-protocol, use the Auto-RAG comparison.
