      How to read the result

      Allocated is what PyTorch's allocator hands out at the training peak, the number torch.cuda.max_memory_allocated() reports. The training peak adds an overhead line: the CUDA context, allocator fragmentation and, on unified memory, the Python process and page cache that share the same pool. That is the number to compare with your GPU. GiB means 230 bytes; GPUs are sold in GB (109 bytes), so the "fits" line converts.

      The evaluation line is the same model generating at the same length with batch 1: weights plus the KV cache. It is usually far below the training peak, which is why a model you can evaluate may still not train. For the bytes-per-parameter view of the same terms, see the memory table in Lesson 1.15 (GPU memory math); when a run does not fit, Lesson 1.16 (OOM and how to survive it) lists the levers in order.

      The formulas

      All terms are bytes. P is the total parameter count, T the trainable (adapter) parameters, n = micro-batch × tokens per row, L layers, h hidden size, q = heads × head size, kv = key/value heads × head size, f the MLP width (top-k × expert width for a mixture of experts), V the vocabulary.

      Two honest caveats. The overhead line is calibrated on that one 30B-A3B run, so the whole-pool rows are not an independent test of it; on another machine, driver or allocator setting the overhead can differ by a few GiB. And the 1.15 measurements count tensors kept after the forward pass, so the calculator's activation bar adds what they cannot see: with checkpointing on, the one layer that is rebuilt during backward (0.08 GB in the 135M case).

      The unified-memory gotcha: loading

      On a machine where the CPU and GPU share one memory pool, the training peak is not the only peak. Loading weights to the CPU and then copying them to the GPU briefly holds two copies, and the operating system's page cache can hold a third (the files just read). For the 30B-A3B model that is about 114 GiB plus up to 57 GiB of cache on a 128 GB box: an out-of-memory error before the first step, even though training itself peaks near 77 GiB. The fix is to create the CUDA context first and load the weights straight to the device. In the calculator, pick "unified memory" to see the load line.

      What this ignores

      • Attention without SDPA or flash attention ("eager"): it keeps a heads × tokens² matrix per layer, which this calculator does not add.
      • Fused or chunked loss kernels, which shrink the logits term; and TRL casting a QLoRA adapter to bf16, which brings its states to about 8 bytes per parameter instead of 16.
      • Other architectures: the activation formulas were counted on decoder layers with RMSNorm, a SwiGLU MLP and grouped-query attention, and on fused-expert mixture-of-experts layers with q/k norms (transformers 5). Other layouts, such as per-expert linear layers or no q/k norms on a mixture of experts, are approximated from the same terms.
      • Quantized mixtures of experts on a GPU: that bitsandbytes leaves fused experts unquantized was checked by loading a small model on a CPU, not in a GPU training run.
      • Multi-GPU sharding (ZeRO, FSDP), CPU offload, sequence packing, and DeepSpeed or framework buffers.
      • Short-lived buffers: a quantized layer's dequantized copy, matmul workspace, the optimizer step's temporaries.
      • Rows shorter than the longest one in their batch: real batches vary, so this is an upper bound for the length you enter.
      • Speed. The calculator says whether a run fits, not how long it takes.

      Questions

      Why does a 1.5B model need over 20 GiB to train at 2,048 tokens?

      Mostly the logits. Every token produces a score for every vocabulary entry, and the loss works on them in fp32: with a 152k vocabulary, a micro-batch of 4 × 2,048 tokens keeps about 4.6 GiB of fp32 log-probabilities and needs about twice that again while the loss backpropagates, about 14 GiB in all, against 2.9 GiB of bf16 weights. Halving the micro-batch or the row length halves it; a fused loss kernel avoids most of it.

      Does gradient accumulation raise peak memory?

      No. The peak is set by the micro-batch, the rows on the device in one step. Accumulation runs more micro-batches before each optimizer step and adds their gradients into buffers that exist anyway, so it raises the effective batch without raising the peak.

      Why doesn't LoRA shrink activation memory?

      LoRA freezes the base weights, so it removes their gradients and optimizer state. The backward pass still runs through every layer to reach the adapters, so the tensors each layer keeps for it are still there. Gradient checkpointing is the lever for activations: it keeps only each layer's input and rebuilds the rest during backward, at the cost of about one extra forward pass.

      Why does a 30B mixture of experts need memory for 30B parameters when only 3B are active?

      Every expert has to be in memory, because any token can be routed to any of them. The active count sets the compute per token and the size of the activations; the total count sets the weights. That is why the 30B-A3B run spent about 57 GiB on weights and only a few GiB on activations.

      What does QLoRA save?

      The frozen base: 4-bit NF4 weights take about a quarter of their bf16 size (4.127 bits per parameter with double quantization). Only the linear layers are quantized. The embeddings, an untied output head and the norms are not, and prepare_model_for_kbit_training, the recipe in Lesson 2.11, casts them to fp32, which also makes the activations fp32. So on a small model with a large vocabulary the saving is small: a 7B model with an untied 152k vocabulary keeps about 1.1 billion parameters in fp32, about 4 GiB. On a fused-expert mixture of experts the experts are not quantized at all. QLoRA helps most on large dense models with modest batches.

      How accurate is this?

      On the measured runs in the validation table it is within 1.5%, and the activation formula reproduces the per-layer counts it was fitted on exactly. Real runs differ by the overhead (driver, allocator, other processes), by architecture details this does not model, and by padding. Read it as a plan, then confirm with torch.cuda.max_memory_allocated() after the first steps.
