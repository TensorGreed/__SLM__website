    Scoring modes: how each task shape is scored

    One pass rate can't score a classifier, a JSON extractor and a free-text answer fairly. BrewSLM picks a scorer from the project's task shape. Here is each one, what counts as a pass, and the switches that change it.

    Checked against: BrewSLM main at 808833e Updated: 23 Nov 2026

    Every held-out eval goes through a handler chosen from the project's task profile (backend/app/services/eval_task_handler_service.py). An unknown profile falls back to a generic handler rather than failing. We wrote up the reasoning in a blog post; this page is the reference.

    Which handler scores what

    Task profileHandlerHeadline
    qa, instruction_sft, chat_sft, language_modelingQAJudge score when a judge applies, else token F1 and exact match
    classificationClassificationAccuracy, macro F1, per-class P/R/F1, confusion matrix
    structured_extraction, extractionStructured extractionDepends on the scoring mode (below)
    tool_callingTool callTool-call pass rate
    rag_qa, rag, grounded_qaRAGEM / F1 plus faithfulness and context recall
    seq2seqSeq2SeqBLEU and chrF (translation), ROUGE (summaries)
    dpo, orpo, preferenceAlignmentShare of rows closer to the chosen answer than the rejected one
    safety, refusalSafetyPass rate per attack type

    There are also handlers for vision-language and audio transcription (WER and CER). We mention them for completeness; we have not shipped a showcase on either.

    Free text: exact match, F1 and the judge

    Exact match and token F1 use SQuAD-style normalisation: lowercase, drop the articles a / an / the, drop punctuation, collapse whitespace. If the answer contains a marker such as "Final answer:" the scorer reads what follows it. Both are fine for short answers. For long ones they mislead, and we have the run to prove it: on IRS Publication 17, run #148 doubled its token F1 (0.13 to 0.27) while its judged correctness fell from 0.20 to 0.02. It learned how the answers sound, not what they say.

    So for QA-like profiles with long references (median reference of 8 words or more) BrewSLM adds an answer judge. The judge reads the question, the answer key and the model's answer and returns correct, partial or wrong, scored 1, 0.5 and 0; judge_correct is the mean (backend/app/services/answer_judge_service.py). The judge is picked in this order: the EVAL_JUDGE_BACKEND setting, the project's judge, then the first local model available, and only when no local model answers, a cloud judge you have configured. A paid cloud model is never picked over a reachable local one, because the judge makes one call per row per eval. If no judge is reachable, the metric is absent and F1 stays the headline. It is not faked.

    A judge is a model and can be wrong. Settings → Judge model has a calibration flow: label a sample of judged answers blind (20 by default, up to 100), and BrewSLM reports agreement, how often the judge was too strict or too lenient, and a weighted kappa. Under 20 labels, or fewer than 5 in either class, it says "too few labels". A judge is "below floor" when the upper end of its strict-agreement interval is under 0.70, or the lower end of its too-strict or too-lenient rate is over 0.15.

    JSON fields

    Structured extraction's default mode is field_match. It scores in layers: is the output valid JSON, does it have the required fields, and is each field right. The per-field comparison is typed: numbers as numbers, booleans as booleans, strings after normalising case and spacing, and null as its own class. It reports null precision and recall too, plus how often the model invented a value the reference doesn't have and how often it said null when the value was there. The headline f1 is the mean per-field F1; exact_match is every field right on the row.

    One switch matters a lot here: Null counts as absent (off by default). With it on, "key": null and a missing key are the same thing, on both sides and in nested objects. Set it per project or per eval run. Compare refuses to pair results scored under different settings, and the lift check won't reuse a base result scored the other way. On the NTSB accident extractor the Verdict card showed per-field F1 of 0.960 for the fine-tune against 0.519 for the base model, on 1,234 test narratives.

    Spans

    span_set is strict. A predicted span counts only when its type, start and end all match a reference span, and a duplicate has to be found twice. There is no partial or overlap credit. It reports micro and macro precision, recall and F1, per-type counts, and exact_match as "rows with every span right". Strict is harsh on purpose: for redaction, a span that stops one character short still leaks. Our sensitive-data tagger went from span F1 0.74 to 0.85 against a second-opinion answer key mostly by fixing the training labels (missing phones and emails, inconsistent conventions), not by training longer. A loose scorer would have hidden most of that gap.

    Tool calls

    A tool-call row passes when the model picked the right tool and the arguments match, and, if the project has a tool catalog, the call is valid against it (backend/app/services/tool_call_scoring.py). {"tool": "none"} is an explicit "no call". By default an extra argument the reference doesn't have is ignored. Turn on strict arguments and any extra key fails the row; the card then leads with the strict pass rate. The difference is real: our tool-call model scored 553 of 600 under the default and 543 under strict.

    SQL execution

    For text-to-SQL, string matching is close to useless. With SQL execution match on (off by default), the reference query and the predicted query both run against each configured SQLite database, and the row passes only if the results match on every database. Row order counts only when the reference's outer query has ORDER BY. Floats compare with a relative tolerance of 1e-6 and NULL equals NULL. Queries run read-only, one statement, SELECT only, 2-second timeout, 10,000-row cap. A reference query that errors makes the row unscoreable, and it is left out of the totals rather than counted as a pass or a fail.

    Classification

    The predicted label is found in the output by matching against the label set, and anything that matches no label counts as unparseable (reported as its own rate). Metrics are accuracy, macro F1, per-class precision, recall and F1, and a confusion matrix up to 20 classes. Macro F1 is there because accuracy flatters a classifier that ignores the rare class.

    Where you set it

    The scoring mode comes from the project's task shape, which you confirm on Data → Labels. The switches above (tool-call scoring, null counts as absent, SQL execution, plan rubric, remediation checks) are under Results → Verdict → How it's scored → Change how it's scored. The card itself prints one line per scored set, such as "scored as JSON fields · null counts as absent · max 256 new tokens, temperature 0", so a number never travels without its rules.

    See it on a result

    Results → Verdict → + Score this run. The form shows a read-only "Scored as" line when the scoring mode decides the score. Under its Advanced section you can pick a metric and a judge for free-text runs. Then read the "How it's scored" card before you read the number.
