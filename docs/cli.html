    The brewslm command line

    The CLI is a thin client for the same HTTP API the web app uses. Anything you click can be scripted. This page lists the command groups and the flags you will actually use, generated from the parser at the commit above.

    Checked against: BrewSLM main at 808833e Updated: 23 Nov 2026

    The CLI is ./brewslm at the root of the repository. It runs backend/scripts/brewslm.py with the backend's virtualenv Python when there is one, and plain python3 otherwise. It needs httpx and a running backend; it does not touch the database or the GPU itself. Every command maps to an API call, so the CLI can't do anything the API can't, and the reverse is mostly true too. The tables below were produced by walking the parser (build_parser()) rather than written by hand, then trimmed to the commands most people need. ./brewslm <command> --help prints the rest.

    Connecting and logging in

    Global flags come before the command:

    FlagDefaultNotes
    --api-basehttp://127.0.0.1:8000/apiOr BREWSLM_API_BASE. A bare http://host:port gets /api added.
    --tokennoneOr BREWSLM_TOKEN; else the file auth login --save wrote (~/.brewslm/token, or BREWSLM_TOKEN_FILE).
    --timeout-seconds60Per HTTP request. Or BREWSLM_TIMEOUT_SECONDS.

    Login is on by default in BrewSLM, so the first command is usually:

    ./brewslm auth login --username admin --save
./brewslm auth whoami
./brewslm version --remote

    The password falls back to BREWSLM_PASSWORD, then a prompt. On a dev install the password is the API_KEY from backend/.env. --save writes the token with 0600 permissions on POSIX systems.

    A first run from the terminal

    ./brewslm project list-demos
./brewslm project create-demo --slug support-faq     # idempotent: returns the existing one
./brewslm doctor --project-id 1
./brewslm train start --project-id 1 --autopilot --one-click --plan-profile safe
./brewslm logs tail --project-id 1

    The demo slugs in the code are support-faq, sentiment-classifier and pii-detector. Project ids are whatever your install assigns. Use the one create-demo prints.

    train start is the autopilot launch: it plans a config from the project, runs preflight and starts the run. Without --autopilot --one-click it says it is defaulting to that mode. Useful flags:

    FlagDefaultNotes
    --base-modelproject'sOverride the base model for this run
    --target-devicelaptopmobile, laptop or server
    --plan-profilebalancedsafe, balanced, max_quality, fastest, best_quality
    --available-vram-gbnoneTell the planner your memory budget
    --dry-runoffAutopilot v2 dry run: show the plan, start nothing
    --run-namenoneOtherwise named after the date

    To repeat a run exactly, train rerun creates a new run whose config is the parent's launch manifest verbatim; train clone does the same with shallow overrides. Both are better than retyping a config when you want a second seed or one changed knob.

    Evaluating and comparing

    ./brewslm eval run --project-id 1 --experiment-id 3 --eval-type llm_judge --max-samples 200
./brewslm eval compare --project-id 1 --baseline 2 --candidate 3

    eval run defaults to the test split, exact_match, 100 rows, 128 new tokens and temperature 0. --eval-type takes exact_match, f1 or llm_judge. Note the CLI's default of 128 new tokens is lower than the automatic lift check's 256, so a CLI result and the Verdict card can disagree on long answers until you pass --max-new-tokens 256. eval compare diffs the latest metrics of two runs by eval type. The paired verdict described in the lift check is what the Verdict card shows; the CLI prints the metrics.

    Exporting and serving

    ./brewslm export --project-id 1 --experiment-id 3 --format gguf --quantization 4-bit
./brewslm serve plan --project-id 1 --export-id 5
./brewslm serve start --project-id 1 --export-id 5 --template-id ollama_local

    --format is one of huggingface (the default), gguf, onnx, tensorrt or docker. --no-run creates the export without running it, and --no-smoke-tests skips the smoke checks. serve start picks the first available serve template (Ollama, vLLM or llama.cpp) when you don't name one. What each format needs on the machine is on the export formats page.

    Getting data in

    ./brewslm dataset import --project-id 1 --file tickets.jsonl
./brewslm ingest --project-id 1 --source hf --id <owner/dataset> --split train --max-samples 5000 --wait

    ingest takes --source hf, kaggle or url, an optional JSON --field-map, and saved secrets for gated datasets unless you pass --no-saved-secrets. --wait polls until the import finishes (every 3 seconds, up to 30 minutes).

    When the CLI is the better tool

    Anything you repeat: re-running a config with train rerun, nightly eval run against a fixed answer key, or manifest export to keep a project's brewslm.yaml in git next to your code. For a first project, the web app shows you more of what is going on.
